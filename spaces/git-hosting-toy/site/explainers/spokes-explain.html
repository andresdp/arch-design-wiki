Git hosting for a fast-growing engineering organization

A self-hosted Git service must support 3,000 engineers in four regions and about 40,000 CI jobs per day, including use of a 200 GB repository with 15 years of history. Five engineers build and operate it in the company's cloud account.

The solution

S · Replicated Git file servers with Spokes-style routing

Plain Git repositories on local server disks are replicated three ways, reference writes use three-phase commit, and reads go to the nearest current replica. Engineers use standard Git clients and full clones.

Composed of 3 partial design points, one per ADR:

  • ADR1 · Three server-disk Git replicas with majority writes and three-phase commit Q1Q4R1 Source of truth for repository state → Repository files on server disksReplication for durability → Three Git replicas with majority writesReference update coordination → Three-phase commit across replicas
  • ADR2 · Full clone over the Git protocol R1R2C2 Client data transfer → Full clone over the Git protocol
  • ADR3 · Nearest up-to-date replica, including remote read replicas Q3Q4 Serving reads → Nearest up-to-date replica

As a whole: Plain Git repositories on local server disks are authoritative, with three replicas for each repository. Reference updates use three-phase commit across replicas, writes succeed after a majority, and clients perform full Git clones from the nearest replica with the latest state.

ADR1 · Authoritative state, replication, and reference updates Q1Q4R1

Context. The service must preserve every accepted push through one machine or disk loss and let subsequent fetches observe committed reference updates. Pushes must continue to use standard Git.

Decision. Three server-disk Git replicas with majority writes and three-phase commit.

Three server-disk Git replicas with majority writes and three-phase commit chosen

Source of truth for repository state → Repository files on server disksReplication for durability → Three Git replicas with majority writesReference update coordination → Three-phase commit across replicas

“Every repository is stored as a plain Git repository on the local disks of three file servers, placed in different racks. The three replicas are the authoritative copies; there is no separate database of repository contents.”
“The three replicas are the authoritative copies; there is no separate database of repository contents.”
“A push updates references through a three-phase commit: a proxy sends the update to all three replicas, each takes a lock and votes, and the update commits once a majority has agreed.”
  • Meets the single-machine durability scenario through three copies and majority writes.
  • Coordinates reference updates across replicas and supports current-state reads.
  • Attested in combination by Git at any scale and Stretching Spokes.
  • Adds replication and transaction overhead to writes.
  • The solution does not quantify failure recovery time.

The requirements force a replicated durable design among the evaluated options: the single-copy contrast misses Q1. The exact server-disk authority and three-phase commit are not shown to be forced by the requirements.

Single copy on a file server discarded

Source of truth for repository state → Repository files on server disksReplication for durability → Single copy on a file server

  • Avoids the storage overhead of multiple repository copies.
  • Loss of the file server can lose the only copy, failing Q1.
  • Does not provide replica participants for three-phase commit.

Rejected by the durability requirement; this is a design-space contrast, not an option the solution says its designers considered.

ADR2 · Client transfer for large repositories R1R2C2

Context. Engineers must use standard Git, and the largest repository must be usable without downloading its full contents and history.

Decision. Full clone over the Git protocol.

Full clone over the Git protocol chosen

Client data transfer → Full clone over the Git protocol

“Engineers use standard Git clients and full clones.”
  • Uses the standard Git protocol and client features.
  • Provides a complete local history.
  • Downloads the whole repository, failing R2 for the largest repository.

The solution chooses this option freely, but it does not satisfy R2. The contrast shows partial clone can retain standard Git while meeting R2.

Partial clone with sparse checkout discarded

Client data transfer → Partial clone with sparse checkout

  • Meets R2 by fetching only needed history and files.
  • Retains standard Git features, satisfying C2.
  • Unselected files or history may need to be fetched later.

This design-space contrast would better fit the problem's large-repository requirement, but the solution text does not choose it.

ADR3 · Regional read routing Q3Q4

Context. CI and engineers across regions need reads from the latest repository state with low latency, including after a successful push.

Decision. Nearest up-to-date replica, including remote read replicas.

Nearest up-to-date replica, including remote read replicas chosen approximate fit

Serving reads → Nearest up-to-date replica

“Reads go to the closest replica that is up to date; in remote regions, extra non-voting replicas serve reads without slowing down writes.”
  • Serves reads near clients when a current replica is available.
  • Supports the requirement that a post-push fetch sees the committed state.
  • The 30-second P95 fetch target has no measured validation in the solution or design space.
  • A stale nearby replica must be bypassed.

The routing choice is supported and directly fits Q4, while it only partly supports Q3 because no latency measurements establish the target. The extra non-voting replica detail is not represented by the value.

Approximate fit. The mapped value captures nearest up-to-date reads but not the non-voting status of the extra remote replicas.

#1 The solution as one design point partial the solution

Thought The complete solution combines disk-backed Git repositories, three replicas, transactional ref updates, full client clones, and locality-aware reads.

Move
  • Source of truth for repository state → Repository files on server disks
  • Replication for durability → Three Git replicas with majority writes
  • Reference update coordination → Three-phase commit across replicas
  • Client data transfer → Full clone over the Git protocol
  • Serving reads → Nearest up-to-date replica

Observed The combination is attested by Git at any scale. The value descriptions support standard Git use, durability, and read-after-push routing. The stated 30-second P95 and one-minute operator-free failover targets are not demonstrated by the design-space evidence or solution details; they remain unproven rather than measured misses. Full clones directly conflict with R2. The five-person staffing constraint is not addressed by an operational-effort dimension.

  • Full clone over the Git protocol: gains R1, C2 gives up R2: Full Git clones support standard-client repository access but transfer the whole history, which conflicts with working on the largest repository without downloading it all.

Plain Git repositories on local server disks are authoritative, with three replicas for each repository. Reference updates use three-phase commit across replicas, writes succeed after a majority, and clients perform full Git clones from the nearest replica with the latest state.

The point's trade-off This provides durable copies, coordinated reference updates, and lower read latency. It sacrifices storage efficiency and write performance to maintain three replicas and coordinate commits, while full clones consume substantial client bandwidth and time.

#2 A region of #1: part of the solution grounded

Thought Q1 and Q4 call for authoritative repository state on servers with replicated writes and coordinated reference updates.

Move
  • Source of truth for repository state → Repository files on server disks
  • Replication for durability → Three Git replicas with majority writes
  • Reference update coordination → Three-phase commit across replicas

Observed The point has no warnings, satisfies the required source-of-truth dependency, and is attested by Git at any scale and Stretching Spokes. Its replica and majority-write choices directly support loss tolerance; transactional ref updates and latest-state reads support the consistency requirement. The point description flags added write and transaction latency, but neither requirement sets a write-latency target.

Q1 meetsQ4 meets

Each repository’s authoritative state is stored as plain Git repositories on server disks, with three replicas maintained for every repository. Reference updates run through a three-phase transaction across replicas, while a write is considered durable after a majority has recorded it.

The point's trade-off This provides disk-based simplicity, replication-based durability, and coordinated reference updates, but adds replication and transaction latency and operational complexity. The majority-write rule is in tension with all-replica voting: an unavailable replica may prevent a transaction even when two replicas are ready.

#3 A contrast on #2: one option changed ungrounded

Thought Does Q1 force three replicas rather than the single-copy alternative offered for durability?

Move
  • change Replication for durability: Three Git replicas with majority writes → Single copy on a file server

Observed This contrast changes the replication value to a single copy. Its point description says loss of the file server can lose the sole copy, so it misses Q1. Q1 therefore forces the three-replica choice among this contrast and the solution value.

Q1 misses

The system would expose a plain Git repository stored on a file server’s local disk as the authoritative state, accessed by RPC. Reference updates would be handled as three-phase transactions requiring replica votes.

The point's trade-off This saves storage and replication overhead, but failure of the file server can lose the sole copy, while three-phase coordination adds complexity without improving durability. The single-copy choice conflicts with three-phase commit across replicas because it provides no replica participants to vote.

#5 A contrast on #4: one option changed grounded

Thought Does R2 force a partial clone rather than the solution's full-clone choice, while retaining C2?

Move
  • change Client data transfer: Full clone over the Git protocol → Partial clone with sparse checkout

Observed The partial-clone contrast is supported by Scalar philosophy and Introducing Scalar, and it meets both R2 and the standard-Git-client constraint. The design space therefore offers an alternative that better meets these requirements; full clone is not forced and appears to be a free choice that conflicts with R2.

R2 meetsC2 meets

Each developer uses standard Git to create a partial clone, configuring sparse checkout to materialize only the files needed for their work. The client fetches only the relevant history and content while retaining standard Git features for that reduced view.

The point's trade-off This reduces download size and local storage for focused work, but unselected files or history are unavailable locally and may require later fetching. Workflows requiring the complete repository may be less convenient.

Attested by Scalar philosophy; Introducing Scalar

#6 A region of #1: part of the solution partial

Thought Q3 and Q4 call for serving reads from a nearby replica that already has the latest state.

Move
  • Source of truth for repository state → Repository files on server disks
  • Replication for durability → Three Git replicas with majority writes
  • Serving reads → Nearest up-to-date replica

Observed The solution's routing rule matches nearest up-to-date replica and the point is attested by Git at any scale and Stretching Spokes. This gives a plausible basis for low-latency regional fetches and directly serves read-after-success consistency. The space and solution provide no benchmark for the 30-second P95 target, so Q3 is only partly supported. Remote non-voting replicas also extend the mapped value, which does not encode voting status.

Q3 partlyQ4 meets
  • Nearest up-to-date replica: gains Q4 gives up Q3: Routing to the nearest current replica supports read-after-push consistency and regional locality, but does not by itself establish the 30-second P95 fetch bound.

Each repository is stored as a plain Git repository on server disks, with three replicas maintained for every repository. Writes complete after a majority of replicas records them, while fetches, clones, and checkouts are routed to the nearest replica with the latest state.

The point's trade-off This provides durable data across one machine failure and reduces read latency through locality. It requires maintaining three copies and coordinating majority writes, and reads may need to bypass a nearer replica if it is stale.
