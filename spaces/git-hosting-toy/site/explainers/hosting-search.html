Git hosting for a fast-growing engineering organization

A company-operated Git service supports 3,000 engineers in four regions and about 40,000 CI fetches per day. The largest repository has 15 years of history and is about 200 GB. A five-engineer team builds and operates the service in the company's cloud account.

Requirements

The alternatives the agent proposes, then its decisions as architecture decision records: each ADR addresses a few related requirements and weighs options (partial design points), chosen by one or more alternatives or discarded. Select an alternative or an option to see it in the graph.

Alternatives

A1 · Replicated Git with flexible read caches

Keep plain Git repositories authoritative, replicate writes to a majority, and use partial clone with sparse checkout. Serve through local disk caches that can be confirmed current.

Composed of 4 partial design points, one per ADR:

  • ADR1 · Replicated Git repositories Q1 Source of truth for repository state → Repository files on server disksReplication for durability → Three Git replicas with majority writes
  • ADR2 · Three-phase commit across replicas Q4 Reference update coordination → Three-phase commit across replicas
  • ADR3 · Partial clone with sparse checkout R2Q3Q4C2 Client data transfer → Partial clone with sparse checkout
  • ADR3 · Stateless servers with a local disk cache R2Q3Q4C2 Serving reads → Stateless servers with a local disk cache

As a whole: Each server stores an authoritative plain Git repository locally, with three replicas accepting writes only after a majority acknowledges them. Reference changes use three-phase commit across replicas; clients use partial clone with sparse checkout, and any server can serve reads from its local disk cache.

B1 · Object-storage log with current regional replicas

Make an append-only object-storage log authoritative, use compare-and-swap for references, and serve sparse partial clones from nearby replicas only after they are current.

Composed of 4 partial design points, one per ADR:

  • ADR1 · Object-storage log Q1 Source of truth for repository state → Write-ahead log in object storageReplication for durability → Durability delegated to object storage
  • ADR2 · Compare-and-swap on the log Q4 Reference update coordination → Compare-and-swap on the log
  • ADR3 · Partial clone with sparse checkout R2Q3Q4C2 Client data transfer → Partial clone with sparse checkout
  • ADR3 · Nearest up-to-date replica R2Q3Q4C2 Serving reads → Nearest up-to-date replica

As a whole: The object-storage append-only log is the authoritative repository state, with compare-and-swap ordering reference updates atomically. Disk repositories are disposable derived replicas; clients use partial clone and sparse checkout, while reads are routed to the nearest replica confirmed current with the log.

ADR1 · Where repository state is authoritative and durable Q1

Context. The service must preserve successful pushes through a single machine or disk loss. The design space compares authoritative Git repositories on disks with an authoritative object-storage log; it does not quantify failover time or the team's operational workload.

Decision. Replicated Git repositories (A1); Object-storage log (B1).

Replicated Git repositories chosen in A1

Source of truth for repository state → Repository files on server disksReplication for durability → Three Git replicas with majority writes

  • Three copies with majority-write success protect accepted commits.
  • Plain Git repositories are the authority and serve as familiar units of state.
  • Replica coordination adds operational and write-path complexity.
  • The space does not establish one-minute operator-free failover.

This is the most direct supported match for durable Git state and avoids an extra log-to-repository derivation path.

Object-storage log chosen in B1

Source of truth for repository state → Write-ahead log in object storageReplication for durability → Durability delegated to object storage

  • Server machines hold no unique repository data.
  • Object storage provides the log's durability.
  • Serving depends on log and object-storage access.
  • The space does not establish service recovery within one minute.

This reduces dependence on any one serving machine and keeps the durable history independent of the cache fleet.

Single unreplicated file server discarded

Source of truth for repository state → Repository files on server disksReplication for durability → Single copy on a file server

  • A single server provides a simple authority and avoids replica coordination.
  • Loss of its machine or disk loses the only copy and fails Q1.

It cannot meet the explicit durability requirement.

ADR2 · How successful pushes order repository references Q4

Context. Pushes must update repository refs atomically enough that a fetch beginning after success sees the pushed state. The alternatives coordinate updates across replicas or serialize them with compare-and-swap on a log. Neither the dimension nor its evidence gives a complete end-to-end guarantee for fetch routing.

Decision. Three-phase commit across replicas (A1); Compare-and-swap on the log (B1).

Three-phase commit across replicas chosen in A1

Reference update coordination → Three-phase commit across replicas

  • All replicas vote on a reference update transaction.
  • Fits the replicated Git repository approach.
  • Coordination may add latency and availability dependence on participants.

Choose this with majority Git replicas so push completion follows coordinated reference updates.

Compare-and-swap on the log chosen in B1

Reference update coordination → Compare-and-swap on the log

  • Orders log appends without a separate consensus protocol.
  • Matches the object-storage authority.
  • The source does not prove all derived read replicas observe the update before a fetch starts.

This provides a single ordered update point in the log-based alternative.

Single-server serialization discarded

Reference update coordination → One server serializes the updates

  • One server applies updates one at a time.
  • It retains the single-server failure and durability problem.

Its simple ordering does not compensate for the unreplicated authority.

ADR3 · How developers and CI obtain repository data R2Q3Q4C2

Context. Engineers need to work in a 200 GB repository without downloading all its history, while CI in four regions needs current reads. Standard Git clients are required. Partial clone with sparse checkout is explicitly described as using standard Git features; virtualized filesystems have mixed evidence and may add client integration. The space does not give latency measurements or a standard Git wire-protocol architecture.

Decision. Partial clone with sparse checkout (A1, B1); Nearest up-to-date replica (B1); Stateless servers with a local disk cache (A1).

Partial clone with sparse checkout chosen in A1, B1

Client data transfer → Partial clone with sparse checkout

  • Fetches only needed history and files.
  • Uses standard Git features and best matches C2.
  • Some data remains unavailable locally until fetched; the space does not quantify developer or CI latency.

This is the strongest evidence-backed fit for reduced developer downloads while keeping standard clients.

Virtualized filesystem with on-demand objects discarded

Client data transfer → Virtualized filesystem with on-demand objects

  • Downloads objects only when files are opened.
  • Evidence is mixed and includes a rejection; client integration may conflict with C2.

The small transfer benefit does not justify the client compatibility uncertainty.

Nearest up-to-date replica chosen in B1

Serving reads → Nearest up-to-date replica

  • Regional reads can use the closest replica that has current state.
  • Freshness selection supports read-after-push behavior.
  • The space gives no measured 30-second p95 or behavior during replica lag.

Choose locality with an explicit current-state condition to balance Q3 and Q4.

Stateless servers with a local disk cache chosen in A1

Serving reads → Stateless servers with a local disk cache

  • Any server can serve any repository from a local cache.
  • Supports a flexible multi-region serving tier.
  • Cold caches need rebuilding, and freshness enforcement is unspecified.

This keeps serving capacity flexible in the replicated Git alternative, provided reads are routed only to current copies.

Observed The point is structurally coherent and has no point-check warnings, but no source attests the full combination. It gives a plausible durability and standard-client path; the evidence does not establish the timed availability or performance scenarios.

R1 partlyR2 meetsQ1 meetsQ2 partlyQ3 partlyQ4 partlyC1 partlyC2 meets

Servers keep plain Git repositories as the authoritative state, with each repository replicated three ways and reference updates coordinated by three-phase commit. Writes succeed after a majority commits, reads use the nearest replica with current state, and clients use Git partial clone with sparse checkout.

The point's trade-off This provides durable copies, atomic reference updates, geographically efficient reads, and reduced client transfer, but replica coordination adds write latency and operational complexity. Partial clones reduce bandwidth while making some local history or files unavailable until fetched.

#2 Seed of approach B strong

Thought An object-storage log should preserve accepted writes independently of serving machines, while compare-and-swap orders references; sparse partial clone serves R2/C2 and stateless caches can scale reads.

Move
  • Source of truth for repository state → Write-ahead log in object storage
  • Replication for durability → Durability delegated to object storage
  • Reference update coordination → Compare-and-swap on the log
  • Client data transfer → Partial clone with sparse checkout
  • Serving reads → Stateless servers with a local disk cache

Observed The point check found no warning, but the combination is novel in the space. It lowers dependence on a particular serving machine while making log access and cache freshness central to serving.

R1 partlyR2 meetsQ1 meetsQ2 partlyQ3 partlyQ4 partlyC1 partlyC2 meets
  • Write-ahead log in object storage, Durability delegated to object storage, Stateless servers with a local disk cache: gains Q1, Q2 gives up Q3: Server-independent durable state and interchangeable caches help recovery and read distribution, but cold-cache reconstruction pulls reads through the log and leaves the 30-second target unproven.

The object-storage append-only log is the authoritative repository state, with reference updates serialized by compare-and-swap. Stateless servers rebuild or refresh local cached copies from that log and serve partial-clone and sparse-checkout requests.

The point's trade-off This provides durable centralized history, interchangeable serving machines, and reduced client transfer. It gives up fast cold-cache reads and makes serving dependent on object-storage availability and log replay; concurrent update coordination is limited to what the storage system’s compare-and-swap can provide.

No source attests this combination.

#3 Seed of approach C weak

Thought A single serialized repository server should make reference ordering simple, while nearby caches and on-demand object access should reduce transfer for engineers.

Move
  • Source of truth for repository state → Repository files on server disks
  • Replication for durability → Single copy on a file server
  • Reference update coordination → One server serializes the updates
  • Client data transfer → Virtualized filesystem with on-demand objects
  • Serving reads → Cache servers near the clients

Observed The local design point offers operational simplicity but directly contradicts the required single-machine/disk durability and operator-free failover. Drop this approach rather than layering caches over the same single origin.

R1 partlyR2 partlyQ1 missesQ2 missesQ3 partlyQ4 partlyC1 meetsC2 partly
  • Single copy on a file server, One server serializes the updates: gains C1, Q4 gives up Q1, Q2: A single serialized server simplifies operations and ordering, but its unreplicated disk loses the only copy on machine or disk failure and it is a failure point.

Each repository’s authoritative Git files reside on one file server, which serializes reference updates. Developers use a virtual filesystem that fetches objects on demand, while nearby cache servers serve reads and forward misses to the file-server origin.

The point's trade-off This provides simple centralized consistency, reduced client downloads, and geographically closer read service. It gives up durability against file-server loss, and the single server can bottleneck updates or uncached reads.

No source attests this combination.

#6 New approach D weak

Thought Test whether a distributed object store as authority can combine replicated durability and locality-aware reads while preserving a plain-Git client path.

The system stores Git objects and references in a distributed key-value store while maintaining three Git replicas for durability. Reference changes use three-phase commit with majority-write success; clients use partial clone with sparse checkout, and reads go to the nearest up-to-date replica.

The point's trade-off This provides durable, locality-aware reads and reduced client transfer, but adds coordination, replica-management, and quorum/freshness costs. The DHT source of truth conflicts with “plain Git replicas” as authoritative repository copies; they must instead be projections or caches of the DHT.
