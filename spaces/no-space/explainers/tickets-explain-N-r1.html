Support-ticket routing

A software company receives about 20,000 support tickets a day in English, Spanish and Portuguese, by e-mail and web form. Each ticket must reach one of 25 teams. First-line staff currently forward tickets by hand, and a misrouted ticket waits a day on average. Products and their support teams change a few times a year.

The solution

S · Ticket routing as built

A multilingual classifier routes webhook tickets, while a weekly correction-driven training pipeline updates the model and keyword rules cover new teams before training data exists. The service runs in the EU and gives agents prediction context and team-level monitoring.

Composed of 6 partial design points, one per ADR:

  • ADR1 · Weekly supervised retraining with an accuracy gate R2Q2 Learning → Weekly supervised retraining on 90 days of final team labelsModel acceptance → Replace only if last-week accuracy is at least current accuracyModel rollout → Store model file in object storage and load within five minutes
  • ADR2 · Team-lead keyword rules R1R2Q2 Cold start → Team-lead keyword rules until agent corrections create training data
  • ADR3 · Multilingual embeddings with logistic regression R1R2Q1Q2 Text representation → Fixed pretrained multilingual sentence embeddingsClassifier → Logistic regression with one class per team
  • ADR4 · Webhook to two EU Kubernetes replicas C1R1Q1 Ingress → Help desk webhookHosting → Managed Kubernetes in EU with two replicas and load balancer
  • ADR5 · Attach same-customer, same-subject tickets within one hour R1Q1 Duplicate handling → One-hour customer-and-subject deduplication
  • ADR6 · Show runner-ups and influential words, with moved-share monitoring R1R2Q2 Agent explanation → Two runner-up teams and influential wordsMonitoring → Per-team moved-ticket share dashboard and alert when share doubles week over week

As a whole: Tickets arrive through the help-desk webhook, are deduplicated for one hour by customer and subject, embedded with a fixed multilingual model, and assigned by team using logistic regression. The service runs on two EU Kubernetes replicas, explains predictions with runner-up teams and influential words, retrains weekly from 90 days of labels, accepts models based on last-week accuracy, and loads approved files from object storage within five minutes; keyword rules cover cold start while dashboards monitor team-share shifts.

ADR1 · Learn routing from agent corrections R2Q2

Context. Agent moves must influence later routing, and new teams need to adapt after creation. The solution records final teams, retrains on a rolling 90-day set each week, gates replacement on last-week accuracy, then loads the accepted model within five minutes.

Decision. Weekly supervised retraining with an accuracy gate.

Weekly supervised retraining with an accuracy gate chosen

Learning → Weekly supervised retraining on 90 days of final team labelsModel acceptance → Replace only if last-week accuracy is at least current accuracyModel rollout → Store model file in object storage and load within five minutes

“Every Sunday a scheduled job exports the tickets of the last 90 days with their final teams, retrains the classifier (the embedding model is never retrained)”
“If it is at least as accurate as the current model, the job replaces the model file in object storage”
“the service loads the new file within five minutes.”
  • Uses corrected final team labels as supervised training data.
  • Checks candidate accuracy before replacing the deployed model.
  • Makes an accepted update available within five minutes.
  • A correction may wait for the next weekly run to influence the model.
  • Last-week accuracy does not establish the new-team two-week target.

Chosen because it directly learns from agent moves and supports periodic adaptation. R2 requires learning from moves, but does not force weekly batch training, this window, this gate or this storage choice.

Online learning after each correction discarded

Learning cadence → Update the classifier online after every agent correction

  • Can incorporate a correction before the next weekly cycle.
  • A mistaken correction can influence subsequent routing before review.

This also supports learning from moves and could react faster, so the requirements do not force the selected cadence; it was not chosen in the solution.

ADR2 · Provide a route for a new team before it has examples R1R2Q2

Context. A new team initially has no training examples. Tickets still need a team assignment, and later agent moves can create labels for learning; Q2 sets a two-week routing target.

Decision. Team-lead keyword rules.

Team-lead keyword rules chosen

Cold start → Team-lead keyword rules until agent corrections create training data

“A new team has no training data until agents move tickets to it. Until then, keyword rules written by the team's lead route its tickets.”
  • Provides an initial route without team-specific training data.
  • Can be written by the team lead with product knowledge.
  • Accuracy depends on rule coverage and maintenance.
  • No evidence establishes the 80% target within two weeks.

Chosen as an immediate fallback while corrections accumulate. It supports the requirements plausibly, but the problem does not force keyword rules or prove the target.

ADR3 · Represent ticket text and select a team R1R2Q1Q2

Context. Incoming tickets are in English, Spanish and Portuguese and must be assigned to one of 25 teams. A learned classifier can incorporate agent corrections; the latency and new-team targets require operational evidence not included in the solution description.

Decision. Multilingual embeddings with logistic regression.

Multilingual embeddings with logistic regression chosen

Text representation → Fixed pretrained multilingual sentence embeddingsClassifier → Logistic regression with one class per team

“Otherwise the service turns the subject and the body into an embedding with a pretrained multilingual sentence-embedding model”
“and a logistic-regression classifier with one class per team picks the team.”
  • Uses a representation intended for the stated languages.
  • Provides one direct class for each support team.
  • Keeps the classifier simple to retrain.
  • Fixed embeddings are not adapted to company-specific language.
  • A new team has no learned examples, and no benchmark demonstrates the time target.

Chosen as the solution's trainable multilingual classification path. R2 supports having a learning mechanism, but neither the embedding model nor logistic regression is forced.

Keyword rules only discarded

Classifier → Keyword rules only, with no learned text model

  • Rules are transparent and directly maintainable.
  • Does not learn a classifier from agent moves.
  • Unmatched wording needs a separate fallback.

The contrast loses the support for R2. This supports a learned mechanism, but leaves the specific model family open.

ADR4 · Keep routing and ticket processing in the EU C1R1Q1

Context. Ticket data can include personal information and must remain in the company's EU cloud region. The webhook starts routing, and the service needs to handle arrivals at the stated peak, although no performance result is supplied.

Decision. Webhook to two EU Kubernetes replicas.

Webhook to two EU Kubernetes replicas chosen

Ingress → Help desk webhookHosting → Managed Kubernetes in EU with two replicas and load balancer

“The help desk tool sends every new ticket to the routing service through a webhook.”
“The service runs on a managed Kubernetes cluster in the company's EU cloud region, with two replicas behind a load balancer.”
  • The hosting location supports the EU data constraint.
  • The webhook connects ticket arrival to routing.
  • Replicas and a load balancer provide basic distribution and redundancy.
  • The solution does not state peak-load measurements against ten seconds.
  • The particular platform and replica count add operational choices beyond the residency constraint.

EU-local hosting is forced by C1; the webhook, Kubernetes and replica arrangement are not forced by the requirements.

ADR5 · Avoid classifying likely duplicate tickets R1Q1

Context. Reducing repeated classification could help processing load, but each ticket still needs an appropriate team and the solution gives no evidence about duplicate frequency or latency benefit.

Decision. Attach same-customer, same-subject tickets within one hour.

Attach same-customer, same-subject tickets within one hour chosen

Duplicate handling → One-hour customer-and-subject deduplication

“It first looks for duplicates: if the same customer sent a ticket with the same subject in the last hour, the service attaches the new ticket to the earlier one and does not classify it.”
  • Avoids repeated classification for likely duplicates.
  • Can attach a distinct issue to the earlier ticket's team.
  • No measured latency benefit is given.

This is a discretionary optimization; no stated requirement forces its matching rule or one-hour window.

ADR6 · Give agents routing context and surface shifts R1R2Q2

Context. Agents can move tickets when assignments are wrong, and their moves are the source of learning. Prediction context and team-level move monitoring may help agents review assignments, but no requirement prescribes these interfaces or alerts.

Decision. Show runner-ups and influential words, with moved-share monitoring.

Show runner-ups and influential words, with moved-share monitoring chosen

Agent explanation → Two runner-up teams and influential wordsMonitoring → Per-team moved-ticket share dashboard and alert when share doubles week over week

“The service writes the team back to the help desk tool, with the two runner-up teams and the words that weighed most in the decision, which the tool shows to agents next to the ticket.”
“A dashboard shows, per team, the share of tickets that agents moved, and sends an alert when that share doubles from one week to the next.”
  • Gives agents context near the ticket when reviewing a predicted team.
  • Makes changes in per-team move rates visible.
  • A doubling alert is not a direct measure of classification accuracy.
  • The interface and threshold do not themselves ensure new-team performance.

These are useful operational choices around review and monitoring, but they are not forced by the stated requirements.

#2 A region of #1: part of the solution grounded

Thought R2 calls for learning from agent moves, and Q2 calls for the learned routing to adapt when a new product team appears; the batch, acceptance and rollout choices should support those needs.

Move
  • Learning → Weekly supervised retraining on 90 days of final team labels
  • Model acceptance → Replace only if last-week accuracy is at least current accuracy
  • Model rollout → Store model file in object storage and load within five minutes

Observed This is the clearest mechanism for learning from recorded moves: the final team is the supervised label. Weekly retraining and rapid file loading describe a plausible update cycle, but neither the sample count for a new team nor its resulting routing accuracy is given, so the 80% target is not established.

R2 meetsQ2 partly
  • Weekly supervised retraining on 90 days of final team labels, Replace only if last-week accuracy is at least current accuracy: gains R2 gives up Q2: Training on final teams uses agent corrections, while the weekly schedule and accuracy gate can defer when a newly created team's examples influence the deployed model.

Weekly, the system retrains a model using the prior 90 days of final team labels. It replaces the current model only when the candidate’s last-week accuracy is at least as high, then stores the accepted model in object storage for loading within five minutes.

The point's trade-off This provides regular adaptation, a simple performance gate, and relatively quick deployment, but it cannot incorporate new labels between weekly retraining cycles and may favor models that perform well on last week’s data while overlooking other periods or conditions.

The point's trade-off This provides rapid learning from current agent feedback, but gives up the stability of batched or validated updates. A mistaken correction can therefore affect later routing before it is reviewed.

#5 A region of #1: part of the solution grounded

Thought R1 calls for assigning tickets across the stated languages, while Q1 calls for a routing path that can operate within the short response target; the multilingual representation and simple classifier should support these requirements.

Move

  • Classifier → Logistic regression with one class per team

Observed The embeddings fit the English, Spanish and Portuguese input, and logistic regression gives a direct team-selection mechanism. These choices do not provide a latency benchmark, and the classifier alone cannot learn a new team's decision boundary without examples. No requirement singles out this specific embedding model or classifier over other trainable multilingual approaches.

R1 meetsQ1 partlyQ2 partly

Each support ticket is converted into a fixed pretrained multilingual sentence embedding. Logistic regression then uses those features to predict the ticket’s team, selecting the class with the highest score for routing.

The point's trade-off This provides a simple, efficient classifier that can reuse multilingual semantic representations across teams and languages. It gives up task-specific adaptation and nonlinear decision boundaries, so domain-specific wording or subtle distinctions between teams may be missed.

Observed The stated deployment puts the service in the company's EU cloud region, directly supporting the residency constraint. Two replicas and a load balancer add availability and request distribution, but C1 does not force Kubernetes, two replicas or a load balancer specifically.

The support-ticket routing service would run on a managed Kubernetes cluster hosted in the EU. Two application replicas would sit behind a load balancer, distributing incoming requests and allowing traffic to continue if one replica is unavailable.

The point's trade-off This gains managed orchestration, EU-based hosting, and basic redundancy and traffic distribution. It gives up some capacity and may increase cost and operational complexity compared with a single instance, while two replicas do not provide broad fault tolerance.

#8 A region of #1: part of the solution partial

Thought R1 and Q1 might support avoiding duplicate classification work, although no requirement explicitly asks for deduplication.

Move
  • Duplicate handling → One-hour customer-and-subject deduplication

Observed Deduplication can reduce repeated work, but the solution gives no latency evidence and identical customer and subject do not prove that two requests have the same intent. This is a discretionary optimization with a risk to independent ticket assignment.

R1 partlyQ1 partly
  • One-hour customer-and-subject deduplication: gains Q1 gives up R1: Skipping classification can reduce processing work, but treating a same-subject ticket as a duplicate can attach a genuinely separate issue to the earlier ticket's team.

The system would compare each incoming ticket with tickets from the same customer received within the previous hour. If the subjects match, it would classify the incoming ticket as a duplicate and handle it together with the existing ticket rather than as an independent case.

The point's trade-off This reduces repeated work and routing noise, but risks suppressing genuinely separate issues that share a subject and occur within the one-hour window.
