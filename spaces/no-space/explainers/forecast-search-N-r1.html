Retail demand forecasting

A retailer forecasts weekly demand per store and product: 400 stores and 30,000 products. Every Monday the forecasts for the next eight weeks feed the replenishment system, which orders stock. Sales from the tills reach the company's data warehouse every night; promotions and public holidays move demand strongly. A team of three data scientists owns the forecasting pipeline end to end. The data warehouse is run by the central IT department, which the team cannot change.

ADR1 · Where should weekly forecasting compute run? R1C1C2Q4

Context. The pipeline must score 12 million store-product series after the nightly load and finish inside six hours. Three data scientists must operate it, and the centrally run warehouse cannot be changed. A single VM is approachable but has limited throughput headroom; distributed managed compute offers capacity with more platform surface to learn.

Decision. Managed distributed batch (A1, B1, D1).

Managed distributed batch chosen in A1, B1, D1

Compute → Managed distributed batch

  • Can spread large training and scoring jobs across workers.
  • Keeps warehouse ownership and configuration unchanged.
  • Adds orchestration and onboarding work for a small team.
  • Six-hour runtime and local setup still require validation.

All retained alternatives use this execution path because it has the most capacity headroom for the deadline while leaving warehouse operations alone.

Single managed VM discarded

Compute → Single managed VM batch

  • A compact environment is easier to understand and run.
  • Fewer execution components may help first-week onboarding.
  • A single host is a throughput bottleneck for 12 million series.
  • Provides little headroom for the six-hour window.

The approach changed to distributed batch after the single-host throughput risk became clear.

Warehouse SQL with one VM discarded

Compute → Warehouse SQL plus single VM

  • Uses familiar warehouse queries and simple scripts.
  • Leaves per-series computation on one host and mutable warehouse data undermines replay.

This approach missed the scale and replay requirements.

ADR2 · How should forecasts share information across series? R1R3Q2Q4

Context. Promotions and holidays strongly affect demand across stores and products, while series differ locally. The model must cover a very large series count, permit historical comparisons, and remain practical for a small team to maintain. A single pooled model is simpler to operate; segmentation and local corrections can represent differences but add model management.

Decision. Pooled global model with known demand drivers (A1); Segmented product and store group models (B1); Global model with category and store residual adjustments (D1).

Pooled global model with known demand drivers chosen in A1

Model → Global pooled model with promotion and holiday features

  • Shares information across many series.
  • Uses promotion and holiday signals directly.
  • Keeps one principal model path for backtesting and maintenance.
  • May miss local category or store residual patterns.

This is the simpler scalable modeling choice where promotion and holiday effects are explicit.

Segmented product and store group models chosen in B1

Model → Segmented models by product and store groups

  • Allows distinct group behavior and comparisons.
  • Increases model inventory and operational maintenance.

This alternative favors local model fit and preserves direct model-to-model backtesting.

Global model with category and store residual adjustments chosen in D1

Model → Global model with category and store residual adjustments

  • Shares broad patterns while adding local correction capacity.
  • Residual stages add complexity and may increase run time.

This balances global learning with category/store-specific adjustment, subject to scale and maintenance validation.

Independent model for each series discarded

Model → Independent per-series models

  • Allows every series its own model behavior.
  • Creates a large model inventory and high compute burden.

The single-host form did not fit the scale or six-hour deadline.

ADR3 · How should historical inputs and run artifacts be retained? R2Q1

Context. The team must rerun any forecast from up to two years ago and reproduce the same numbers within one working day. Current warehouse data can change after the original run. Retaining frozen input snapshots and code/model artifacts costs storage and requires lifecycle management, while requerying current data cannot guarantee the original run's inputs.

Decision. Freeze all run artifacts (A1); Retain raw extracts and pinned code (B1); Keep versioned input snapshots in object storage (D1).

Freeze all run artifacts chosen in A1

History → Immutable input, feature, code, and model snapshots

  • Captures data, transformations, code, and model needed for exact replay.
  • Requires storage retention and artifact management.

This most directly supports exact replay of the same output.

Retain raw extracts and pinned code chosen in B1

History → Immutable raw extracts and pinned code snapshots

  • Preserves source values and transformation version for reruns.
  • Feature and model artifact handling needs explicit implementation.

This lightweight artifact set covers repeatable input and code for the segmented approach.

Keep versioned input snapshots in object storage chosen in D1

History → Versioned input snapshots in object storage

  • Provides a durable historical data source outside the warehouse.
  • Code, feature, and model versions must also be associated with each run.

This gives the hybrid approach a durable replay input while keeping warehouse changes out of scope.

Requery current warehouse data discarded

History → Requery current warehouse data

  • Avoids a separate input snapshot store.
  • Later warehouse changes can change historical outputs.

This fails the exact replay requirement.

ADR4 · How should a run reach replenishment and how should models be promoted? R1R3Q2Q3

Context. The handoff must finish by Monday 06:00 and must never expose a partial forecast. New models must be compared on past weeks and move to production within a week after approval. Staging and an atomic promotion protect downstream consumers; automated backtests reduce manual work, but a robust release pipeline requires setup.

Decision. Manifested atomic output with approval-gated automation (A1, D1); Manifested atomic output with manually released experiments (B1).

Manifested atomic output with approval-gated automation chosen in A1, D1

Delivery → Stage complete output with run manifest and atomic publishExperiment → Automated backtests with approval-gated model promotion

  • Publishes only complete outputs and ties each run to its inputs.
  • Automates historical comparison and limits manual promotion to approval.
  • Requires orchestration and an explicit approval workflow.

This best combines safe delivery and the requested one-week promotion path.

Manifested atomic output with manually released experiments chosen in B1

Delivery → Stage complete output with run manifest and atomic publishExperiment → Automated backtests with manual packaging and deployment

  • Protects replenishment from partial runs and provides traceability.
  • Automated backtests reduce repetitive comparison work.
  • Manual packaging and deployment can extend the release cycle.

This retains safe delivery while trading some development velocity for hands-on control.

Atomic output with manual backtests and releases discarded

Delivery → Stage complete output and atomically publishExperiment → Versioned backtests with manual packaging and deployment

  • Stages complete forecasts and supports versioned comparisons.
  • Manual packaging and deployment slow promotion and there is no run manifest.

Later refinements added automated promotion and manifest provenance.

Direct writes with manual scripts discarded

Delivery → Write forecasts directly to replenishment tablesExperiment → Manual scripts and backtests

  • Uses a direct path to the downstream table.
  • A failed run may leave partial forecasts visible and release work remains manual.

This is unsafe for replenishment and misses the development velocity target.

#1 Seed of approach A strong

Thought Managed parallel batch scoring should make R1 and C2 plausible at this scale; immutable snapshots should serve R2 and Q1; atomic publication should serve Q3. Manual packaging may slow Q2, and the workload and platform still need to be easy for this team to operate (C1, Q4).

A managed distributed batch process trains one global model across retail series using promotion and holiday features.
