Search · design rationale · no design space

Large-scale document classification

An insurer receives between two and eight million documents a day (scanned forms, e-mails, PDFs) and classifies each one into one of 60 claim types with an LLM-based classifier. Volume varies strongly over the year: storm season brings four times the usual load. Three teams use the results: claims handling, fraud investigation and analytics. The documents contain personal data.

How to read this page

A coding agent searched for designs that solve this problem. It combined decisions (dimensions) and their options (values) into design points, and judged each point against every requirement: meets, partly or misses. It proposes 4 alternatives. Every judgement here is the agent's; the page lays out its rationale file.

  • Decisions (ADRs) lists the alternatives, then one record per decision: the requirements that drive it, and every option weighed, with its pros and cons, chosen by an alternative or discarded.
  • Comparison puts the alternatives side by side, with the rows where they differ first.
  • Trajectory shows how the agent got there:
    • the lanes show each approach round by round, with every point coloured strong, mixed or weak;
    • a strip shows how each point met each requirement;
    • the story gives each point's thought, change, observation and trade-offs.

No design space was used. The agent named the decisions and options itself, so nothing was checked against a space and there are no gaps in one.

Alternatives

A1 · Single-call event pipeline

Use one approved EU LLM call for each document, durable autoscaling queues, versioned event delivery, and a daily correction review. This is the simpler baseline with a clear path to consumer independence.

Composed of 5 partial design points, one per ADR:

  • ADR1 · One approved LLM call R1Q1Q3C2 Inference → One approved EU LLM call per document
  • ADR2 · Autoscaling asynchronous workers Q1Q3 Scheduling → Durable asynchronous queue with autoscaling workers
  • ADR3 · Shared versioned event stream R2Q4C1 Delivery → Publish versioned results to shared event stream
  • ADR4 · Daily prompt and model release review R3Q2Q3 Human feedback → Confidence threshold routes uncertain cases to reviewers; corrections feed daily prompt and model release review
  • ADR5 · Daily per-type alerting Q2R3 Monitoring → Alerting per-claim-type quality dashboard with daily detection objective

As a whole: Documents are placed on a durable asynchronous queue, where autoscaling workers make one approved EU LLM call per document. Versioned classifications are published to a shared event stream; low-confidence claims go to reviewers, whose corrections inform daily prompt and model-release reviews, while per-claim-type dashboards support daily detection objectives.

B1 · Cost-aware LLM cascade

Try a low-cost approved EU LLM first and escalate uncertain cases to a stronger approved LLM. Track per-type quality and fallback rates so the cost and quality assumptions can be measured.

Composed of 5 partial design points, one per ADR:

  • ADR1 · Two-tier approved LLM cascade R1Q1Q3C2 Inference → Two-tier approved EU LLM cascade, low-cost model first and stronger fallback
  • ADR2 · Autoscaling asynchronous workers Q1Q3 Scheduling → Durable asynchronous queue with autoscaling workers
  • ADR3 · Shared versioned event stream R2Q4C1 Delivery → Publish versioned results to shared event stream
  • ADR4 · Periodic correction training R3Q2Q3 Human feedback → Confidence threshold routes uncertain cases to reviewers; corrections feed periodic training
  • ADR5 · Quality and fallback-rate alerts Q2R3 Monitoring → Near-real-time per-claim-type quality alerts and fallback-rate dashboard

As a whole: The system queues documents for autoscaling workers, which try the low-cost approved EU LLM first and send failures or difficult cases to the stronger fallback. It publishes versioned results to a shared event stream, routes low-confidence claims to reviewers, uses corrections in periodic training, and monitors claim-type quality and fallback rates.

C1 · Deadline-managed provider batches

Use the approved provider's EU batch inference with storm-season capacity reservations and deadline-prioritized microbatches. Deliver versioned results through an event stream and review corrections daily.

Composed of 5 partial design points, one per ADR:

  • ADR1 · Provider batch inference R1Q1Q3C2 Inference → Approved EU LLM provider batch inference
  • ADR2 · Deadline-aware reserved microbatches Q1Q3 Scheduling → Deadline-prioritized microbatches with reserved storm-season capacity
  • ADR3 · Shared versioned event stream R2Q4C1 Delivery → Publish versioned results to shared event stream
  • ADR4 · Sampled and uncertain review with daily release review R3Q2Q3 Human feedback → Sampled and uncertain cases go to reviewers; corrections feed daily prompt and model release review
  • ADR5 · Daily per-type alerting Q2R3 Monitoring → Alerting per-claim-type quality dashboard with daily detection objective

As a whole: Approved EU LLM batch inference processes documents in deadline-prioritized microbatches, using reserved storm-season capacity, and publishes versioned results to a shared event stream. The system routes sampled or uncertain cases to reviewers, incorporates corrections into daily prompt and model-release reviews, and tracks per-claim-type quality against a daily detection objective.

E1 · Claim-type specialist pipelines

Route documents to approved EU LLM specialist prompts, each with its own durable autoscaling queue and versioned result topic. Feed reviewer corrections into the relevant prompt and monitor each type closely.

Composed of 5 partial design points, one per ADR:

  • ADR1 · Claim-type specialist prompts R1Q1Q3C2 Inference → Approved EU LLM specialist prompt selected by claim-type router
  • ADR2 · Independent per-type queues Q1Q3 Scheduling → Independent durable queue and autoscaling workers per claim type
  • ADR3 · Per-type topics with shared contracts R2Q4C1 Delivery → Versioned per-type result topics with shared event contracts
  • ADR4 · Update specialist prompts from corrections R3Q2Q3 Human feedback → Confidence threshold routes uncertain cases to reviewers; corrections update versioned specialist prompts
  • ADR5 · Quality alerts with correction tracking Q2R3 Monitoring → Near-real-time per-claim-type quality alerts and reviewer-correction tracking

As a whole: The router selects an approved EU LLM specialist prompt for each claim type and sends work to that type’s durable queue, whose workers autoscale independently. Results are published to versioned per-type topics under shared contracts; low-confidence cases go to reviewers, whose corrections update versioned prompts while monitoring alerts on quality and tracks corrections.

ADR1 · Choose the classification inference path R1Q1Q3C2

Context. Every document needs a confident claim type from the approved provider's EU LLM. Peak throughput and average cost are strict targets, but provider capacity, token pricing, and fallback rates are not provided, so all numeric claims need measurement.

Decision. One approved LLM call (A1); Two-tier approved LLM cascade (B1); Provider batch inference (C1); Claim-type specialist prompts (E1).

One approved LLM call chosen in A1

Inference → One approved EU LLM call per document

  • Simple per-document path
  • Uses the approved EU LLM
  • Provider throughput and price determine whether Q1 and Q3 hold

A1 favors operational simplicity and direct compliance.

Two-tier approved LLM cascade chosen in B1

Inference → Two-tier approved EU LLM cascade, low-cost model first and stronger fallback

  • Keeps all inference on approved LLMs
  • Potentially lowers average cost for easy documents
  • Fallback frequency affects cost and latency

B1 explicitly trades cascade complexity for cost control and measures fallback rate.

Provider batch inference chosen in C1

Inference → Approved EU LLM provider batch inference

  • Fits high-volume workloads and approved EU provider use
  • Batch service limits and completion latency need testing

C1 pairs the provider's batch path with explicit storm capacity planning.

Claim-type specialist prompts chosen in E1

Inference → Approved EU LLM specialist prompt selected by claim-type router

  • Tailors classification to each claim type and layout
  • Many prompts require versioning and quality governance

E1 ties specialization to the 60 claim types and layout-change scenario.

Parallel consensus calls discarded

Inference → Parallel multi-call LLM consensus per document

  • Multiple opinions can increase confidence
  • Multiplies inference cost and response work

The approach conflicts with both the peak deadline and average cost target.

ADR2 · Schedule work through peak volume Q1Q3

Context. Storm season multiplies volume, and each document has a two-hour classification deadline. Buffering and capacity controls help, while queues, reservations, and provider limits affect cost and latency.

Decision. Autoscaling asynchronous workers (A1, B1); Deadline-aware reserved microbatches (C1); Independent per-type queues (E1).

Autoscaling asynchronous workers chosen in A1, B1

Scheduling → Durable asynchronous queue with autoscaling workers

  • Buffers bursts and scales worker count
  • Autoscaling cannot exceed provider capacity

A1 and B1 use the shared queue as a flexible processing baseline.

Deadline-aware reserved microbatches chosen in C1

Scheduling → Deadline-prioritized microbatches with reserved storm-season capacity

  • Makes storm capacity and deadline priority explicit
  • Capacity reservations may raise annual cost

C1 prioritizes the two-hour storm requirement and will validate reservation economics.

Independent per-type queues chosen in E1

Scheduling → Independent durable queue and autoscaling workers per claim type

  • Isolates backlogs and scales claim types separately
  • Adds fleet and queue management overhead

E1 favors isolation and targeted capacity for claim-type variation.

Synchronous fan-out discarded

Scheduling → Synchronous request fan-out to inference calls

  • Returns a result in the request path when calls finish
  • Adds latency and lacks durable burst buffering

Waiting on multiple calls conflicts with peak throughput and cost.

ADR3 · Decouple delivery to consuming teams R2Q4C1

Context. Claims handling, fraud investigation, and analytics need the results, and each team should be able to change its processing independently. Personal data must stay in the EU throughout storage and delivery.

Decision. Shared versioned event stream (A1, B1, C1); Per-type topics with shared contracts (E1).

Shared versioned event stream chosen in A1, B1, C1

Delivery → Publish versioned results to shared event stream

  • Supports independent subscriptions and versioned result contracts
  • Requires EU-region stream controls and consumer operations

The event stream offers one stable publication path to all teams.

Governed versioned object storage discarded

Delivery → Write versioned results to governed object storage for team consumption

  • Provides durable governed result snapshots
  • Teams may need polling or separate change notifications

It is viable but less direct for independently changing consumers than event delivery.

Per-type topics with shared contracts chosen in E1

Delivery → Versioned per-type result topics with shared event contracts

  • Combines type-specific streams with common consumer contracts
  • Creates more topics and access policies to govern in the EU

E1 uses shared contracts to keep per-type publishing from coupling consumers.

ADR4 · Turn review corrections into model improvement R3Q2Q3

Context. Uncertain classifications must receive human review, and corrections must improve the classifier. The feedback path should support per-type quality diagnosis while keeping review and release costs sustainable.

Decision. Periodic correction training (B1); Daily prompt and model release review (A1); Update specialist prompts from corrections (E1); Sampled and uncertain review with daily release review (C1).

Periodic correction training chosen in B1

Human feedback → Confidence threshold routes uncertain cases to reviewers; corrections feed periodic training

  • Collects corrections for a repeatable training cycle
  • Improvements wait for the next periodic cycle

B1 favors a controlled periodic loop while focusing its primary refinement on cost monitoring.

Daily prompt and model release review chosen in A1

Human feedback → Confidence threshold routes uncertain cases to reviewers; corrections feed daily prompt and model release review

  • Creates a daily, governed path from corrections to improvement
  • Requires reviewer and release-management capacity

A1 and C1 use daily release review to shorten the feedback cycle.

Update specialist prompts from corrections chosen in E1

Human feedback → Confidence threshold routes uncertain cases to reviewers; corrections update versioned specialist prompts

  • Directs each correction toward the affected claim type
  • Requires prompt review and version management across types

E1 aligns correction ownership with claim-type specialization.

Review all disagreements discarded

Human feedback → All disagreements and low-confidence cases go to reviewers

  • Captures more possible errors for review
  • Can overwhelm human review capacity

Consensus-driven review volume is costly and was not tied to a sustainable feedback cadence.

Sampled and uncertain review with daily release review chosen in C1

Human feedback → Sampled and uncertain cases go to reviewers; corrections feed daily prompt and model release review

  • Samples model behavior while prioritizing uncertain documents for review
  • Creates a daily governed correction path
  • Sampling and release review require reviewer and operations capacity

C1 combines broad sampling with targeted uncertainty review to improve confidence in the batch classifier.

ADR5 · Detect claim-type quality regressions Q2R3

Context. A layout change can degrade one type while aggregate quality remains stable. Operators need a signal within one day, with enough detail to connect the regression to reviewer corrections and model changes.

Decision. Daily per-type alerting (A1, C1); Quality and fallback-rate alerts (B1); Quality alerts with correction tracking (E1).

Daily per-type alerting chosen in A1, C1

Monitoring → Alerting per-claim-type quality dashboard with daily detection objective

  • Directly measures the one-day detection goal by claim type
  • Detection depends on labeled outcomes and sufficient sample volume

A1 and C1 target the stated observability window.

Quality and fallback-rate alerts chosen in B1

Monitoring → Near-real-time per-claim-type quality alerts and fallback-rate dashboard

  • Adds faster type-level signals and a cost-relevant fallback metric
  • More metrics and alerts require tuning

B1 makes cascade economics and quality shifts visible together.

Quality alerts with correction tracking chosen in E1

Monitoring → Near-real-time per-claim-type quality alerts and reviewer-correction tracking

  • Links quality shifts to correction patterns by type
  • Requires consistent reviewer labels and many monitored streams

E1 uses the specialist structure to make regressions actionable.

Aggregate quality only discarded

Monitoring → Aggregate quality dashboard across all claim types

  • Simple overall health view
  • Can conceal a decline limited to one type

Aggregate-only quality does not adequately expose the example per-type regression.
