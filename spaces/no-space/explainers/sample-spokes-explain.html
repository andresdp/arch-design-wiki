Git hosting for a fast-growing engineering organization

A company hosts Git for 3,000 engineers in four regions and about 40,000 CI jobs a day. Its largest repository has 15 years of history and is about 200 GB. Five engineers build and operate the service in the company's cloud account.

The solution

S · Replicated Git file servers

Plain Git repositories on rack-separated file servers coordinate writes by majority and serve reads from current nearby replicas. Standard clients use full clones, leaving the large-repository requirement unmet.

Composed of 4 partial design points, one per ADR:

  • ADR1 · Three replicas in separate racks Q1 Replica placement → Three replicas in different racksRepository authority → Plain Git repositories on local disks, with no separate content database
  • ADR2 · Three-phase majority commit with background repair Q1Q2Q4 Write coordination → Three-phase commit with majority voteReplica repair → Checksum detection, background repair, and re-replication
  • ADR3 · Closest current replica with remote read copies Q2Q3Q4C1 Read routing → Closest up-to-date replica, with remote non-voting read replicasReplica repair → Checksum detection, background repair, and re-replication
  • ADR4 · Standard clients with full clones R1C1C2 Client and clone mode → Standard Git clients with full clonesPackfile maintenance → Periodic repacking on every replica

As a whole: 1. Three rack-separated Git repositories coordinate updates through three-phase majority commit, while checksums detect corruption and background repair re-replicates damaged data. Reads use the closest up-to-date replica; remote non-voting replicas serve additional reads, standard clients make full clones, and every replica is periodically repacked. 2.

ADR1 · Keep three rack-separated authoritative copies Q1

Context. A pushed commit must survive loss of any one machine or disk, so independent copies must remain available after a single failure.

Decision. Three replicas in separate racks.

Three replicas in separate racks chosen

Replica placement → Three replicas in different racksRepository authority → Plain Git repositories on local disks, with no separate content database

“Every repository is stored as a plain Git repository on the local disks of three file servers, placed in different racks.”
“The three replicas are the authoritative copies; there is no separate database of repository contents.”
  • A single machine or disk loss leaves two copies.
  • Separate racks reduce exposure to one rack failure.
  • Three copies consume more storage and replication bandwidth than two.

This meets the single-loss durability requirement. The third copy is a free margin choice because two rack-separated copies also survive one machine or disk loss.

Two replicas in separate racks discarded

Replica placement → Two replicas in different racksRepository authority → Plain Git repositories on local disks, with no separate content database

  • A surviving copy remains after one machine or disk loss.
  • Uses less storage and replication bandwidth.
  • Leaves less redundancy after a failure.

It still meets the stated single-loss case, so the solution does not force three replicas; this option was not chosen.

ADR2 · Coordinate writes across replicas and repair missed updates Q1Q2Q4

Context. Successful pushes must be durable and visible to subsequent fetches, and the service should recover from a server failure without operator action.

Decision. Three-phase majority commit with background repair.

Three-phase majority commit with background repair chosen

Write coordination → Three-phase commit with majority voteReplica repair → Checksum detection, background repair, and re-replication

“A push updates references through a three-phase commit: a proxy sends the update to all three replicas, each takes a lock and votes, and the update commits once a majority has agreed.”
“Replicas that miss an update are detected by comparing checksums of their references and repaired in the background from a healthy replica.”
  • A majority coordinates committed updates.
  • Checksums detect and repair replicas that miss updates.
  • Multi-phase writes add latency.
  • No recovery-time bound establishes the one-minute availability target.

This supports durability and repair, but the requirements do not force this particular protocol and the solution supplies no timing proof for availability.

ADR3 · Route reads to current nearby replicas Q2Q3Q4C1

Context. Fetches after successful pushes must see the new state while CI jobs in every region need fast reads and service should continue after a server failure.

Decision. Closest current replica with remote read copies.

Closest current replica with remote read copies chosen

Read routing → Closest up-to-date replica, with remote non-voting read replicasReplica repair → Checksum detection, background repair, and re-replication

“Reads go to the closest replica that is up to date; in remote regions, extra non-voting replicas serve reads without slowing down writes.”
“Replicas that miss an update are detected by comparing checksums of their references and repaired in the background from a healthy replica.”
  • Freshness-aware routing supports read-after-push consistency.
  • Remote copies add regional read capacity.
  • Extra copies add storage and operational work.
  • No latency or failover measurements establish the numeric targets.

Freshness supports Q4 and remote copies plausibly help Q3. The exact targets remain unproven, and the contrast without remote copies shows they are not forced by the available evidence.

Closest current replica without remote read copies discarded

Read routing → Closest up-to-date replica, without remote non-voting read replicasReplica repair → Checksum detection, background repair, and re-replication

  • Retains routing to a current nearby copy.
  • Avoids the extra read-copy storage.
  • Provides less regional read capacity.

It continues to support freshness, while its effect on the 30-second target is unknown; remote copies remain a free choice on this evidence.

ADR4 · Use standard Git clients with complete clones R1C1C2

Context. The service must use the standard Git protocol and must not require a custom client. The problem also asks engineers to work on the largest repository without downloading all of it.

Decision. Standard clients with full clones.

Standard clients with full clones chosen

Client and clone mode → Standard Git clients with full clonesPackfile maintenance → Periodic repacking on every replica

“Engineers use standard Git clients and full clones.”
“The team relies on Git's own packfile format and runs periodic repacking on every replica.”
  • Preserves familiar standard Git client behavior.
  • Periodic repacking maintains Git packfiles.
  • A full clone downloads all repository data and misses R2.
  • Repacking every replica consumes storage I/O and operator capacity.

Standard clients are required, but full clones are not. This choice meets R1 and C2 while contradicting R2, so it is not justified by the requirements.

Standard clients with partial clones discarded

Client and clone mode → Standard Git clients with partial clonesPackfile maintenance → Periodic repacking on every replica

  • Can fetch selected objects initially while retaining standard Git clients.
  • Better matches work on the large repository without downloading all objects.
  • Requires compatible partial-clone behavior and object serving.

This contrast indicates a way to retain standard-client compatibility while addressing R2; the supplied solution does not choose it.

#2 A region of #1: part of the solution grounded

Thought Q1 should explain independent authoritative copies on separate machines and racks.

Move
  • Replica placement → Three replicas in different racks
  • Repository authority → Plain Git repositories on local disks, with no separate content database

Observed Three independent copies across racks leave copies available after one machine or disk is lost. The requirement only covers a single loss, so this supports Q1; it does not establish protection from correlated or multiple failures.

Q1 meets

Each repository is stored as a standard Git repository on local disks, with three copies placed in separate racks. The Git repositories themselves are authoritative, while the replicas provide alternate copies of that authority.

The point's trade-off Rack separation improves availability during a rack failure, and avoiding a separate content database simplifies the storage model. It requires maintaining replica consistency and incurs three-way storage and replication costs; repository content is also less convenient to query as centralized database records.

#3 A contrast on #2: one option changed grounded

Thought Test whether Q1 forces three copies rather than two rack-separated copies.

Move
  • change Replica placement: Three replicas in different racks → Two replicas in different racks

Observed Two independent copies also leave a surviving copy after any one machine or disk loss. Three copies add margin, but the stated single-loss requirement does not force the third copy; replica count is free relative to Q1.

Q1 meets

The system stores each repository as ordinary Git data on local disks and maintains a second replica in another rack. The Git repositories themselves are authoritative, with no separate content database.

The point's trade-off This gains rack-level failure tolerance and a simpler authority model, but gives up centralized metadata or transactional guarantees and makes replica synchronization and recovery part of the system.

#4 A region of #1: part of the solution partial

Thought Q1 and Q4 should explain acknowledged writes on a replica majority and repair of lagging or damaged replicas; Q2 should benefit from automatic repair.

Observed Majority agreement plus repair supports durable updates and convergence. The description does not define commit visibility or read behavior alone well enough to prove Q4, and it gives no recovery-time bound for Q2. The three-phase write path also adds latency, but no measured push target was supplied.

Q1 meetsQ2 partlyQ4 partly
  • Three-phase commit with majority vote, Checksum detection, background repair, and re-replication: gains Q1, Q4 gives up Q2: Majority coordination and repair improve durable, consistent replica state, while multi-phase commits and background re-replication do not specify that service recovers within one minute.

A write proceeds through three commit phases and is finalized when a majority of replicas votes to commit. Replicas verify checksums, while background processes repair detected corruption and re-replicate damaged or missing copies.

The point's trade-off This improves coordinated write durability and automatically restores replica health, but adds multi-phase write latency and majority-quorum dependence, while repair consumes background resources.

#5 A region of #1: part of the solution partial

Thought Q3 and Q4 should explain serving regional reads from the closest replica only when it has the latest successful push; Q2 may benefit from alternate replicas.

Move
  • Read routing → Closest up-to-date replica, with remote non-voting read replicas
  • Replica repair → Checksum detection, background repair, and re-replication

Observed Routing only to an up-to-date copy directly supports read-after-push consistency. Nearby read copies plausibly help regional latency and alternate service, but there are no measurements against 30 seconds p95 or one minute recovery. Up-to-date filtering may also leave a lagging regional replica temporarily ineligible; this is a trade-off, not proof of a target miss.

Q2 partlyQ3 partlyQ4 meetsC1 partly
  • Closest up-to-date replica, with remote non-voting read replicas: gains Q4 gives up C1: Remote non-voting replicas add nearby read capacity and improve the chance of serving current state, at the cost of storage, replication, and routing work for a small operations team.

The system routes each read to the geographically closest replica that is sufficiently up to date, while remote non-voting replicas serve additional read demand. Checksums detect corrupted data; background repair restores affected replicas and re-replication replaces replicas that cannot be repaired.

The point's trade-off This improves read latency, local availability, and storage durability, but requires extra replication bandwidth, storage, and operational complexity, while non-voting replicas do not participate in write or failover decisions.

The point's trade-off This preserves broad client compatibility, reduces initial clone transfer, and keeps replica storage organized. It adds recurring CPU and I/O work on every replica, and packs may remain less optimized between repacking runs.
