Large-scale document classification

An insurer receives between two and eight million documents a day (scanned forms, e-mails, PDFs) and classifies each one into one of 60 claim types with an LLM-based classifier. Volume varies strongly over the year: storm season brings four times the usual load. Three teams use the results: claims handling, fraud investigation and analytics. The documents contain personal data.

Alternatives

A1 · Confidence-gated queue

Use an EU compact model for confident cases and the approved EU LLM for uncertain cases, with queued priority processing, event-based team delivery, and a rapid correction loop.

Composed of 3 partial design points, one per ADR:

  • ADR1 · Confidence-gated cascade with queued priority workers R1Q1Q3C1C2 Inference routing → Confidence-gated cascade (EU compact model then approved LLM EU endpoint)Work orchestration → Autoscaled queue workers with backpressure and priority lanes
  • ADR2 · Versioned claim-type event topics R2Q4 Result delivery → Versioned claim-type event topics for each team
  • ADR3 · Confidence-threshold review and rapid versioned corrections R3Q2 Review and learning → Confidence-threshold review with versioned correction feedbackQuality monitoring → Per-claim-type drift alerts and outcome dashboards

As a whole: The system first routes documents to an EU compact model and escalates low-confidence cases to an approved EU-hosted LLM. Autoscaled, backpressured workers prioritize processing, publish versioned claim-type events to team-specific topics, and feed confidence-based reviews and corrections into monitoring and future learning.

B1 · Deadline-aware direct inference

Send every document to the approved EU LLM in elastic deadline-aware micro-batches, then publish versioned team events and use per-type review and monitoring.

Composed of 3 partial design points, one per ADR:

  • ADR1 · Direct approved-LLM deadline batches R1Q1Q3C1C2 Inference routing → Approved LLM EU endpoint for every documentWork orchestration → Elastic deadline-aware micro-batches
  • ADR2 · Versioned claim-type event topics R2Q4 Result delivery → Versioned claim-type event topics for each team
  • ADR3 · Confidence-threshold review and rapid versioned corrections R3Q2 Review and learning → Confidence-threshold review with versioned correction feedbackQuality monitoring → Per-claim-type drift alerts and outcome dashboards

As a whole: Documents are sent to an approved EU LLM endpoint, processed in elastic, deadline-aware micro-batches, and emitted as versioned claim-type events to each team’s topic. Low-confidence claims enter review, whose versioned corrections support learning, while per-claim-type drift alerts and outcome dashboards monitor quality over time.

D1 · Class-specific priority pipeline

Specialize compact-model and approved-LLM routing by claim type, prioritize work against deadlines, and target review and monitoring by type.

Composed of 3 partial design points, one per ADR:

  • ADR1 · Claim-specific cascade with priority backpressure R1Q1Q3C1C2 Inference routing → Class-specific cascade using compact EU model and approved LLM EU endpointWork orchestration → Autoscaled priority lanes with deadline backpressure
  • ADR2 · Versioned claim-type event topics R2Q4 Result delivery → Versioned claim-type event topics for each team
  • ADR3 · Targeted review and versioned corrections R3Q2 Review and learning → Targeted human review with versioned correction feedbackQuality monitoring → Per-claim-type drift alerts and outcome dashboards

As a whole: Documents are routed by claim class through a compact EU model and, where selected, an approved EU LLM endpoint, while autoscaled priority lanes use deadline backpressure to manage work. Results are published to versioned claim-type topics for team consumption; targeted human corrections support learning, while per-claim-type drift alerts and outcome dashboards monitor quality.

ADR1 · Route documents through EU inference capacity R1Q1Q3C1C2

Context. The classifier must return a claim type and confidence for every document while respecting EU residency and the approved provider. Seasonal peaks make elastic capacity important, and the average cost target favors controlling expensive inference. The problem supplies neither endpoint prices nor measured throughput, so cost and deadline claims remain candidates for benchmarking.

Decision. Confidence-gated cascade with queued priority workers (A1); Direct approved-LLM deadline batches (B1); Claim-specific cascade with priority backpressure (D1).

Confidence-gated cascade with queued priority workers chosen in A1

Inference routing → Confidence-gated cascade (EU compact model then approved LLM EU endpoint)Work orchestration → Autoscaled queue workers with backpressure and priority lanes

  • Uses the approved EU LLM for uncertain cases and can reserve its capacity for them.
  • Queue autoscaling and priority lanes support variable volume.
  • A second inference stage adds latency and confidence calibration work.
  • Measured throughput and average cost are still needed.

This balances reduced LLM volume with asynchronous burst handling while keeping the approved endpoint in the classification path.

Direct approved-LLM deadline batches chosen in B1

Inference routing → Approved LLM EU endpoint for every documentWork orchestration → Elastic deadline-aware micro-batches

  • Uses one direct approved-provider inference path.
  • Elastic micro-batches can schedule work against deadlines.
  • Every document incurs approved-endpoint inference, leaving the cost target unverified.
  • Endpoint capacity and response times need peak-load validation.

This favors a uniform classification path and deadline-based batch scheduling over cascade specialization.

Claim-specific cascade with priority backpressure chosen in D1

Inference routing → Class-specific cascade using compact EU model and approved LLM EU endpointWork orchestration → Autoscaled priority lanes with deadline backpressure

  • Routing and priority can reflect differences among claim types.
  • Backpressure helps expose overload before it silently accumulates.
  • Per-class routing policies require calibration and maintenance.
  • Additional routing can add latency; numerical cost and deadline targets need validation.

This makes classification and workload control class-aware, with the cost of more policy and operational complexity.

ADR2 · Deliver independent result feeds to consuming teams R2Q4

Context. Claims handling, fraud investigation and analytics all need results, and each team must be able to change its processing without coordinating changes with the classifier or other consumers. A shared polled database offers a central handoff but makes consumers share an interface and operational dependency.

Decision. Versioned claim-type event topics (A1, B1, D1).

Versioned claim-type event topics chosen in A1, B1, D1

Result delivery → Versioned claim-type event topics for each team

  • Each consumer has an independent feed and can evolve its processing separately.
  • Versioning makes result schema changes explicit.
  • Topic and schema lifecycle management adds operational work.

All three alternatives use independently consumed, versioned outputs to meet delivery and loose-coupling needs.

Shared relational polling discarded

Result delivery → Shared relational results database polled by teams

  • Provides one familiar, centralized place for results.
  • Consumers share the database contract and polling load, undermining independent change.

The shared interface conflicts with the loose-coupling requirement.

Durable lake with team exports discarded

Result delivery → Durable result lake with team-specific exports

  • Preserves a durable record and allows different team export formats.
  • Scheduled exports can delay delivery and require per-team handoff management.

This is a viable batch-oriented handoff but less direct and independently consumable than versioned team feeds.

ADR3 · Close the human correction and quality feedback loop R3Q2

Context. Uncertain documents need human review, corrections must improve the classifier, and operators must see when an individual claim type degrades within a day. Broad periodic sampling and aggregate metrics reduce review and monitoring effort but may delay or conceal category-specific problems.

Decision. Confidence-threshold review and rapid versioned corrections (A1, B1); Targeted review and versioned corrections (D1).

Confidence-threshold review and rapid versioned corrections chosen in A1, B1

Review and learning → Confidence-threshold review with versioned correction feedbackQuality monitoring → Per-claim-type drift alerts and outcome dashboards

  • Routes uncertain cases for review and makes correction inputs traceable.
  • Per-type alerts match the specified quality-drop scenario.
  • Review thresholds and alert signals need calibration and ongoing operation.

This combines case selection and traceable learning with day-level, category-specific visibility.

Targeted review and versioned corrections chosen in D1

Review and learning → Targeted human review with versioned correction feedbackQuality monitoring → Per-claim-type drift alerts and outcome dashboards

  • Focuses human work on the claim types and cases most in need of attention.
  • Versioned corrections and per-type alerts support investigation and improvement.
  • Targeting policy and correction-set maintenance require ownership.

This aligns review allocation and monitoring with the 60 claim-type taxonomy.

Sampled review with periodic updates discarded

Review and learning → Sampled human review with periodic model updatesQuality monitoring → Daily aggregate quality and volume reports

  • Bounds routine review effort and gives a regular summary of overall quality.
  • Aggregate daily reports can hide one claim type's quality drop, and periodic updates slow the correction loop.

It cannot reliably surface localized degradation and act on corrections at the required pace.

Round 1 · 3 points: seed A, seed B, seed C
#1 Seed of approach A strong

Thought A queue and confidence-gated cascade should scale the LLM workload, route uncertain cases for correction, and separate the three consumers. Per-type monitoring should expose category-specific drops. The two-hour and per-document cost targets remain partly dependent on unprovided throughput and pricing evidence.

Move
  • Inference routing → Confidence-gated cascade (EU compact model then approved LLM EU endpoint)
  • Work orchestration → Autoscaled queue workers with backpressure
  • Result delivery → Versioned claim-type event topics for each team
  • Review and learning → Confidence-threshold human review with correction feedback
  • Quality monitoring → Per-claim-type drift and outcome dashboards

Observed The queue and topic-based output cover the volume and team-boundary concerns structurally, and per-type dashboards address the required visibility. The actual two-hour throughput and 0.2-cent average cannot be verified without workload benchmarks, model behavior, and endpoint pricing.

  • Confidence-gated cascade (EU compact model then approved LLM EU endpoint): gains Q3 gives up Q1: Using a compact model for confident cases may lower LLM spend, while the extra routing stage can add latency to the two-hour path.

A queue-based pipeline uses autoscaled workers with backpressure to run an EU compact model first and route low-confidence cases to an approved EU LLM endpoint. It publishes versioned claim-type events for teams, while human corrections feed learning and dashboards track drift and outcomes by claim type.

The point's trade-off This gains scalable processing, controlled escalation, team-specific delivery, and measurable improvement. It gives up simplicity and some speed and cost efficiency because it requires cascade management, human review, versioned topics, and per-claim-type monitoring.

#2 Seed of approach B mixed

Thought Elastic batches and a durable store should absorb seasonal volume and distribute results, while sampled corrections improve the model. Aggregate reporting may not identify a claim-type drop within a day, and capacity and price targets need measurement.

Move

  • Work orchestration → Elastic scheduled micro-batches
  • Result delivery → Durable result lake with team-specific exports
  • Review and learning → Sampled human review with periodic model updates
  • Quality monitoring → Daily aggregate quality and volume reports

Observed Durable exports give each team a stable handoff, but daily aggregate reports lack the granularity required by the observability scenario. Scheduled batching supports scale in principle, though the two-hour deadline needs sizing evidence; full-volume approved-LLM pricing is also unknown.

Documents are queued into elastic scheduled micro-batches and sent to the approved EU LLM endpoint for inference. Results are stored durably, exported for individual teams, reviewed through sampling, and used for periodic model updates, with daily aggregate quality and volume reports.

The point's trade-off This provides centralized, durable outputs and controlled learning with consistent endpoint usage, but gives up immediate processing, fine-grained quality visibility, and rapid adaptation between review cycles.

#3 Seed of approach C weak

Thought A centralized synchronous service should be straightforward to operate, but serial request handling, shared polling, monthly review and global-only monitoring are likely to fail the burst, loose-coupling and quality-response requirements.

Move
  • Inference routing → Approved LLM EU endpoint for every document
  • Work orchestration → Synchronous per-document service calls
  • Result delivery → Shared relational results database polled by teams
  • Review and learning → Manual exception queue with monthly correction review
  • Quality monitoring → Global success-rate dashboard

Observed The approach violates the two-hour burst target by construction at this volume and its global dashboard cannot show a category-specific drop. Shared polling couples consumers, monthly correction review delays learning, and full-volume LLM spend has no cost control; this is the deliberately less promising centralized approach.
