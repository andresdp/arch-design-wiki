Card-fraud scoring service

A payments company scores every card transaction for fraud before authorization, processing 3,000 transactions per second normally and up to 15,000 during seasonal sales. Fraud patterns adapt within weeks; confirmed labels arrive days to weeks later. Auditors may ask months later why a transaction was scored as it was. Five data scientists and two ML engineers build the system; operations runs the data centres and shared infrastructure, with no ML platform team.

Alternatives

A1 · Stream store with cached fail-open

Scale stateless scoring over stream-maintained keyed features, with automated canaries, an immutable audit ledger and a circuit-breaker fallback.

Composed of 3 partial design points, one per ADR:

  • ADR1 · Stream-maintained online store R1Q1Q2C1C2 Serving → Stateless scoring tierFeature state → Stream-processed keyed online storeFailure handling → Local feature cache with circuit breaker and fail-open authorization fallback
  • ADR2 · Automated champion challenger canary R2Q4C2 Model rollout → Automated champion challenger with canary
  • ADR3 · Immutable score and training ledger R3Q3 Audit record → Append-only score ledger with immutable model and training snapshots

As a whole: The stateless scoring tier retrieves keyed, stream-maintained features from the online store and scores requests using the current champion or canary model. It records each score with immutable model and training snapshots, while a local feature cache and circuit breaker enable a fail-open authorization fallback during dependency failures.

B1 · Colocated stateful shards

Keep per-cardholder rolling state beside scoring shards, automate shadow comparison and activation, and use local last-known features when dependencies fail.

Composed of 3 partial design points, one per ADR:

  • ADR1 · Colocated partitioned state R1Q1Q2C1C2 Serving → Sharded scoring with colocated stateFeature state → Partitioned stream processor keyed by cardholderFailure handling → Local last-known features and fail-open authorization fallback
  • ADR2 · Automated shadow validation and atomic switch R2Q4C2 Model rollout → Automated shadow validation and atomic version switch
  • ADR3 · Immutable score and training ledger R3Q3 Audit record → Append-only score ledger with immutable model and training snapshots

As a whole: Shards host scoring and cardholder-keyed feature state together, allowing low-latency scoring from colocated stream-processed features. Automated shadow tests validate new models before an atomic switch, while an append-only ledger records scores alongside immutable model and training snapshots; if dependencies fail, scoring uses local last-known features and fail-open authorization.

C1 · Relational scoring with cache and replicas

Use transactional rolling aggregates and database history with read replicas, local cache, and a manual shadow release process.

Composed of 3 partial design points, one per ADR:

  • ADR1 · Relational aggregates with local cache R1Q1Q2C1C2 Serving → Synchronous scoring from shared relational database with read replicasFeature state → Transactional rolling aggregates with asynchronous local cacheFailure handling → Cached aggregates and fail-open authorization fallback
  • ADR2 · Manual shadow and scheduled switch R2Q4C2 Model rollout → Manual shadow evaluation then scheduled switch
  • ADR3 · Database score history and retained model artifacts R3Q3 Audit record → Database score history with retained model artifacts

As a whole: The service synchronously scores each transaction using rolling aggregates maintained transactionally and served through an asynchronous local cache, with relational read replicas supporting scoring. Scores are recorded with the model artifacts, while models undergo manual shadow evaluation before scheduled activation; if dependencies fail, cached aggregates support a fail-open authorization fallback.

D1 · Embedded shard-local scoring

Embed the model beside replicated rolling aggregates in each authorization shard, distribute signed model bundles, replay events for recovery, and retain score provenance.

Composed of 3 partial design points, one per ADR:

  • ADR1 · Embedded shard-local state R1Q1Q2C1C2 Serving → Embedded model in authorization serviceFeature state → Replicated in-memory rolling aggregates with event replayFailure handling → Cached aggregates with health-gated fail-open authorization fallback
  • ADR2 · Signed bundles staged per shard R2Q4C2 Model rollout → Signed model bundles staged to each shard
  • ADR3 · Immutable score and training ledger R3Q3 Audit record → Append-only score ledger with immutable model and training snapshots

As a whole: Each authorization shard runs the embedded model against replicated in-memory rolling aggregates, rebuilding them through event replay and using signed model bundles staged locally. It appends scores with immutable model and training snapshots, while health checks determine whether to use cached aggregates or fail open when scoring dependencies are unhealthy.

ADR1 · Where scoring and recent activity state run R1Q1Q2C1C2

Context. The service must use current cardholder activity before authorization at seasonal peak, remain available during component failure, and keep card data within the PCI environment. A local path reduces hops but increases state ownership; shared services reduce duplication but can add latency and failure concentration.

Decision. Stream-maintained online store (A1); Colocated partitioned state (B1); Relational aggregates with local cache (C1); Embedded shard-local state (D1).

Stream-maintained online store chosen in A1

Serving → Stateless scoring tierFeature state → Stream-processed keyed online storeFailure handling → Local feature cache with circuit breaker and fail-open authorization fallback

  • Separates scoring from keyed state and supports horizontal scaling.
  • Cache fallback keeps authorizations moving.
  • Online lookup adds a dependency and cache staleness can weaken detection.
  • Several services add operational work.

Choose when independent scaling and explicit online feature processing are priorities.

Colocated partitioned state chosen in B1

Serving → Sharded scoring with colocated stateFeature state → Partitioned stream processor keyed by cardholderFailure handling → Local last-known features and fail-open authorization fallback

  • Avoids a remote feature hop and maintains per-cardholder ordering.
  • Local state supports fail-open authorization.
  • Stateful shards need balancing and recovery operations.
  • Stale local state can degrade detection.

Choose when local latency and cardholder-level state locality justify shard ownership.

Relational aggregates with local cache chosen in C1

Serving → Synchronous scoring from shared relational database with read replicasFeature state → Transactional rolling aggregates with asynchronous local cacheFailure handling → Cached aggregates and fail-open authorization fallback

  • Central transactional operations are familiar to the existing infrastructure team.
  • Replicas and cache reduce contention.
  • Database dependence and replica lag still threaten peak latency and freshness.

Choose when minimizing distinct platform components outweighs peak-path latency concerns.

Embedded shard-local state chosen in D1

Serving → Embedded model in authorization serviceFeature state → Replicated in-memory rolling aggregates with event replayFailure handling → Cached aggregates with health-gated fail-open authorization fallback

  • Avoids network feature reads and keeps a local authorization fallback.
  • Replication and replay create state consistency work for a small team.

Choose when minimum scoring-path hops matter most and shard operations are manageable.

ADR2 · How confirmed fraud labels reach production models R2Q4C2

Context. New confirmed cases arrive days or weeks later, and a segment loss increase must lead to a compared model within 48 hours. More automation shortens the release path but adds platform and monitoring ownership.

Decision. Automated champion challenger canary (A1); Automated shadow validation and atomic switch (B1); Manual shadow and scheduled switch (C1); Signed bundles staged per shard (D1).

Automated champion challenger canary chosen in A1

Model rollout → Automated champion challenger with canary

  • Automates comparison and staged exposure.
  • Requires monitoring and reliable model evaluation automation.

Choose for repeatable, fast releases when the team can operate automation.

Automated shadow validation and atomic switch chosen in B1

Model rollout → Automated shadow validation and atomic version switch

  • Compares the candidate with current traffic before a controlled switch.
  • Shadow inference consumes extra capacity and the total pipeline time remains to be measured.

Choose for explicit comparison and rollback while reducing manual activation work.

Manual shadow and scheduled switch chosen in C1

Model rollout → Manual shadow evaluation then scheduled switch

  • Familiar and bounded operator workflow.
  • Manual scheduling makes the 48-hour target less dependable.

Choose when operational simplicity outweighs release speed.

Signed bundles staged per shard chosen in D1

Model rollout → Signed model bundles staged to each shard

  • Controlled, verifiable distribution to local scoring instances.
  • Bundle staging by itself does not specify the required recent-transaction comparison.

Choose for local deployment control, paired with a separately owned evaluation process.

ADR3 · What evidence is retained for each historical score R3Q3

Context. A score must remain explainable for 13 months, including model version, input values and training data, with an answer within one working day. Immutable artifacts strengthen reproducibility but increase storage and retention management.

Decision. Immutable score and training ledger (A1, B1, D1); Database score history and retained model artifacts (C1).

Immutable score and training ledger chosen in A1, B1, D1

Audit record → Append-only score ledger with immutable model and training snapshots

  • Binds a score to input and model provenance and retained training snapshots.
  • Requires durable storage, retention controls and retrieval tooling.

Choose where reproducible audit answers are central.

Database score history and retained model artifacts chosen in C1

Audit record → Database score history with retained model artifacts

  • Central history is easy to query operationally.
  • Artifact retention alone may not preserve exact training data and inputs for the full period.

Choose for centralized retrieval only if training-data lineage is added to the retention process.

#1 Seed of approach A mixed

Thought A stream-maintained keyed store should supply recent activity at scoring time; automated comparisons and immutable provenance should support R2, R3, Q3 and Q4. Centralized feature reads may strain Q1 and dependencies may hurt Q2.

Move
  • Serving → Stateless scoring tier
  • Feature state → Stream-processed keyed online store
  • Model rollout → Automated champion challenger with canary
  • Audit record → Append-only score ledger with immutable model and training snapshots

Observed Recent keyed features and versioned score lineage are represented directly, but no failure fallback is present. The numeric latency target and 48-hour retrain cycle need measurement; several moving services add work for the small team.

R1 meetsR2 partlyR3 meetsQ1 partlyQ2 missesQ3 meetsQ4 partlyC1 meetsC2 partly
  • Stateless scoring tier, Stream-processed keyed online store: gains R1 gives up Q1: The remote online feature lookup provides recent keyed activity but adds a hop whose peak latency needs measurement.

A stateless scoring tier receives requests, retrieves keyed online features from the stream-processed store, and scores them with the currently approved model. Automated champion–challenger canaries compare model versions, while the append-only ledger records each score alongside immutable model and training snapshots.

The point's trade-off This supports horizontal scaling, controlled rollout, and strong auditability, but introduces online-store dependency and feature-read latency. Immutable snapshots and score history also increase storage and operational costs, while automated comparison requires reliable monitoring.

#2 Seed of approach B mixed

Thought Colocating cardholder state and scoring should support R1 and Q1, while shadow comparison and immutable snapshots support R2, R3, Q3 and Q4. Missing fallback risks Q2 and stateful shards add operational load.

Move
  • Serving → Sharded scoring with colocated state
  • Feature state → Partitioned stream processor keyed by cardholder
  • Model rollout → Shadow evaluation then atomic version switch
  • Audit record → Append-only score ledger with immutable model and training snapshots

Observed Colocation reduces a remote feature lookup, and the ledger makes past scores reproducible. A service or state failure still has no authorization fallback, and shadow comparison duration is unspecified.

R1 meetsR2 partlyR3 meetsQ1 partlyQ2 missesQ3 meetsQ4 partlyC1 meetsC2 partly
  • Sharded scoring with colocated state, Partitioned stream processor keyed by cardholder: gains R1 gives up C2: Cardholder-local state supports recent-activity scoring but creates shard balancing and state-recovery work for the small team.

Shards receive scoring requests and colocate each cardholder’s state with a partitioned stream processor, while scores are evaluated against a shadow model before an atomic version switch. Every score is written to an append-only ledger that retains the model and training snapshots used to produce it.

The point's trade-off This combines low-latency state access, per-cardholder ordering, controlled rollouts, and reproducible audits. It gives up simplicity through shard balancing and state-management concerns, duplicate shadow-evaluation resources, and continually growing immutable storage.

#3 Seed of approach C mixed

Thought A shared relational system could reduce platform components for C2 and simplify consistency and history, but synchronous aggregate access may miss Q1 and a database failure could block Q2.

  • Feature state → Transactional rolling aggregates in database
  • Model rollout → Manual shadow evaluation then scheduled switch
  • Audit record → Database score history with retained model artifacts

Observed Centralized transactions and model history fit a small operations footprint, but synchronous database work is a poor fit for the 30 ms peak target and has a large failure blast radius. Manual rollout also leaves Q4 timing uncertain.

R1 meetsR2 partlyR3 partlyQ1 missesQ2 missesQ3 partlyQ4 partlyC1 meetsC2 meets
  • Synchronous scoring from shared relational database, Transactional rolling aggregates in database: gains C2 gives up Q1, Q2: Centralized transactions reduce platform components but make database contention and failure affect the authorization path.

Each transaction is scored synchronously using transactional rolling aggregates in a shared relational database, with the active model producing the score. Candidate models are evaluated manually in shadow mode before a scheduled switch, and each score is recorded with retained model artifacts for auditing.

The point's trade-off This favors transactional consistency, centralized operation, controlled rollout, and reproducibility. It gives up rollout speed and scalability; synchronous database access and aggregate updates can increase latency and database contention.
