Git hosting for a fast-growing engineering organization

A software company hosts its own Git service for 3,000 engineers in four regions. Its CI system starts about 40,000 jobs a day, each fetching a repository. The largest repository has 15 years of history and is about 200 GB; most engineers touch only a small part of it. The service runs in the company's cloud account, and a team of five engineers builds and operates it.

Alternatives

A1 · Quorum commits with regional commit-aware caches

Store immutable objects in replicated cloud storage and use regional stateless gateways with commit-aware caches. A push succeeds after quorum commit and cache invalidation; clients use partial clone.

Composed of 3 partial design points, one per ADR:

  • ADR1 · Replicated cloud object storage Q1C1 Repository storage → Replicated immutable Git objects in cloud object storage
  • ADR2 · Commit-aware stateless gateways R1Q2Q3C2 Serving topology → Stateless Git protocol gateways across regions with commit-aware caches
  • ADR3 · Quorum metadata and cache invalidation with partial clone R2Q1Q3Q4C2 Consistency → Quorum-committed push metadata with cache invalidation before successLarge repository access → Standard Git partial clone with blob filtering

As a whole: Git objects are replicated immutably in cloud object storage, while stateless regional gateways serve Git traffic through commit-aware caches. A push succeeds only after metadata reaches quorum and affected caches are invalidated; clients can use partial clone to fetch only required blobs.

B1 · Synchronous multi-zone storage with regional gateways

Use synchronously replicated block storage across three zones and a single metadata writer, with stateless regional Git gateways and standard partial clone.

Composed of 3 partial design points, one per ADR:

  • ADR1 · Synchronous three-zone block storage Q1C1 Repository storage → Synchronously replicated block storage across three zones
  • ADR2 · Stateless gateways with a synchronous writer R1Q2Q3C2 Serving topology → Stateless Git protocol gateways across regions
  • ADR3 · Synchronous single-writer metadata with partial clone R2Q1Q3Q4C2 Consistency → Single-writer repository metadata with synchronous replicationLarge repository access → Standard Git partial clone with blob filtering

As a whole: Repositories reside on block storage synchronously replicated across three zones, while a single authoritative metadata writer replicates its updates synchronously. Stateless Git gateways in each region serve clients and route operations to that writer and storage, with partial-clone filtering limiting large-repository data transfer.

D1 · Fenced leader with regional read replicas

Store immutable objects in replicated cloud storage, accept pushes through a designated leader, and serve reads from regional replicas with fencing and read barriers. Use standard partial clone.

Composed of 3 partial design points, one per ADR:

  • ADR1 · Replicated cloud object storage Q1C1 Repository storage → Replicated immutable Git objects in cloud object storage
  • ADR2 · Regional read replicas with push leader R1Q2Q3C2 Serving topology → Regional read replicas and a designated push leader
  • ADR3 · Fenced leader and read barriers with partial clone R2Q1Q3Q4C2 Consistency → Leader-committed metadata with fencing and read barriersLarge repository access → Standard Git partial clone with blob filtering

As a whole: The system stores immutable Git objects in replicated cloud object storage, with a designated leader accepting pushes and regional replicas serving reads. The leader commits metadata under fencing, while read barriers ensure replicas expose committed state; partial-clone clients fetch only the blobs they request.

ADR1 · Choose durable repository object storage Q1C1

Context. A single machine or disk loss must not lose a pushed commit, and five engineers must operate the platform. Managed replicated object storage limits storage operations; synchronous multi-zone block storage offers a direct durability model but introduces a tightly coordinated write path.

Decision. Replicated cloud object storage (A1, D1); Synchronous three-zone block storage (B1).

Replicated cloud object storage chosen in A1, D1

Repository storage → Replicated immutable Git objects in cloud object storage

  • Replicated immutable objects tolerate individual machine or disk loss.
  • Managed storage reduces custom storage operations.
  • The service depends on object-storage availability and replication behavior.

It supports durability while reducing storage maintenance for the small team.

Synchronous three-zone block storage chosen in B1

Repository storage → Synchronously replicated block storage across three zones

  • Synchronous zone replication protects persisted data.
  • Synchronous writes and recovery coordination add latency and operations work.

This option favors a direct replicated volume model and is retained as a distinct durability trade-off.

ADR2 · Serve standard Git traffic and recover from a server failure R1Q2Q3C2

Context. The service must use standard Git protocol and clients, continue after a server failure within one minute, and serve CI quickly in four regions. Stateless regional gateways offer replaceable serving capacity; regional read replicas improve locality but depend on leader and replica coordination.

Decision. Commit-aware stateless gateways (A1); Stateless gateways with a synchronous writer (B1); Regional read replicas with push leader (D1).

Commit-aware stateless gateways chosen in A1

Serving topology → Stateless Git protocol gateways across regions with commit-aware caches

  • Regional stateless endpoints support standard Git traffic and automated failover.
  • Commit-aware caches can serve recent refs near CI.
  • Cache management adds coordination, and latency targets need load evidence.

This pairs regional serving with pre-success invalidation for freshness.

Stateless gateways with a synchronous writer chosen in B1

Serving topology → Stateless Git protocol gateways across regions

  • Regional gateways distribute Git reads and remain replaceable.
  • The writer remains a common dependency and can constrain throughput.

This keeps Git serving stateless while retaining a synchronous central writer.

Regional read replicas with push leader chosen in D1

Serving topology → Regional read replicas and a designated push leader

  • Local replicas can serve regional fetches.
  • Replica lag, leader failover, and barriers need operational handling.

This prioritizes local reads while using leader coordination to preserve commit order.

ADR3 · Make pushes visible and keep large repositories usable R2Q1Q3Q4C2

Context. The largest repository is about 200 GB, so engineers need selective access through standard Git clients. A fetch after a successful push must see that push. Quorum commits with invalidation and leader commits with read barriers can preserve visibility, while partial clone reduces initial transfers but deferred object reads may affect latency.

Decision. Quorum metadata and cache invalidation with partial clone (A1); Synchronous single-writer metadata with partial clone (B1); Fenced leader and read barriers with partial clone (D1).

Quorum metadata and cache invalidation with partial clone chosen in A1

Consistency → Quorum-committed push metadata with cache invalidation before successLarge repository access → Standard Git partial clone with blob filtering

  • Pre-success invalidation and quorum commit make pushed refs authoritative.
  • Partial clone avoids downloading unneeded blobs with standard Git.
  • Quorum coordination and invalidation can add push latency; deferred blobs can affect fetch time.

This directly addresses post-push visibility and large-repository access.

Synchronous single-writer metadata with partial clone chosen in B1

Consistency → Single-writer repository metadata with synchronous replicationLarge repository access → Standard Git partial clone with blob filtering

  • Synchronous single-writer ordering gives a clear read-after-write path.
  • Partial clone limits initial transfer.
  • Synchronous writes can add latency and the writer can bottleneck.

This trades write latency for straightforward metadata ordering.

Fenced leader and read barriers with partial clone chosen in D1

Consistency → Leader-committed metadata with fencing and read barriersLarge repository access → Standard Git partial clone with blob filtering

  • Fencing and barriers keep reads ordered behind committed writes.
  • Partial clone limits initial transfer.
  • Leader coordination may add latency and complicates failover.

This separates push leadership from regional reads while preserving visibility.

Asynchronous regional propagation discarded

Consistency → Asynchronous metadata propagation between regions

  • Asynchronous replication can keep regional reads responsive.
  • A regional fetch can observe stale refs after a successful push.

It fails the required post-push visibility guarantee.

The search, round by round

Round 1 · 3 points: seed A, seed B, seed C
#1 Seed of approach A mixed

Thought Replicated storage and committed metadata directly address durability and read-after-write. Regional gateways support availability and locality; neither failover timing nor the 30-second p95 target is measured. Partial clone addresses the large repository with standard clients.

Move
  • Repository storage → Replicated immutable Git objects in cloud object storage
  • Serving topology → Stateless Git protocol gateways across regions
  • Consistency → Quorum-committed push metadata with authoritative post-push reads
  • Large repository access → Standard Git partial clone with blob filtering

Observed The architecture is plausible but quantitative availability, performance and staffing fit remain unverified.

R1 meetsR2 meetsQ1 meetsQ2 partlyQ3 partlyQ4 meetsC1 partlyC2 meets
  • Quorum-committed push metadata with authoritative post-push reads: gains Q1, Q4 gives up Q3: Quorum and authoritative reads protect durable, current refs but add latency.
  • Standard Git partial clone with blob filtering: gains R2, C2 gives up Q3: Filtering reduces transfers with standard clients but later blob retrieval can affect fetch time.
  • Stateless Git protocol gateways across regions: gains Q2, Q3 gives up C1: Regional stateless gateways improve locality and failover while adding operational coordination.

Replicated immutable Git objects are stored in cloud object storage, while stateless gateways in multiple regions serve Git clients. Pushes become visible after quorum-committed metadata updates, and authoritative post-push reads ensure clients observe the committed state; partial clone blob filtering limits large-repository transfers.

The point's trade-off This provides durable, horizontally scalable, multi-region access and efficient large-repository checkout, but pays replication and quorum latency/costs and depends on object-storage availability. Partial clones also shift some cost and complexity to later blob retrieval.

#2 Seed of approach B mixed

Thought Synchronous three-zone replication with active-passive Git servers should protect commits and support automatic failover, while partial clone limits large transfers.

Move
  • Repository storage → Synchronously replicated block storage across three zones
  • Serving topology → Active-passive Git servers with automatic leader failover
  • Consistency → Single-writer repository metadata with synchronous replication
  • Large repository access → Standard Git partial clone with blob filtering

Observed The single writer and synchronous path simplify ordering but raise latency and create failover and operations work.

R1 meetsR2 meetsQ1 meetsQ2 meetsQ3 partlyQ4 meetsC1 partlyC2 meets
  • Synchronously replicated block storage across three zones, Single-writer repository metadata with synchronous replication: gains Q1, Q4 gives up Q3: Synchronous replication and single-writer ordering protect data and read-after-write behavior but add write latency.
  • Active-passive Git servers with automatic leader failover: gains Q2 gives up C1: Automatic standby takeover aids recovery but maintaining failover behavior adds operational work.
  • Standard Git partial clone with blob filtering: gains R2, C2 gives up Q3: Partial clone limits transferred data but later blob requests add work.

The system stores repositories on block storage synchronously replicated across three zones, with one active Git server serving writes and a passive server ready to assume leadership. Repository metadata remains single-writer and synchronously replicated, while clients use partial clone blob filtering for large repositories.

The point's trade-off This provides strong metadata consistency, zone-level durability, automatic failover, and reduced large-clone transfer. It gives up write latency and operational simplicity due to synchronous cross-zone replication, keeps standby capacity underused, and makes clients depend on fetching omitted blobs when needed.

#3 Seed of approach C weak

Thought Asynchronous regional replicas should improve local read latency and partial clone should reduce transfer; replication delay may compromise post-push visibility.

Move
  • Repository storage → Eventually replicated object storage with regional caches
  • Serving topology → Regional read replicas with a central push endpoint
  • Consistency → Asynchronous metadata propagation between regions
  • Large repository access → Standard Git partial clone with blob filtering

Observed The point misses Q4 by design: a fetch can start after the central push succeeds and still reach a lagging regional replica.

R1 meetsR2 meetsQ1 partlyQ2 partlyQ3 partlyQ4 missesC1 partlyC2 meets
  • Eventually replicated object storage with regional caches, Asynchronous metadata propagation between regions: gains Q3 gives up Q4, Q1: Regional asynchronous propagation favors local read speed but cannot guarantee that a post-success fetch sees the push.
  • Regional read replicas with a central push endpoint: gains Q3 gives up Q2: Regional read replicas aid local reads but the central push endpoint remains a failure and throughput focus.

Repositories are stored in eventually replicated object storage, with regional caches serving regional read replicas while pushes go through a central endpoint. Metadata propagates asynchronously between regions, and clients use Git partial clone with blob filtering to fetch only needed large-repository content.

The point's trade-off This improves regional read performance, storage scalability, and large-repository transfer efficiency. It gives up immediate cross-region metadata freshness and local write latency, while central pushes remain a potential bottleneck and cached or replica data may temporarily lag.

The point's trade-off This provides durable storage, regional scalability, and fresher read results, but quorum coordination and invalidation increase push latency and operational complexity. Partial clone reduces initial transfer costs but can add on-demand fetch latency and depends on client support.
