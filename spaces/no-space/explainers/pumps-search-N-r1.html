Pump failure prediction

A water utility runs about 400 pumps in 12 pumping stations. Each pump has vibration, temperature and pressure sensors reporting every second. Unexpected failures interrupt water supply. The utility wants predictive maintenance; several stations have unreliable mobile connections, there are two data scientists, and IT supports servers and networks.

How to read this page

A coding agent searched for designs that solve this problem. It combined decisions (dimensions) and their options (values) into design points, and judged each point against every requirement: meets, partly or misses. It proposes 4 alternatives. Every judgement here is the agent's; the page lays out its rationale file.

  • Decisions (ADRs) lists the alternatives, then one record per decision: the requirements that drive it, and every option weighed, with its pros and cons, chosen by an alternative or discarded.
  • Comparison puts the alternatives side by side, with the rows where they differ first.
  • Trajectory shows how the agent got there:
    • the lanes show each approach round by round, with every point coloured strong, mixed or weak;
    • a strip shows how each point met each requirement;
    • the story gives each point's thought, change, observation and trade-offs.

No design space was used. The agent named the decisions and options itself, so nothing was checked against a space and there are no gaps in one.

Alternatives

A1 · Shared edge model with rule fallback

Run the shared on-premises model at each station and queue local warnings, with fallback rules and versioned family retraining. This favors resilient operations while retaining fleet-wide learning.

Composed of 2 partial design points, one per ADR:

  • ADR1 · Station edge with queued local inference Q1C1 Inference placement → Station edgeOffline warning path → Local inference and alert queue
  • ADR2 · Shared fleet model with family-versioned learning R1R2Q2 Model organization → Shared fleet model with local fallback rulesLearning loop → Versioned per-family retraining from inspection labels

As a whole: At each station, a shared fleet model runs at the edge, with local fallback rules maintaining decisions when the model is unavailable. Offline warnings are handled by local inference and an alert queue, while inspection labels drive versioned retraining for each equipment family.

B1 · Calibrated model-family plugins

Deploy calibrated plugins at station edges, with local warning queues and separately versioned retraining from inspection labels. This provides model-family modularity at the cost of more deployment work.

Composed of 2 partial design points, one per ADR:

  • ADR1 · Station edge with model and rule fallback Q1C1 Inference placement → Station edgeOffline warning path → Local model with rule fallback
  • ADR2 · Calibrated family plugins with versioned retraining R1R2Q2 Model organization → Model-family plugins with calibrationLearning loop → Versioned per-family retraining from inspection labels

As a whole: At each station, family-specific model plugins run at the edge and apply calibration to produce predictions. A local warning model operates offline, falling back to rules when needed, while inspection labels drive versioned retraining separately for each model family.

C1 · Independent family models

Run separate pump-family models at station edges and queue warnings locally, with central retraining from inspection labels. It favors independent scoring paths without requiring federated coordination.

Composed of 2 partial design points, one per ADR:

  • ADR1 · Station edge with queued local inference Q1C1 Inference placement → Station edgeOffline warning path → Local inference and alert queue
  • ADR2 · Independent family models with central retraining R1R2Q2 Model organization → Independent model per pump familyLearning loop → Central retraining from inspection labels

As a whole: At each station, a pump-family-specific model runs locally, producing predictions and placing warnings in a local alert queue. Inspection labels are later centralized to retrain the independent family models, which are then redeployed to stations.

D1 · Calibrated plugins with edge fallback

Deploy calibrated model-family plugins at station edges, with local model and rule fallback for warnings and central retraining from inspection labels. This isolates pump-family scoring while keeping the feedback loop centrally managed on premises.

Composed of 2 partial design points, one per ADR:

  • ADR1 · Station edge with model and rule fallback Q1C1 Inference placement → Station edgeOffline warning path → Local model with rule fallback
  • ADR2 · Calibrated family plugins with central retraining R1R2Q2 Model organization → Model-family plugins with calibrationLearning loop → Central retraining from inspection labels

As a whole: Pump data is evaluated at the station edge using a selected model-family plugin and its calibration. When offline, the local model continues issuing warnings and falls back to rules, while inspection labels are sent to central retraining to improve future model releases.

ADR1 · Where inference runs and warnings remain available Q1C1

Context. Sensor processing must stay on utility premises, and warnings must reach station technicians through a two-day connection loss. Station-edge inference with a local warning path satisfies both demands; the remaining choice is whether the offline path also includes local rule fallback.

Decision. Station edge with queued local inference (A1, C1); Station edge with model and rule fallback (B1, D1).

Station edge with queued local inference chosen in A1, C1

Inference placement → Station edgeOffline warning path → Local inference and alert queue

  • Keeps inference on premises.
  • Generates and queues warnings during network loss.
  • Does not describe a fallback when model inference itself is unavailable.

Chosen by the shared and independent family model alternatives.

Station edge with model and rule fallback chosen in B1, D1

Inference placement → Station edgeOffline warning path → Local model with rule fallback

  • Keeps inference on premises.
  • Provides a local fallback warning path.
  • Requires maintaining local rules alongside model versions.

Chosen by alternatives that prioritize a fallback path during degraded operation.

ADR2 · How pump models and inspection learning are organized R1R2Q2

Context. Predictions need to identify likely failures, improve from inspection findings, and allow a new pump model to receive predictions without changing other pumps’ scoring. Shared models simplify fleet learning, while family-specific plugins or models isolate scoring and updates.

Decision. Shared fleet model with family-versioned learning (A1); Calibrated family plugins with versioned retraining (B1); Independent family models with central retraining (C1); Calibrated family plugins with central retraining (D1).

Shared fleet model with family-versioned learning chosen in A1

Model organization → Shared fleet model with local fallback rulesLearning loop → Versioned per-family retraining from inspection labels

  • Inspection labels can improve a fleet-wide model.
  • Versioned family retraining supports controlled updates.
  • New-family work may still affect shared model management.

Chosen when fleet-wide reuse of inspection learning is preferred.

Calibrated family plugins with versioned retraining chosen in B1

Model organization → Model-family plugins with calibrationLearning loop → Versioned per-family retraining from inspection labels

  • Isolates new-family scoring and calibration.
  • Provides traceable per-family updates from inspection findings.
  • Adds plugin, calibration, and version management across stations.

Chosen when onboarding isolation and controlled family updates are primary.

Independent family models with central retraining chosen in C1

Model organization → Independent model per pump familyLearning loop → Central retraining from inspection labels

  • Separates pump-family scoring paths.
  • Offers a direct central inspection-label learning loop.
  • Requires maintaining several model families.

Chosen for family independence while using a straightforward on-premises learning pipeline.

Calibrated family plugins with central retraining chosen in D1

Model organization → Model-family plugins with calibrationLearning loop → Central retraining from inspection labels

  • Isolates scoring by pump family.
  • Keeps retraining centrally managed on premises.
  • Updates are less explicitly versioned per family.

Chosen for isolated scoring with a simpler central feedback pipeline.

Federated station updates discarded

Model organization → Independent model per pump familyLearning loop → Federated station updates

  • Can update models using station-local training data.
  • Requires coordinating federated updates, and inspection findings do not automatically translate into improved deployed predictions.

Set aside because the learning effect and coordination burden are less direct for this utility.
