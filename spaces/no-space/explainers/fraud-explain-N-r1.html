Card-fraud scoring service

A payments company scores every card transaction for fraud before it is authorized. It processes about 3,000 transactions per second on a normal day and up to five times as many during seasonal sales. Fraudsters adapt within weeks, and the confirmed fraud labels (chargebacks) arrive days to weeks after the transaction. Auditors and the card schemes can ask, months later, why a given transaction was scored the way it was. The ML team has five data scientists and two ML engineers. The company's operations team runs the data centres and the shared infrastructure, but there is no platform team for machine learning.

The solution

S · Fraud scoring as built

A Kafka and Flink feature path feeds a synchronous XGBoost scorer with a rule fallback. Scores and training lineage are retained, while nightly retraining is guarded by a three-day shadow review.

ADR1 · Maintain recent card activity for online scoring R1Q1C1C2

Context. Scoring must use recent per-card activity within a tight request budget, and card data must remain in the certified environment. The implementation also needs to fit a small team without a dedicated ML platform group.

Decision. Kafka, Flink and Redis aggregates with XGBoost service.

Kafka, Flink and Redis aggregates with XGBoost service chosen

Activity state → Kafka to Flink aggregates in RedisScoring runtime → XGBoost Python REST on six autoscaling Kubernetes replicas

“Flink jobs consume the topic and keep per-card aggregates (spend and counts over the last hour, day and week, and the number of distinct merchants) up to date in a Redis cluster.”
“The model is a gradient-boosted tree model (XGBoost). It is packaged in a container with a small Python REST service and runs on the company's Kubernetes cluster, with six replicas and autoscaling on CPU.”
  • Maintains rolling card aggregates for the request path.
  • Runs in the company's environment and can scale serving replicas.
  • Adds multiple operated components.
  • No peak p99 or capacity result demonstrates Q1.

This combination is plausible for low-latency online features and is compatible with C1 when deployed inside the environment. The requirements do not force Kafka, Flink, Redis, XGBoost or six replicas; those choices remain unproven against Q1 and partly at odds with C2.

Neural network scorer on the same serving platform discarded

Model type → neural network modelServing runtime → Python REST on six autoscaling Kubernetes replicas

  • Can score transactions and may represent complex patterns.
  • May require more inference resources and operational effort.
  • No evidence establishes the latency target.

The requirements do not select a model family. The contrast confirms that the selected tree family is a free choice absent comparative evidence.

ADR2 · Keep authorizations moving when scoring fails Q2

Context. A scorer or data source failure must not prevent authorization; weaker fraud detection is acceptable for a limited period.

Decision. Timeout to existing rule engine.

Timeout to existing rule engine chosen

Failure behavior → 25 ms timeout with rule-engine fallback

“The authorization switch calls the service synchronously with a 25 ms timeout. If the call times out or fails, the switch uses the existing rule engine for that transaction and logs that no score was used.”
  • Bounds how long authorization waits on the scorer.
  • Provides a decision path when scoring fails.
  • Fallback decisions can have weaker fraud detection.

Q2 forces continued authorization through a fallback. The particular 25 ms timeout and existing rule engine are implementation choices.

ADR3 · Retain enough evidence to reconstruct a score R3Q3C1

Context. The team must answer about a score up to 13 months later with its model version, input values and training data, while keeping card data in the PCI environment.

Decision. Retained score records and training snapshots.

Retained score records and training snapshots chosen

Score audit record → append-only on-prem object store for 13 monthsModel lineage → MLflow records runs and holds registry

“Every score is written, with the model version and all input values, to an append-only table in the company's on-premises object store, kept for 13 months.”
“MLflow records the parameters, the metrics, the training data snapshot and the model artifact of every run, and holds the model registry.”
  • Preserves per-score model identity and all inputs for the full requested period.
  • Connects model artifacts to their training data snapshots.
  • Requires retention and storage operations.
  • Specific storage and tracking products are choices.

The retention, fields and in-environment location are forced by R3, Q3 and C1. Append-only object storage and MLflow are free implementation choices that provide the needed records.

ADR4 · Retrain and control model promotion R2Q3Q4C2

Context. Delayed confirmed labels require recurring retraining, with lineage for audit and a comparison against the current model before release. A release must reach production within 48 hours under Q4.

Decision. Nightly training with three-day manual shadow gate.

Nightly training with three-day manual shadow gate chosen

Training cadence → nightly Airflow on 90 days of labelled dataModel lineage → MLflow records runs and holds registryPromotion gate → three-day shadow comparison and manual risk-team promotionActivation → load promoted model at service restart

“An Airflow pipeline retrains the model every night on the last 90 days of labelled transactions.”
“MLflow records the parameters, the metrics, the training data snapshot and the model artifact of every run, and holds the model registry.”
“A new model first runs in shadow mode next to the production model for three days; the risk team reviews the comparison and promotes it by hand in MLflow.”
“The scoring service loads the promoted model at its next restart.”
  • Retrains regularly as labelled cases arrive.
  • Records run details and compares a candidate before promotion.
  • Keeps a human review checkpoint.
  • The three-day shadow period exceeds the 48-hour production target.
  • Manual review and restart add deployment delay; restart time is unspecified.

Recurring retraining and comparison are required, but the specific scheduler, window, registry, manual review and restart activation are choices. The three-day gate misses Q4, so this chosen combination is only partially supported.

Automated promotion after shadow comparison discarded

Promotion gate → automated promotion after shadow comparison

  • Retains comparison while removing a manual delay.
  • Automated gates can miss weaknesses not exposed by the comparison.
  • No duration is specified, so 48-hour compliance remains unproven.

Manual approval is not required by the drivers; the alternative could help Q4 but has no stated duration and therefore cannot be shown to meet it.

Load the model while the service remains running discarded

Activation → load promoted model without restarting the service

  • Avoids restart delay and can speed activation.
  • Adds runtime model switching complexity and transition risks.

Q4 does not prescribe activation mechanics. Hot loading may reduce delay, while the chosen restart behavior is free because its duration is unknown.

ADR5 · Expose operational and decision signals Q2Q4C2

Context. The dispute team benefits from explanations, while operators need visibility into fallback and score drift to understand service behavior and changing fraud patterns.

Decision. Top feature explanations and Grafana monitoring.

Top feature explanations and Grafana monitoring chosen

Score explanation → return three top featuresOperations monitoring → Grafana distribution, fallback and drift dashboards/alerts

“The service returns, with every score, the three features that pushed the score up the most, which the dispute team uses to explain declines to cardholders.”
“Grafana dashboards show the score distribution and the share of rule-engine fallbacks, and alert when the score distribution drifts from last month's.”
  • Gives the dispute team a concise explanation signal.
  • Makes fallback and distribution changes visible to operators.
  • Top features do not replace the exact input and model records required for audit.
  • Dashboards and alerts add operational configuration.

These are useful additions, but no requirement forces the specific explanations, dashboard or tool. The retained audit record separately addresses exact reconstruction.

#2 A region of #1: part of the solution grounded

Thought R1 and Q1 call for recent activity at scoring time; C1 requires all processing to remain within the PCI environment.

Move
  • Activity state → Kafka to Flink aggregates in Redis

Observed The region provides recent rolling values and can meet the PCI boundary when its components are deployed inside it. Its low-latency intent is plausible, but no measured p99 under peak load proves Q1.

R1 meetsQ1 partlyC1 meets
  • Kafka to Flink aggregates in Redis: gains R1 gives up Q1: Precomputed state avoids calculating long activity windows during each request, but the extra stream and Redis hops can add lag and latency.

Kafka streams card-activity events to Flink, which computes rolling aggregates such as transaction counts or spending totals. Flink writes the resulting activity state to Redis, where the fraud-scoring service can retrieve it with low latency.

The point's trade-off This provides fast, continuously updated features and separates stream processing from scoring, but introduces operational complexity and possible lag or inconsistency between Kafka processing and the Redis state.

#3 A region of #1: part of the solution grounded

Thought Q2 calls for authorizations to continue through scorer failures, accepting degraded fraud detection.

Move
  • Failure behavior → 25 ms timeout with rule-engine fallback

Observed The timeout bounds waiting on the scorer and the existing rules keep an authorization decision available; logging the fallback also makes degraded operation visible.

Q2 meets

The service attempts its primary fraud score and permits it up to 25 ms. If the score is not returned within that limit, it applies the rule-engine fallback so a decision can still be produced.

The point's trade-off This provides bounded latency and continued operation, but sacrifices the primary scorer’s potentially richer or more accurate assessment whenever it times out; the 25 ms limit may therefore increase missed fraud or false declines.

The point's trade-off This provides regular retraining, reproducible lineage, and a cautious production gate, but the fixed 90-day window may limit historical context and manual approval slows deployment. The shadow period also postpones realizing a candidate model’s potential benefits.
