Card-fraud scoring service

A payments company scores every card transaction for fraud before it is authorized. It processes about 3,000 transactions per second on a normal day and up to five times as many during seasonal sales. Fraudsters adapt within weeks, and the confirmed fraud labels (chargebacks) arrive days to weeks after the transaction. Auditors and the card schemes can ask, months later, why a given transaction was scored the way it was. The ML team has five data scientists and two ML engineers. The company's operations team runs the data centres and the shared infrastructure, but there is no platform team for machine learning.

Alternatives

A1 · Redis features with delegated operations

Use Redis keyed features and stateless replicated scoring with a local rules fallback. Daily challenger promotion and an immutable 13-month record support adaptation and audit, while operations owns the managed components.

Composed of 3 partial design points, one per ADR:

  • ADR1 · Shared keyed feature store and stateless replicas R1Q1Q2C1 Online features → Redis keyed by cardholderServing → replicated stateless scorer with local feature cache and rules fallback
  • ADR2 · Automated daily champion validation with operations-owned components R2Q4C2C1 Model updates → automated daily batch retraining with champion-challenger validationOperations → managed open-source components owned by operations
  • ADR3 · Immutable 13-month score and training snapshots R3Q3 Audit → immutable score log with model, input, and training dataset snapshots retained for 13 months

As a whole: The system stores cardholder-keyed online features in Redis, while replicated stateless scorers use local caches and rules as a fallback to serve scores. Automated daily retraining uses champion-challenger validation, and immutable logs retain each score, model, inputs, and training-dataset snapshot for 13 months; operations owns the managed open-source components.

B1 · Stateful stream scoring on existing infrastructure

Co-locate keyed feature processing and scoring on replicated stream infrastructure, with rule fallback and replay-based champion evaluation. The append-only record retains score inputs and model training snapshots.

Composed of 3 partial design points, one per ADR:

  • ADR1 · Co-located stateful stream scoring R1Q1Q2C1 Online features → stateful stream processor with local keyed stateServing → co-located scoring with replicated stream processing and rule fallback
  • ADR2 · Frequent replay evaluation on existing stream infrastructure R2Q4C2C1 Model updates → frequent batch retraining with champion-challenger replayOperations → existing stream infrastructure operated by shared operations
  • ADR3 · Append-only score, input, model, and training snapshots R3Q3 Audit → append-only event log with versioned model and training snapshots including input values retained for 13 months

As a whole: Transactions flow through a stateful stream processor, whose local keyed state supports online features and co-located scoring; replicated processors provide resilience, with rules as fallback. Frequent batch retraining replays audited inputs and versioned training snapshots to compare challengers with the champion, while shared operations runs the existing stream infrastructure.

D1 · Local journal with replicated rules fallback

Keep rolling counters in durable local journals, replicate scoring, and fall back to deterministic rules. Daily challenger replay supports model updates, with immutable score and training lineage records.

Composed of 3 partial design points, one per ADR:

  • ADR1 · Embedded journaled counters R1Q1Q2C1 Online features → embedded rolling counters backed by a durable local journalServing → replicated scorer with deterministic rules fallback
  • ADR2 · Daily challenger replay with local model pipelines R2Q4C2C1 Model updates → daily challenger retraining and replay comparison on recent transactions after label confirmationOperations → shared operations runs commodity services; ML team owns model pipelines
  • ADR3 · Immutable score records with dataset references R3Q3 Audit → immutable score records with model version, input values, and training dataset references retained for 13 months

As a whole: The system computes online features with embedded rolling counters persisted in a durable local journal, and a replicated scorer serves decisions with deterministic rules as fallback. The ML team retrains daily challengers, replaying recent transactions after labels arrive, while immutable score records retain model versions, inputs, and dataset references for 13 months; shared operations runs the commodity services.

ADR1 · How to keep recent activity on the authorization scoring path R1Q1Q2C1

Context. Every authorization needs a score informed by recent activity, even at 15,000 transactions per second. The scoring path must return within 30 ms at p99 and failures must not stop authorization. All transaction data and processing remain inside the PCI-certified environment.

Decision. Shared keyed feature store and stateless replicas (A1); Co-located stateful stream scoring (B1); Embedded journaled counters (D1).

Shared keyed feature store and stateless replicas chosen in A1

Online features → Redis keyed by cardholderServing → replicated stateless scorer with local feature cache and rules fallback

  • Scoring replicas can scale independently while reading shared recent activity.
  • Local rules provide a degraded path during feature or model-service failure.
  • The shared feature store must be provisioned, replicated, and operated for peak throughput.
  • Fallback detection quality is weaker during outages.

Chosen for a separately scalable serving path with an explicit authorization-safe fallback.

Co-located stateful stream scoring chosen in B1

Online features → stateful stream processor with local keyed stateServing → co-located scoring with replicated stream processing and rule fallback

  • Recent keyed state is close to scoring and can avoid a remote feature lookup.
  • Replicated processing and rule fallback support continuity.
  • State recovery and replication add complexity to the critical service.
  • Throughput and latency targets still need peak-load measurement.

Chosen where a stream platform already exists and its team can operate the stateful service.

Embedded journaled counters chosen in D1

Online features → embedded rolling counters backed by a durable local journalServing → replicated scorer with deterministic rules fallback

  • Local state avoids an external feature lookup on the scoring path.
  • Replicated scorers and rules provide a continuity path.
  • Replica consistency, recovery, and journal retention require careful implementation.
  • Peak performance and cross-replica feature consistency remain unproven.

Chosen as a compact data path when the team can own journal synchronization and recovery.

Asynchronous event-sourced scoring discarded

Online features → event-sourced transaction stream and materialized per-cardholder stateServing → asynchronous scoring with authorization timeout and static fallback

  • Event history can rebuild recent state and supports replay.
  • Timeout fallback allows authorization to proceed.
  • Asynchronous completion does not reliably satisfy scoring before authorization and the 30 ms p99 target.

Dropped because it misses transaction-time score availability and latency.

ADR2 · How to update models and divide operational ownership R2Q4C2C1

Context. Confirmed fraud labels arrive late, yet new models must be compared on recent transactions and promoted within 48 hours after a segment loss rate rises. Seven people operate the system without a dedicated ML platform team, and data processing must stay internal.

Decision. Automated daily champion validation with operations-owned components (A1); Frequent replay evaluation on existing stream infrastructure (B1); Daily challenger replay with local model pipelines (D1).

Automated daily champion validation with operations-owned components chosen in A1

Model updates → automated daily batch retraining with champion-challenger validationOperations → managed open-source components owned by operations

  • Daily retraining and comparison provide a clear promotion cadence.
  • Operations owns common infrastructure components.
  • Training cannot use fraud labels before they arrive.
  • Daily cadence may lag a rapidly changing segment and requires storage and governance ownership.

Chosen to automate a controlled refresh while relying on the existing operations function.

Frequent replay evaluation on existing stream infrastructure chosen in B1

Model updates → frequent batch retraining with champion-challenger replayOperations → existing stream infrastructure operated by shared operations

  • Replay compares challenger models against recent transactions.
  • Reuses a stream platform already operated internally.
  • Frequent replay and stream recovery increase system complexity.
  • The ML team and operations need an explicit division of model and platform support.

Chosen when existing stream operations can support the replay workload and stateful serving.

Daily challenger replay with local model pipelines chosen in D1

Model updates → daily challenger retraining and replay comparison on recent transactions after label confirmationOperations → shared operations runs commodity services; ML team owns model pipelines

  • Makes recent-transaction comparison explicit before candidate promotion.
  • Leaves commodity infrastructure to shared operations.
  • ML engineers retain pipeline and model release ownership.
  • Delayed labels bound how quickly a new pattern can enter training.

Chosen to meet the explicit comparison workflow without building a custom ML platform.

Label-matured scheduled batch discarded

Model updates → scheduled batch retraining after label maturationOperations → managed open-source components owned by operations

  • Uses confirmed labels and has a simple scheduled operating pattern.
  • The point did not specify recent-transaction comparison or a cadence that assures the 48-hour promotion window.

Replaced with daily challenger validation to make Q4 testable.

Custom online learning platform discarded

Model updates → online updates when delayed fraud labels arriveOperations → custom streaming platform maintained by ML team

  • Can integrate new labels directly into a model update path.
  • Custom platform maintenance conflicts with the small team's capacity, and online updates alone do not provide the required challenger comparison.

Dropped because of the C2 staffing conflict and incomplete promotion gate.

ADR3 · What evidence to retain for historical score explanations R3Q3

Context. For any past score, the team must identify the model and inputs. Auditors may ask about scores 13 months later and need a response within one working day that also identifies the training data. The record therefore needs durable score inputs, model identity, and model training lineage.

Decision. Immutable 13-month score and training snapshots (A1); Append-only score, input, model, and training snapshots (B1); Immutable score records with dataset references (D1).

Immutable 13-month score and training snapshots chosen in A1

Audit → immutable score log with model, input, and training dataset snapshots retained for 13 months

  • Explicitly retains all requested evidence for the full period.
  • Immutable records support consistent historical reconstruction.
  • Storage, privacy controls, and retrieval operations need capacity planning.

Chosen to make the retention period and required audit artifacts explicit.

Append-only score, input, model, and training snapshots chosen in B1

Audit → append-only event log with versioned model and training snapshots including input values retained for 13 months

  • Connects score inputs to model and training artifacts in an append-only history.
  • Retention duration and response process still need operational policy.

Chosen because it captures the full lineage while fitting the stream replay approach.

Immutable score records with dataset references chosen in D1

Audit → immutable score records with model version, input values, and training dataset references retained for 13 months

  • Records model identity, inputs, and the training dataset reference for each score.
  • The alternative must enforce 13-month retention and keep referenced datasets available.

Chosen as direct score evidence with dataset lineage, with retention policy to be specified.

Model and input snapshot only discarded

Audit → immutable decision log with model and input snapshot

  • Explains which model and values produced a score.
  • Does not identify the training data or specify a 13-month retention period.

Insufficient for the full historical audit scenario.

Versioned model and training snapshot without explicit inputs discarded

Audit → append-only event log with versioned model and training snapshots

  • Preserves model versions and training lineage.
  • Does not explicitly retain input values needed to reproduce a score explanation.

Refined to include captured score inputs.
