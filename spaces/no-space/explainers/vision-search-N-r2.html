On-device visual inspection

A manufacturer inspects parts for defects with cameras along its production lines. There are 40 lines in three plants, each with two to four cameras attached to a small edge computer next to the line. The plants' network is unreliable: some lines are cut off for days at a time. Quality inspectors label images of defects, about 5,000 new labels a week, and the model is retrained every week from them and pushed to the devices. The team is two ML engineers and one person who spends half their time on operations. The infrastructure budget is tight.

Alternatives

A1 · Managed training with staged releases

Keep classification and image queues on the line, use managed weekly retraining, and distribute compact signed models through staged pulls with rollback. This favors lower operating effort and controlled fleet updates, while retaining cost and timing validation as rollout gates.

Composed of 4 partial design points, one per ADR:

  • ADR1 · Quantized edge inference R1Q1Q2C2 Inference → Edge quantized inference
  • ADR2 · Sample into a durable local queue R3Q2 Image capture → Uncertainty and error sampling with durable local queue
  • ADR3 · Managed weekly pipeline with minimal artifact storage R2Q4C1 Training → Managed weekly retraining and model registryOperations → Minimal object-storage artifact service
  • ADR4 · Staged signed pulls with automatic rollback R2Q3C1C2 Rollout → Staged signed pull with automatic rollbackModel package → Compact hardware-specific signed model with enforced 200 ms release gate

As a whole: Devices run compact, hardware-specific signed models locally with quantized inference and a 200 ms release gate. They queue uncertain or erroneous samples durably, upload artifacts through minimal object storage, and support managed weekly retraining followed by staged signed deployment with automatic rollback.

D1 · Managed training with lightweight line agents

Use edge inference, durable sample queues, managed weekly training and compact signed models, with line agents pulling artifacts from minimal object storage and operators able to roll back. This keeps central platform scope small while retaining weekly pipeline and operator procedure work.

Composed of 4 partial design points, one per ADR:

  • ADR1 · Quantized edge inference R1Q1Q2C2 Inference → Edge quantized inference
  • ADR2 · Sample into a durable local queue R3Q2 Image capture → Uncertainty and error sampling with durable local queue

As a whole: Devices run a compact, hardware-specific signed model using quantized edge inference, while uncertainty and error cases are sampled into a durable local queue. A managed weekly pipeline retrains and registers models, stores artifacts in minimal object storage, and lets line agents pull releases with an operator rollback drill under 15 minutes.

ADR1 · Where should each part be classified? R1Q1Q2C2

Context. Inspection must keep pace with the line and continue through week-long network outages, while the existing ARM computers remain in place. Cloud inference centralizes compute but depends on a network round trip; edge inference requires a model that fits and runs fast enough on the installed accelerator.

Decision. Quantized edge inference (A1, D1).

Quantized edge inference chosen in A1, D1

Inference → Edge quantized inference

  • Inspection continues during network outages.
  • No image round trip is needed for each decision.
  • Latency and model compatibility on the actual accelerator must be measured.
  • Quantization may reduce accuracy.

All retained alternatives place inference beside the line so connectivity does not gate inspection.

Central cloud inference discarded

Inference → Cloud inference

  • Centralizes model execution and compute management.
  • Network latency and outages prevent the required line response and continuous inspection.

It misses the most constraining operating conditions and cannot be repaired within a centralized-inference approach.

ADR2 · Which images should be retained for labeling? R3Q2

Context. Inspectors need uncertain and incorrect cases, and disconnected plants must retain collected images until upload resumes. Sending every image increases network and storage demand; keeping no local durable buffer loses samples during outages.

Decision. Sample into a durable local queue (A1, D1).

Sample into a durable local queue chosen in A1, D1

Image capture → Uncertainty and error sampling with durable local queue

  • Captures useful labeling candidates while limiting upload volume.
  • Preserves samples through a network outage.
  • Requires queue capacity management and later upload monitoring.

It directly supports inspector labeling and deferred upload without relying on continuous connectivity.

Stream all images to the cloud discarded

Image capture → Stream every image to cloud

  • Provides a complete central image stream.
  • Consumes bandwidth and cannot transfer during outages.

The approach couples image collection to unreliable connectivity and misses the availability scenario.

ADR3 · How should weekly training and artifacts be operated? R2Q4C1

Context. New labels arrive each week, so training and artifact publication must recur weekly. Spending must stay below the stated cap and the small team has limited operations time. Managed services reduce maintenance but can accumulate charges; self-hosting gives control over the bill but requires support and reliability work.

Decision. Managed weekly pipeline with minimal artifact storage (A1, D1).

Managed weekly pipeline with minimal artifact storage chosen in A1, D1

Training → Managed weekly retraining and model registryOperations → Minimal object-storage artifact service

  • Automates the recurring training and registry work.
  • Limits the always-on service footprint.
  • End-to-end charges and glue work need a cost estimate and operating trial.

This combines managed recurring training with a narrow artifact service to balance staffing and spending.

Self-managed weekly pipeline on one small server discarded

Training → Self-hosted weekly training pipelineOperations → Single small self-managed cloud server

  • Can keep infrastructure charges predictable and compact.
  • The small team owns patching, monitoring, backups, and weekly pipeline recovery; the server is a single failure point.

It may constrain service charges, but its recurring server work violates the staffing constraint.

Federated weekly learning with managed coordination discarded

Training → Federated weekly learning across line devicesOperations → Managed federated learning coordination service

  • Can reduce routine transfer of imagery while learning from distributed samples.
  • Coordination, convergence, service cost, and fleet rollout remain unproven for the small team.

It adds coordination complexity without improving the edge alternatives on the stated requirements.

ADR4 · How should approved models reach lines and roll back? R2Q3C1C2

Context. Every connected line needs the approved model within 24 hours, and an operator must restore the previous model within 15 minutes without ML support. Updates must fit the unchanged edge computers. Automated staged deployment can improve repeatability but takes more implementation; a line agent can keep central infrastructure small but needs a reliable procedure.

Decision. Staged signed pulls with automatic rollback (A1); Line-agent pulls with rehearsed operator rollback (D1).

Staged signed pulls with automatic rollback chosen in A1

Rollout → Staged signed pull with automatic rollbackModel package → Compact hardware-specific signed model with enforced 200 ms release gate

  • Staging and automatic rollback can limit the effect of a bad release.
  • Compact signed artifacts suit the installed hardware.
  • The fleet automation must be built and tested; target timings still need measurement.

This maximizes release control for the managed pipeline while retaining hardware-specific packaging.

Line-agent pulls with operator rollback discarded

Rollout → Line-agent pull with operator rollback

  • Provides a direct operator rollback path with a lightweight deployment agent.
  • Compact signed artifacts suit the installed hardware.
  • Operator usability, polling cadence, and fleet-wide completion time need a plant trial.

A line agent is lightweight, but operator recovery still requires a proven procedure and the self-managed server approach was dropped for its staffing burden.

Line-agent pulls with rehearsed operator rollback chosen in D1

Rollout → Line-agent pull with operator rollback drill under 15 minutesModel package → Compact hardware-specific signed model

  • A recurring drill rehearses the 15-minute operator recovery target.
  • Compact signed artifacts suit the installed hardware.
  • The 24-hour fleet delivery target and agent support still need validation.

This retains a lightweight local agent while making the operator rollback procedure testable.

Federated line-agent update path discarded

Rollout → Line-agent pull with operator rollback

  • Retains a local operator rollback path.
  • Weekly federated update quality and deployment timing need validation.

It adds coordination work without improving the stated latency and availability profile.
