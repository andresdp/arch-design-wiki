Hosting an open-source monorepo

An open-source foundation hosts a 12-year, 40 GB monorepo with about 300 daily pushes and 2,000 contributors across five continents. Most clones come from CI and first-time contributors, who usually need only the latest version. Four volunteers operate donated servers in Europe and North America.

How to read this page

A coding agent explained an existing solution. It mapped the solution's choices onto decisions (dimensions) and their options (values), and tested which parts of the solution the requirements justify. It contrasted one value at a time to tell whether the requirements force that value or it was chosen freely. Every judgement here is the agent's; the page lays out its rationale file.

The solution

S · Monorepo hosting as built

A single European standard-Git origin accepts serialized pushes, with manual disk-copy failover. Regional caches and filtered sparse clones serve contributors, CI reads the origin, and bundles and release tarballs cover full-history and release downloads.

Composed of 5 partial design points, one per ADR:

  • ADR1 · Single European standard-Git origin R1Q2 Canonical origin → Single European originOrigin protocol → Standard Git protocolOrigin storage → Plain Git repository on local diskPush serialization → One push at a time
  • ADR2 · Blob filter and sparse checkout R2Q1 Contributor clone → Blob-filtered clone with sparse checkout
  • ADR3 · Regional caches with direct-origin CI Q1Q2 Clone distribution → Regional cachesCache freshness → Webhook-triggered fetch after each pushCI source → Origin directly
  • ADR4 · Manual disk-copy failover and mixed cache hosts C1 Failover → Manual takeover from block-level disk copyCache hosting → Donated North American server and rented Asia/South America VMs
  • ADR5 · Nightly bundles and CDN release tarballs R2 Full-history distribution → Nightly Git bundles from originRelease distribution → CDN source tarballs

As a whole: A single European plain Git repository is the standard Git origin, accepting one push at a time; CI reads it directly, with manual failover from a block-level disk copy. Regional caches on donated North American and rented Asia/South America hosts fetch after push webhooks; contributors use blob-filtered sparse clones, nightly bundles carry full history, and a CDN serves release tarballs.

ADR1 · Canonical maintainer push endpoint R1Q2

Context. Maintainers need one canonical repository that accepts standard Git pushes, and CI must be able to read every accepted push.

Decision. Single European standard-Git origin.

Single European standard-Git origin chosen

Canonical origin → Single European originOrigin protocol → Standard Git protocolOrigin storage → Plain Git repository on local diskPush serialization → One push at a time

“Maintainers push to one origin server in the European data centre.”
“It holds the repository as a plain Git repository on its local disk”
“and applies pushes one at a time.”
  • Meets the single canonical standard-Git push contract.
  • Provides one authoritative repository for CI reads.
  • Concentrates service capacity and availability in one origin.

The canonical endpoint and protocol are forced by R1. Local plain-Git storage and serialized pushes are free implementation choices.

Single origin with full-history clones discarded

Clone distribution → Single originContributor clone → Full-history clone

  • Keeps repository service centralized.
  • Requires downloading the full history, violating R2; a 40 GB transfer cannot meet Q1's two-minute target over 50 Mbit/s.

This contrast misses R2 and Q1.

ADR2 · Contributor checkout scope R2Q1

Context. First-time contributors should start without downloading the whole history, and the latest-version clone should be quick for distant users.

Decision. Blob filter and sparse checkout.

Blob filter and sparse checkout chosen

Contributor clone → Blob-filtered clone with sparse checkout

“The contributing guide tells first-time contributors to clone with a blob filter and a sparse checkout of the directories they work on.”
  • Avoids retrieving all file contents and materializes only selected directories.
  • Reduces initial transfer.
  • Omitted content may need later network fetches; the numeric latency target is unmeasured.

R2 requires avoiding a whole-history download, but does not force these specific mechanisms because a shallow clone also meets it.

Shallow clone of latest revision discarded

Contributor clone → Shallow clone of the latest revision

  • Avoids older history and can provide a complete checkout for the selected revision.
  • May transfer more current file content than a filtered sparse checkout.

It also meets R2, so requirements do not force the chosen option; there is no measured Q1 comparison.

ADR3 · Geographic clone service and CI freshness Q1Q2

Context. Contributors in Asia and South America need fast access, while CI must fetch the accepted push whenever it starts after acceptance.

Decision. Regional caches with direct-origin CI.

Regional caches with direct-origin CI chosen

Clone distribution → Regional cachesCache freshness → Webhook-triggered fetch after each pushCI source → Origin directly

“Cache servers in North America, Asia and South America serve clones and fetches.”
“After every push, the origin calls a webhook on each cache so that it fetches the new state, which usually takes a few seconds.”
“CI jobs are configured to fetch from the origin directly.”
  • Places clone service near contributors.
  • Direct origin fetch gives CI the accepted canonical state.
  • Cache refresh is asynchronous for ordinary clone users.
  • The two-minute target is not supported by measurements.

Regional caches are a plausible response to Q1. Direct-origin CI is forced by Q2 because caches can lag after an accepted push; webhook cache refresh is not forced.

Regional caches with cache-based CI discarded

Clone distribution → Regional cachesCache freshness → Eventual cache refreshCI source → Regional cache

  • Can reduce distance and origin load for CI fetches.
  • A CI job can start before the accepted push has propagated, violating Q2.

Eventual cache propagation misses Q2, so CI must fetch from the authoritative origin.

ADR4 · Failover and hosting operations C1

Context. Four volunteers operate the service in their spare time, with donated servers in two data centres. The solution describes failover and a mix of donated and rented cache hosts, but does not state an operational time budget or recovery target.

Decision. Manual disk-copy failover and mixed cache hosts.

Manual disk-copy failover and mixed cache hosts chosen

Failover → Manual takeover from block-level disk copyCache hosting → Donated North American server and rented Asia/South America VMs

“A second server in the same data centre receives a block-by-block copy of the origin's disk and can take over by hand if the origin fails.”
“The North American cache runs on a donated server; the other two run on small rented virtual machines.”
  • Uses the described donated infrastructure and keeps failover procedure manual.
  • Adds separate machines and manual recovery work; fit within volunteer spare time is unverified.

These choices are not forced by C1. The problem provides no workload or operations evidence to show this design meets the volunteer time constraint.

ADR5 · Additional full-history and release artifacts R2

Context. The requirements cover contributor onboarding, pushes, performance, consistency, and volunteer operation. They do not require full-history cache downloads or non-Git release artifacts.

Decision. Nightly bundles and CDN release tarballs.

Nightly bundles and CDN release tarballs chosen

Full-history distribution → Nightly Git bundles from originRelease distribution → CDN source tarballs

“Every night the origin also writes a Git bundle of the full history, which the caches offer for clones that need everything.”
“For every release tag, a script builds a source tarball and publishes it on a content delivery network, so that packagers download releases without using Git at all.”
  • Offers a full-history path and lets packagers download release archives without Git.
  • Adds scheduled bundle and release-publishing processes outside the stated requirements.

Both are free additions; no requirement forces them.

#2 A region of #1: part of the solution grounded

Thought R2 explains using blob filtering and sparse checkout because contributors can begin without retrieving the full history or materializing every file.

Move
  • Contributor clone → Blob-filtered clone with sparse checkout

Observed This region clearly meets the no-whole-history requirement. It helps the transfer-time target, although the exact two-minute bound is not evidenced. A shallow clone is another plausible way to omit history, so the solution's particular filter and sparse-worktree combination is not yet shown to be forced.

R2 meetsQ1 partly
  • Blob-filtered clone with sparse checkout: gains R2 gives up Q1: Omitting blobs and unrelated paths satisfies the no-whole-history requirement; the two-minute target remains unverified because transfer sizes and timings are absent.

A blob-filtered clone downloads repository structure and commits while omitting file contents until they are needed. Sparse checkout then materializes only the selected directories or files, giving contributors a focused working tree within the monorepo.

The point's trade-off This reduces initial bandwidth, disk usage, and checkout time, especially for contributors working on one area. It gives up immediate local access to omitted paths and may cause later network fetches or tooling limitations when commands require them.

#3 A contrast on #2: one option changed partial

Thought Test whether R2 forces blob filtering and sparse checkout over a shallow clone.

Move
  • change Contributor clone: Blob-filtered clone with sparse checkout → Shallow clone of the latest revision

Observed A shallow clone also omits older history while giving a complete working tree for its selected revision. It meets R2 and is also plausibly faster to transfer, so R2 does not force the chosen filtering and sparse-checkout details; those details are free choices. Neither option has measured evidence for the two-minute target.

R2 meetsQ1 partly
  • Shallow clone of the latest revision: gains R2 gives up Q1: A shallow clone avoids older history and meets R2, but unlike the chosen sparse checkout it may transfer all current file contents; that gives Q1 less support, with no measured time to establish the target.

Contributors clone the monorepo with only the latest revision, obtaining the current source without its earlier commit history. The hosting workflow therefore optimizes initial checkout for working on the present state.

The point's trade-off This reduces download size and clone time, but prevents contributors from inspecting older commits, traversing history, or using history-dependent debugging until they fetch more history.

#4 A region of #1: part of the solution grounded

Thought Q1 motivates regional caches; Q2 motivates sending CI directly to the canonical origin so an accepted push is visible immediately.

Move
  • Clone distribution → Regional caches
  • Cache freshness → Webhook-triggered fetch after each push
  • CI source → Origin directly

Observed The split between cached contributor traffic and direct CI traffic makes the consistency path independent of webhook timing. The regional placement is directionally supported by Q1, but its numeric target remains unproven.

Q1 partlyQ2 meets
  • Regional caches, Webhook-triggered fetch after each push, Origin directly: gains Q2 gives up Q1: Direct origin reads preserve freshness for CI, but that central route and the absent transfer measurements leave Q1's two-minute bound unverified despite nearby clone caches.

Regional cache nodes serve repository clones close to users. After each push, a webhook triggers those caches to fetch the updated repository, while CI checks out source directly from the origin.

The point's trade-off This reduces clone latency and distributes clone traffic, with cache updates initiated promptly after pushes. It leaves CI dependent on origin capacity and performance, and caches may briefly be stale if webhook delivery or fetching is delayed.

#5 A contrast on #4: one option changed ungrounded

Thought Test whether routing CI through a cache would preserve Q2 while retaining the latency benefits of regional distribution.

Move
  • change Cache freshness: Webhook-triggered fetch after each push → Eventual cache refresh
  • change CI source: Origin directly → Regional cache

Observed This contrast misses Q2 because eventual cache refresh does not guarantee that the accepted push has reached the cache before CI starts. Direct origin reads are therefore forced by Q2. The regional caches remain useful for contributor clone latency, while the two-minute bound still needs measurements.

Q1 partlyQ2 misses
  • Regional caches, Eventual cache refresh, Regional cache: gains Q1 gives up Q2: Regional reads can reduce fetch distance, but eventual propagation permits a CI job after an accepted push to read stale state.

Regional cache nodes serve clone requests near users, reducing dependence on the central repository. Cache contents refresh eventually, and CI checks out source from the regional cache rather than directly from the origin.

The point's trade-off This improves clone and CI-source latency and reduces origin load, but users and CI may temporarily receive stale repository contents after a change. It also makes correctness dependent on cache-refresh propagation across regions.

#6 A region of #1: part of the solution grounded

Thought R1 requires one canonical destination and standard Git push access; the local repository and serialized writes are implementation choices unless another stated requirement depends on them.

Move
  • Canonical origin → Single European origin
  • Origin protocol → Standard Git protocol
  • Origin storage → Plain Git repository on local disk
  • Push serialization → One push at a time

Observed R1 forces a canonical repository and standard Git protocol. Q2 is supported by having CI read the same origin that accepts pushes. No requirement distinguishes local plain Git storage or one-at-a-time application from alternatives; these are free choices. The text does not quantify their operational fit for four volunteers.

R1 meetsQ2 meetsC1 partly
  • Single European origin, Plain Git repository on local disk, One push at a time: gains R1, Q2 gives up C1: A single standard Git origin gives maintainers a clear push target and gives CI one authoritative state, while a single server and serialized writes concentrate capacity and operations on the volunteer-run service.

A single canonical Git repository is stored on local disk at an origin in Europe, with contributors accessing it through the standard Git protocol. The origin serializes pushes, applying one before accepting the next.

The point's trade-off This gains simple storage, broad Git compatibility, and predictable push consistency. It gives up geographic proximity for non-European contributors and push throughput under concurrent load, while the single origin concentrates availability risk.

Observed A full-history clone contradicts the request to let first-time contributors start without downloading the whole history. At 40 GB, transferring the complete repository over 50 Mbit/s cannot fit within two minutes even before protocol overhead. The solution's partial clone and regional serving choices are supported for these requirements, though the exact size of a latest-version filtered clone remains unspecified.

R2 missesQ1 misses

A single canonical origin hosts the monorepo, and contributors obtain it by cloning the repository’s complete history from that origin. All work can be based on the same centralized source while preserving every prior revision locally.

The point's trade-off This provides a simple source of truth and enables local history inspection and offline operations, but full-history clones consume more time, bandwidth, and storage, while the single origin becomes a central dependency and potential bottleneck.
