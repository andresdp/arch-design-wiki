Explain · design rationale · no design space

Card-fraud scoring service

A payments company scores every card transaction for fraud before it is authorized. It processes about 3,000 transactions per second on a normal day and up to five times as many during seasonal sales. Fraudsters adapt within weeks, and the confirmed fraud labels (chargebacks) arrive days to weeks after the transaction. Auditors and the card schemes can ask, months later, why a given transaction was scored the way it was. The ML team has five data scientists and two ML engineers. The company's operations team runs the data centres and the shared infrastructure, but there is no platform team for machine learning.

The solution

S · Fraud scoring as built

An on-premises streaming feature and synchronous model-scoring service with a rules fallback, retained score evidence, and a nightly human-reviewed model release process.

Composed of 5 partial design points, one per ADR:

  • ADR1 · Streaming aggregates in Redis R1Q1 Feature state → Streaming per-card aggregatesFeature store → Redis online aggregates
  • ADR2 · Synchronous model score with rules fallback R1Q1Q2 Scoring path → Synchronous REST on KubernetesFailure behavior → Rule-engine fallbackModel family → Gradient-boosted trees (XGBoost)
  • ADR3 · Return top features and retain complete score records R3Q3C1 Score explanation → Top three contributing featuresAudit record → Append-only full input and model logRetention → 13 months on-premises object storeModel management → MLflow registry
  • ADR4 · Nightly Airflow training with three-day shadow and manual promotion R2Q4C2 Retraining pipeline → Airflow nightly on 90 days of labelsExperiment and promotion → Three-day shadow and manual reviewModel management → MLflow registry
  • ADR5 · Grafana drift and fallback dashboards Q2Q4C2 Monitoring → Grafana score drift and fallback dashboards

As a whole: Streaming per-card aggregates are maintained in Redis and served to a synchronous REST scorer on Kubernetes, using an XGBoost model that returns a score and its top three contributing features. Failures invoke a rule engine; full inputs and model logs are appended to 13-month on-premises object storage, while Airflow retrains nightly on 90 days of labels, MLflow manages versions, three-day shadow/manual review controls promotion, and Grafana tracks drift and fallback use.

ADR1 · Maintain fresh online activity features R1Q1

Context. Each transaction must use the cardholder's recent activity before authorization. Seasonal throughput makes the feature read path latency-sensitive.

Decision. Streaming aggregates in Redis.

Streaming aggregates in Redis chosen

Feature state → Streaming per-card aggregatesFeature store → Redis online aggregates

“Flink jobs consume the topic and keep per-card aggregates (spend and counts over the last hour, day and week, and the number of distinct merchants) up to date in a Redis cluster.”
  • Keeps hour/day card aggregates current as events arrive.
  • Supports online reads for the transaction scoring path.
  • Depends on Redis availability and capacity.
  • The 30 ms peak p99 is not established by this design description.

Streaming is the better-supported match for per-transaction recent activity; Redis is a reasonable online store but its exact choice is free.

Batch recomputation discarded

Feature state → Batch recomputation of recent card aggregatesFeature store → Redis online aggregates

  • Can rebuild consistent aggregates and correct state.
  • Can serve stale features between runs and create periodic processing load.

It weakens the freshness required for recent activity and is less supportive of the low-latency scoring intent.

ADR2 · Score synchronously and preserve authorization continuity R1Q1Q2

Context. The score must be available before the authorization decision, while a scoring outage or timeout must not prevent authorization.

Decision. Synchronous model score with rules fallback.

Synchronous model score with rules fallback chosen

Scoring path → Synchronous REST on KubernetesFailure behavior → Rule-engine fallbackModel family → Gradient-boosted trees (XGBoost)

“The model is packaged in a container with a small Python REST service and runs on the company's Kubernetes cluster, with six replicas and autoscaling on CPU.”
“If the call times out or fails, the switch uses the existing rule engine for that transaction and logs that no score was used.”
“The model is a gradient-boosted tree model (XGBoost).”
  • Returns a model score on the authorization path.
  • A rules fallback lets authorization continue through scoring failures.
  • The synchronous dependency can add latency and capacity pressure.
  • Fallback decisions may provide weaker fraud detection.

Q2 forces a continuity path such as the rules fallback. Synchronous REST, Kubernetes, and XGBoost are implementation choices; the stated peak latency remains unverified.

Synchronous scoring with no fallback discarded

Scoring path → Synchronous REST on KubernetesFailure behavior → No fallback on scoring failureModel family → Gradient-boosted trees (XGBoost)

  • Every completed decision comes directly from the model path.
  • A service failure can stop the authorization flow.

It misses Q2, which forbids an authorization failure caused by scoring.

ADR3 · Keep score explanations and replay evidence R3Q3C1

Context. Months after a transaction, the team must identify the model and values used, and answer with training lineage within one working day while card data stays in the PCI environment.

Decision. Return top features and retain complete score records.

Return top features and retain complete score records chosen

Score explanation → Top three contributing featuresAudit record → Append-only full input and model logRetention → 13 months on-premises object storeModel management → MLflow registry

“The service returns, with every score, the three features that pushed the score up the most, which the dispute team uses to explain declines to cardholders.”
“Every score is written, with the model version and all input values, to an append-only table in the company's on-premises object store, kept for 13 months.”
“MLflow records the parameters, the metrics, the training data snapshot and the model artifact of every run, and holds the model registry.”
  • Complete score inputs and model version support replay and historical explanation.
  • Thirteen months covers the stated lookback.
  • Training snapshots and model artifacts preserve lineage.
  • Top features support dispute explanations.
  • Full input retention consumes storage and requires careful access governance.

The versioned input record, required retention and internal storage are forced by Q3 and C1. Top-feature output and MLflow are useful choices, but alternatives could satisfy the same requirements.

ADR4 · Retrain and compare candidate models R2Q4C2

Context. New confirmed cases must feed model updates, and a candidate must be compared on recent transactions and reach production within 48 hours. The seven-person team has no ML platform group.

Decision. Nightly Airflow training with three-day shadow and manual promotion.

Nightly Airflow training with three-day shadow and manual promotion chosen

Retraining pipeline → Airflow nightly on 90 days of labelsExperiment and promotion → Three-day shadow and manual reviewModel management → MLflow registry

“An Airflow pipeline retrains the model every night on the last 90 days of labelled transactions.”
“A new model first runs in shadow mode next to the production model for three days; the risk team reviews the comparison and promotes it by hand in MLflow.”
“MLflow records the parameters, the metrics, the training data snapshot and the model artifact of every run, and holds the model registry.”
  • Nightly jobs consume newly confirmed labels.
  • The shadow comparison and manual review limit exposure to a poor release.
  • The registry tracks parameters, snapshots and artifacts.
  • Three days in shadow exceeds the 48-hour deadline.
  • Nightly scheduling and manual review still use scarce staff time.
  • A fixed 90-day window may omit useful older patterns.

R2 supports regular retraining and Q4 supports comparison before promotion, but the chosen three-day duration is not forced and fails Q4. Airflow and MLflow are practical rather than mandatory tools.

One-day shadow with manual review discarded

Experiment and promotion → One-day shadow and manual reviewModel management → MLflow registry

  • Can compare the candidate with current production transactions within the 48-hour target.
  • Retains a human review gate and registry lineage.
  • Shorter observation gives less evidence about varied fraud patterns.
  • Manual review still consumes team time.

This shows that the three-day delay is not required by the comparison requirement; the requirements do not explain why the built system chose a delay that misses Q4.

ADR5 · Monitor drift and operational fallback Q2Q4C2

Context. Fraud patterns change and the shared operations team needs visibility into degraded scoring and changing score behavior.

Decision. Grafana drift and fallback dashboards.

Grafana drift and fallback dashboards chosen

Monitoring → Grafana score drift and fallback dashboards

“Grafana dashboards show the score distribution and the share of rule-engine fallbacks, and alert when the score distribution drifts from last month's.”
  • Shows fallback share and score distribution changes.
  • Alerts provide an operational signal for drift.
  • Drift alerts do not themselves retrain or validate a model.
  • Dashboards add operational ownership.

This supports responding to changing fraud and service health, though the monitoring tool and thresholds are free choices and do not alone satisfy Q4's release deadline.

#2 A region of #1: part of the solution grounded

Thought R1 calls for fresh per-card recent-activity features at scoring time, and Q1 favors keeping feature access fast.

Move

  • Feature store → Redis online aggregates

Observed The feature choices directly provide the recent hour/day activity R1 needs, and streaming state is more current than periodic recomputation. R1 meetsQ1 partly

The point's trade-off This provides fresh, low-latency feature access, but relies on Redis’s in-memory availability and operational capacity, with weaker durability or historical access than a persistent feature store.

#3 A region of #1: part of the solution grounded

Thought R1 and Q1 call for a prompt per-transaction score, while Q2 requires authorization to continue through scoring failures.

Move

  • Failure behavior → Rule-engine fallback
  • Model family → Gradient-boosted trees (XGBoost)

Observed The fallback is directly supported by Q2's explicit acceptance of weaker fraud detection during failures. The scoring architecture is plausible for synchronous decisions, but latency capacity at the seasonal peak remains unverified.

R1 meetsQ1 partlyQ2 meets
  • Synchronous REST on Kubernetes, Rule-engine fallback, Gradient-boosted trees (XGBoost): gains R1, Q2 gives up Q1: Synchronous serving makes the model result available before authorization and a rule fallback preserves continuity, but the request path adds a latency dependency and the 25 ms timeout does not itself establish a 30 ms p99 at peak.

A Kubernetes-hosted REST service synchronously receives each transaction and scores it with an XGBoost gradient-boosted-tree model before returning a result. If the model path fails or is unavailable, the service applies its rule-engine fallback and returns that decision instead.

The point's trade-off This combines immediate responses, flexible model-based scoring, and degraded-service operation, but synchronous serving can increase request latency or capacity pressure, while fallback decisions may be less accurate or consistent with the model.

#6 A contrast on #2: one option changed ungrounded

Thought Does R1 force streaming updates, or could periodically recomputed aggregates serve the recent-activity requirement?

Move
  • change Feature state: Streaming per-card aggregates → Batch recomputation of recent card aggregates

Observed Periodic recomputation can provide aggregates, but cannot ensure the freshest per-card state for every transaction and adds a stale interval before scoring. Streaming is therefore the better-supported choice for the recent-activity and low-latency intent. The exact p99 target remains unproven for either design.

R1 missesQ1 misses

A batch job periodically recomputes aggregates for recent card activity and writes the resulting values to Redis. The fraud-scoring service reads those Redis aggregates during online authorization decisions.

The point's trade-off This provides fast online access and allows aggregate correction or rebuilding through recomputation, but values can be stale between batch runs and recomputation may create periodic processing load.

#7 A contrast on #3: one option changed ungrounded

Thought Does Q2 force the rule-engine fallback when synchronous scoring fails?

Move
  • change Failure behavior: Rule-engine fallback → No fallback on scoring failure

Observed Without fallback, a service timeout or outage can stop authorization, which Q2 prohibits. The rule-engine fallback is forced by Q2, while its weaker fraud detection is an accepted degradation for a bounded interval.

Q2 misses

The service exposes a synchronous REST endpoint on Kubernetes, invokes an XGBoost model for each request, and returns the fraud score in the response. If scoring fails, the request fails rather than being handled by an alternate mechanism.

The point's trade-off This provides direct, consistent decisions from a deployable and potentially scalable model-serving path, but makes request latency and availability depend on the scoring service and model. With no fallback, transient failures can block transactions rather than allowing degraded processing.

#8 A contrast on #5: one option changed partial

Thought Does Q4 require the three-day shadow, or can comparison and manual review be completed with a one-day shadow?

Move
  • change Experiment and promotion: Three-day shadow and manual review → One-day shadow and manual review
  • drop Retraining pipeline (was Airflow nightly on 90 days of labels)

Observed The shorter shadow preserves a recent-transaction comparison and can meet the time bound, so the three-day duration is not forced by Q4. The requirements do not establish that one day supplies enough statistical confidence; the chosen three days may be a freely chosen caution, but it misses the explicit deadline.

Q4 meetsC2 partly
  • One-day shadow and manual review, MLflow registry: gains Q4 gives up C2: A one-day shadow plus review can complete comparison within 48 hours, though the manual gate still takes scarce team time and one day may provide less evidence.

The candidate model is registered and versioned in MLflow, then deployed for one day in shadow mode alongside the live fraud system. Its scores do not affect approvals or declines; reviewers inspect selected cases manually and use those observations to decide whether to promote the registered version.

The point's trade-off This reduces production risk and provides a controlled human check, while preserving model lineage. It gives up immediate automated impact and requires reviewer time; a single day may also provide limited evidence about behavior across varied fraud patterns.
