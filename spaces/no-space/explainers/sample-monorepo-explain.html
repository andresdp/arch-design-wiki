Hosting an open-source monorepo

An open-source foundation hosts a 12-year, 40 GB monorepo with about 300 pushes a day and 2,000 contributors across five continents. Most clones come from CI and first-time contributors. Four volunteers operate donated servers in Europe and North America.

The solution

S · Monorepo hosting as built

One European Git origin accepts writes and supplies CI; regional caches and filtered sparse clones support contributors, while volunteers operate a manual backup and supplementary distribution paths.

Composed of 3 partial design points, one per ADR:

  • ADR1 · Canonical origin with direct CI reads R1Q2 Write endpoint → One canonical origin in EuropeCI source → Origin directlyCache refresh → Origin webhooks after every push
  • ADR2 · Regional caches and filtered sparse checkout Q1R2 Read distribution → Caches in North America, Asia and South AmericaCache behavior → Serve present objects and forward misses to originContributor clone → Blob filter and sparse checkoutCache refresh → Origin webhooks after every pushFull-history clone → Nightly Git bundle served by cachesRelease distribution → Source tarball on CDN

As a whole: Contributors push to a single European origin, where serialized writes update a plain local Git repository; webhooks notify geographically distributed caches, which serve existing objects and forward misses. CI reads the origin, filtered sparse clones use it, nightly full-history bundles are cached, and source tarballs are delivered through the CDN; a same-datacentre block copy supports manual takeover.

ADR1 · Keep CI on the canonical write source R1Q2

Context. Maintainers need one canonical Git repository, and a CI job that starts after an accepted push must fetch that push. A regional cache can lag while its webhook-triggered fetch completes.

Decision. Canonical origin with direct CI reads.

Canonical origin with direct CI reads chosen

Write endpoint → One canonical origin in EuropeCI source → Origin directlyCache refresh → Origin webhooks after every push

“Maintainers push to one origin server in the European data centre.”
“CI jobs are configured to fetch from the origin directly.”
“After every push, the origin calls a webhook on each cache so that it fetches the new state, which usually takes a few seconds.”
  • CI reads the authoritative repository after a push.
  • The canonical write endpoint is clear.
  • CI and cache refresh traffic depend on the European origin.

Direct origin reads are forced by Q2 because asynchronous cache refresh can leave CI stale.

CI reads a regional cache discarded

Write endpoint → One canonical origin in EuropeCI source → Regional cacheCache refresh → Origin webhooks after every push

  • Can serve CI locally.
  • A job can start before the cache fetch finishes and miss the accepted push.

It misses Q2 during the webhook refresh interval.

ADR2 · Reduce distance and initial contributor transfer Q1R2

Context. The repository is 40 GB, and contributors in Asia and South America need a latest-version clone within two minutes on 50 Mbit/s while first-time contributors must start without downloading all history.

Decision. Regional caches and filtered sparse checkout.

Regional caches and filtered sparse checkout chosen

Read distribution → Caches in North America, Asia and South AmericaCache behavior → Serve present objects and forward misses to originContributor clone → Blob filter and sparse checkoutCache refresh → Origin webhooks after every pushFull-history clone → Nightly Git bundle served by cachesRelease distribution → Source tarball on CDN

“Cache servers in North America, Asia and South America serve clones and fetches.”
“Each cache serves the objects it has and forwards everything else to the origin.”
“The contributing guide tells first-time contributors to clone with a blob filter and a sparse checkout of the directories they work on.”
“After every push, the origin calls a webhook on each cache so that it fetches the new state, which usually takes a few seconds.”
“Every night the origin also writes a Git bundle of the full history, which the caches offer for clones that need everything.”
“For every release tag, a script builds a source tarball and publishes it on a content delivery network, so that packagers download releases without using Git at all.”
  • Regional objects reduce distance for cached reads.
  • Filtering and sparse checkout avoid an initial full-history download.
  • Nightly bundles offer a full-history path for users who need everything.
  • Release tarballs give packagers a Git-free download path.
  • Cache misses use the origin, and the measured two-minute target is not established.

The partial clone is forced by R2 and supports Q1; caches are a plausible regional aid, though the available evidence does not prove their necessity or verify the target. The bundle and release archive are supplementary paths; no stated requirement forces these details.

Regional caches with full-history clones discarded

Read distribution → Caches in North America, Asia and South AmericaCache behavior → Serve present objects and forward misses to originContributor clone → Full-history clone

  • Provides the complete history in one clone.
  • Transfers all 40 GB and defeats the requirement to start without downloading the whole history.

The contrast misses R2 and makes Q1 implausible.

Origin-only filtered sparse checkout discarded

Read distribution → Origin onlyCache behavior → Serve all objects from originContributor clone → Blob filter and sparse checkout

  • Still avoids a full-history initial transfer.
  • Remote reads have no regional object cache and put more load on the origin.

It meets R2 but has weaker support for Q1; available data do not quantify whether it would miss the target.

ADR3 · Use a modest origin and manual recovery C1R1

Context. Four volunteers operate the service in spare time, while maintainers need a canonical Git repository for pushes.

Decision. Local repository, serial writes and manual backup takeover.

Local repository, serial writes and manual backup takeover chosen

Repository storage → Plain Git repository on local diskWrite concurrency → Pushes applied one at a timeOrigin failover → Same-datacentre block copy with manual takeoverOperations model → Four volunteers using donated and small rented servers

“It holds the repository as a plain Git repository on its local disk”
“and applies pushes one at a time.”
“A second server in the same data centre receives a block-by-block copy of the origin's disk and can take over by hand if the origin fails.”
“The North American cache runs on a donated server; the other two run on small rented virtual machines.”
  • Uses a familiar Git repository and modest server arrangement.
  • A disk copy gives volunteers a takeover path.
  • Manual takeover needs volunteer attention and same-datacentre copies do not cover site-wide failure.

This is compatible with C1, but no requirement specifies recovery time, write throughput, or a required failover design, so the particular choices are not shown to be forced.

Thought The solution as one design point covers canonical writes, fast contributor reads, CI freshness and volunteer operation.

Observed The architecture directly serves the consistency requirement by having CI read the canonical origin. CI reads the origin, filtered sparse clones use it, nightly full-history bundles are cached, and source tarballs are delivered through the CDN; a same-datacentre block copy supports manual takeover.

The point's trade-off This provides simple consistency and inexpensive global reads and releases, but sacrifices write locality, automatic high availability, and fresh full-history bundles between nightly runs, while relying on volunteers for failover and operations.

#2 A region of #1: part of the solution grounded

Thought R1 and Q2 explain a single authoritative write endpoint and direct CI reads; webhooks keep distributed caches useful after pushes.

Move
  • Write endpoint → One canonical origin in Europe
  • CI source → Origin directly
  • Cache refresh → Origin webhooks after every push

Observed A CI cache contrast can improve locality but depends on webhook delivery and refresh completion. The solution avoids that freshness dependency for CI by reading the origin. Cache refresh can help later regional reads, though it does not prove Q1's latency target.

R1 meetsQ2 meetsQ1 partly
  • One canonical origin in Europe: gains Q2 gives up Q1: The origin guarantees CI freshness, while an uncached object requested from Asia or South America still depends on a distant origin.

The monorepo is written to one canonical origin located in Europe. CI reads directly from that origin, and after every push, origin webhooks trigger cache refreshes.

The point's trade-off This provides a single authoritative source, immediate CI access to the latest changes, and prompt cache updates. It gives up geographic locality and resilience, while CI and cache-refresh traffic depend on the European origin and may incur cross-region latency.

#3 A contrast on #2: one option changed ungrounded

Thought If CI reads the regional cache, Q2 may be missed while refresh is still pending.

Move
  • change CI source: Origin directly → Regional cache

Observed The description says cache refresh usually takes a few seconds, so a CI job starting during that interval can miss the accepted push. Direct origin reads are forced by Q2; the source text does not establish a quantitative latency penalty for CI.

R1 meetsQ2 missesQ1 partly

All writes go to one canonical origin in Europe, which emits a webhook after each push. The webhook refreshes the regional cache, and CI jobs use that cache as their source.

The point's trade-off This provides a single authoritative write location while potentially improving CI access through regional copies. It gives up geographically local writes and makes cache freshness depend on webhook delivery and refresh completion.

#4 A region of #1: part of the solution partial

Thought Q1 and R2 explain regional object caches and a partial working clone for first-time contributors.

Move

  • Cache behavior → Serve present objects and forward misses to origin
  • Contributor clone → Blob filter and sparse checkout

Observed This combination directly addresses both distant access and avoiding a full-history download. It is supported by the 40 GB repository and the guide's recommendation, but the two-minute threshold remains unverified because clone timings are not supplied.

Q1 partlyR2 meets

Regional caches in North America, Asia, and South America serve Git objects already present locally, while forwarding cache misses to the origin. Contributors use a blob filter and sparse checkout to clone only selected repository content and avoid downloading unnecessary blobs.

The point's trade-off This reduces latency for repeated regional access and lowers contributors’ download and storage needs. It gives up immediate cache availability for uncached objects and may require additional fetches when contributors later need omitted files or blobs.

#5 A contrast on #4: one option changed ungrounded

Thought A full-history first clone is likely to undermine the time and download reduction sought by Q1 and R2.

Move
  • change Contributor clone: Blob filter and sparse checkout → Full-history clone

Observed The contrast removes the partial-clone benefit and requires all history; the repository size makes the two-minute target implausible on a 50 Mbit/s link. Blob filtering and sparse checkout are forced by R2 and materially support Q1.

Q1 missesR2 misses

Regional caches in North America, Asia, and South America serve repository objects already stored locally, while requests for missing objects are forwarded to the origin. Contributors perform full-history clones through these caches, retrieving every required historical object regardless of whether it is cached.

The point's trade-off This improves latency for repeated reads and reduces origin traffic across regions, but cache misses still depend on the origin. Full-history clones also require transferring and storing substantially more data than shallow clones.

#6 A contrast on #4: one option changed partial

Thought Without regional caches, the partial clone may still reduce transfer size but remote object fetches use the distant origin.

Move
  • change Read distribution: Caches in North America, Asia and South America → Origin only
  • change Cache behavior: Serve present objects and forward misses to origin → Serve all objects from origin

Observed Filtering alone satisfies the no-whole-history behavior. The contrast weakens the geographic latency case, but available facts do not give timings that prove regional caches are necessary for the two-minute target; cache distribution is supported, not conclusively forced.

Q1 partlyR2 meets
  • Origin only, Serve all objects from origin, Blob filter and sparse checkout: gains R2 gives up Q1: Filtering lets a contributor start without full history, while distant origin reads and greater origin load weaken the latency case.

The monorepo is hosted and read exclusively from its origin, with every object served directly rather than through replicas or caches. Contributors clone it using blob filtering and sparse checkout, downloading only selected history content and working-tree paths initially.

The point's trade-off This minimizes contributor download and local storage requirements while keeping distribution simple. It increases origin bandwidth and load, and contributors may experience slower access or need to fetch omitted blobs and paths later.

#7 A region of #1: part of the solution partial

Thought C1 explains using a modest, familiar repository service and manual failover that volunteers can operate.

Move
  • Repository storage → Plain Git repository on local disk
  • Write concurrency → Pushes applied one at a time
  • Origin failover → Same-datacentre block copy with manual takeover
  • Operations model → Four volunteers using donated and small rented servers

Observed The ordinary Git repository and serialized updates are compatible with a small volunteer team and canonical pushes. Manual takeover avoids a larger automated failover system but the solution gives no staffing schedule or recovery target, so C1 is supported rather than fully demonstrated.

C1 partlyR1 meets
  • Plain Git repository on local disk, Pushes applied one at a time, Same-datacentre block copy with manual takeover: gains R1 gives up C1: A plain canonical Git origin supports maintainer pushes, while manual recovery adds volunteer work and offers limited site-level protection.

A bare Git repository on local disk accepts pushes through a single serialized writer, avoiding concurrent repository updates. Its storage is copied at the block level to another server in the same datacentre, with the volunteers manually promoting that copy if the origin fails.

The point's trade-off This is inexpensive and relatively simple to operate with modest hardware, but serialized pushes limit write throughput. Same-datacentre replication and manual takeover leave the service exposed to site-wide failures and slower recovery, while relying on four volunteers limits operational coverage.
