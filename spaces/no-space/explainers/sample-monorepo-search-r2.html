Hosting an open-source monorepo

An open-source foundation hosts a 12-year, 40 GB monorepo with about 300 pushes a day and 2,000 contributors on five continents. Most clones come from CI and first-time contributors who need the latest version. Four volunteers run the service on donated servers in Europe and North America.

How to read this page

A coding agent searched for designs that solve this problem. It combined decisions (dimensions) and their options (values) into design points, and judged each point against every requirement: meets, partly or misses. It proposes 3 alternatives. Every judgement here is the agent's; the page lays out its rationale file.

  • Decisions (ADRs) lists the alternatives, then one record per decision: the requirements that drive it, and every option weighed, with its pros and cons, chosen by an alternative or discarded.
  • Comparison puts the alternatives side by side, with the rows where they differ first.
  • Trajectory shows how the agent got there:
    • the lanes show each approach round by round, with every point coloured strong, mixed or weak;
    • a strip shows how each point met each requirement;
    • the story gives each point's thought, change, observation and trade-offs.

No design space was used. The agent named the decisions and options itself, so nothing was checked against a space and there are no gaps in one.

Alternatives

A1 · Primary with ordered CI reads

Keep one canonical primary, shallow filtered clones, and CI reads gated on push completion. This is the simplest operational option; two-minute clone performance remains to be measured.

Composed of 4 partial design points, one per ADR:

  • ADR1 · One canonical primary R1Q2 Write authority → Single canonical primary
  • ADR2 · Primary read after push completion Q2 Read freshness → CI uses primary with push-completion barrier
  • ADR3 · Shallow filtered clones from origins R2Q1 Clone transfer → Shallow clone with blob filtering
  • ADR4 · Two data-centre origins Q1C1 Serving topology → Two data-centre origins

As a whole: All writes go to a single canonical primary. Repository clients are served by two data-centre origins using shallow clones with blob filtering, while CI uses the primary only after a push-completion barrier.

B1 · Regional replicas with safe fallback

Use one primary and two read replicas for regional shallow clones, routing reads to the primary until replicas catch up. This improves locality while preserving a single write authority, at the cost of replica operations.

Composed of 4 partial design points, one per ADR:

  • ADR1 · One canonical primary R1Q2 Write authority → Single canonical primary
  • ADR2 · Primary fallback until replica catches up Q2 Read freshness → Primary fallback until replica catches up
  • ADR3 · Regional shallow clones R2Q1 Clone transfer → Shallow clone from regional read replicas
  • ADR4 · Two synchronized replicas Q1C1 Serving topology → Two data-centre replicas

As a whole: A single canonical primary accepts all writes, while two replicas in separate data centres serve reads. Users can make shallow clones from a nearby regional replica, with reads falling back to the primary until that replica catches up.

D1 · CDN snapshots with primary CI

Publish immutable shallow snapshots through a CDN and two origins, while CI fetches from the primary after a push-completion barrier. This can distribute clone traffic globally but adds snapshot operations.

Composed of 4 partial design points, one per ADR:

  • ADR1 · One canonical primary R1Q2 Write authority → Single canonical primary
  • ADR2 · Primary read after push completion Q2 Read freshness → CI uses primary with push-completion barrier
  • ADR3 · Immutable shallow snapshots at CDN R2Q1 Clone transfer → Immutable shallow snapshots at CDN
  • ADR4 · Snapshot CDN and two origins Q1C1 Serving topology → Snapshot CDN plus two origins

As a whole: A single primary accepts all writes, while CI reads from it only after the push-completion barrier. Immutable shallow snapshots are published to a CDN backed by two origins, allowing repository consumers to fetch consistent snapshots without querying the primary.

ADR1 · Where do maintainer pushes become canonical? R1Q2

Context. Maintainers need a standard Git push target that is unambiguously canonical. CI must fetch the push after it is accepted. Multiple writable sites add coordination burden and risk stale reads, while one primary can bottleneck and become a failure dependency.

Decision. One canonical primary (A1, B1, D1).

One canonical primary chosen in A1, B1, D1

Write authority → Single canonical primary

  • Matches the single canonical repository requirement.
  • Gives CI a clear authoritative source.
  • The primary is a write and CI dependency.

All live alternatives preserve a single standard Git push destination.

Federated writable replicas discarded

Write authority → Federated writable replicas

  • Can accept writes near contributors.
  • Does not provide a single canonical write authority and async copies can be stale.

It fails the canonical repository and post-push freshness requirements.

ADR2 · How are post-push CI reads kept current? Q2

Context. Every CI job starting after an accepted push must fetch that push. Direct reads from the primary provide a clear source; barriers make ordering explicit. Replicas can reduce read distance, but their lag must be handled, and synchronous replication can increase push latency and reduce availability.

Decision. Primary read after push completion (A1, D1); Primary fallback until replica catches up (B1).

Primary read after push completion chosen in A1, D1

Read freshness → CI uses primary with push-completion barrier

  • Makes post-acceptance ordering explicit.
  • Avoids stale cache and replica reads for CI.
  • CI depends on primary availability.

The barrier directly enforces the required read-after-accepted-push behavior.

Primary reads discarded

Read freshness → CI fetches from primary

  • Reads the authoritative repository.
  • The ordering guarantee depends on push visibility and job scheduling semantics.

Direct primary reads are sound, but the barrier states the required ordering more precisely.

Primary fallback until replica catches up chosen in B1

Read freshness → Primary fallback until replica catches up

  • Avoids serving a known stale replica result.
  • Requires lag detection and fallback routing.

This permits regional reads while protecting CI freshness during replication lag.

Synchronous replication before acceptance discarded

Read freshness → Synchronous replication before push acceptance

  • Replicas contain accepted pushes before acknowledgement.
  • Remote site failures or latency can block pushes.

The stronger coupling is not justified for four spare-time operators when primary fallback can protect reads.

Asynchronous replication and cache invalidation discarded

Read freshness → Asynchronous replication with cache invalidation

  • Does not wait for remote replication.
  • Cannot guarantee a CI fetch always sees an accepted push.

Eventual propagation misses the consistency requirement.

ADR3 · How should first clones reach distant contributors? R2Q1

Context. First-time contributors need to start without downloading 12 years of history, and distant users have a two-minute clone target. Shallow transfer reduces history; filtering and snapshots can reduce or distribute bytes. The current checkout size and server measurements are absent, so no option proves the time target. Additional replica and CDN paths add operations for the volunteer team.

Decision. Shallow filtered clones from origins (A1); Regional shallow clones (B1); Immutable shallow snapshots at CDN (D1).

Shallow filtered clones from origins chosen in A1

Clone transfer → Shallow clone with blob filtering

  • Avoids full history and unnecessary blob transfer.
  • Checkout still needs required current blobs, and the time target is unmeasured.

It supports quick starts with the fewest additional systems.

Regional shallow clones chosen in B1

Clone transfer → Shallow clone from regional read replicas

  • Combines reduced history with regional serving.
  • Replica lag and operations require monitoring.

It favors regional clone performance while preserving safe fallback behavior.

Immutable shallow snapshots at CDN chosen in D1

Clone transfer → Immutable shallow snapshots at CDN

  • Edge distribution can reduce distant transfer latency.
  • Snapshot publication and cache management add volunteer work and can lag the primary.

It offers the strongest geographic distribution path while keeping CI on the primary.

CDN source snapshots with federation discarded

Clone transfer → CDN-hosted source snapshots

  • Can distribute source near global users.
  • The surrounding federated asynchronous design cannot ensure current content.

Its freshness and operating model do not satisfy the problem.

ADR4 · How much read serving infrastructure should volunteers operate? Q1C1

Context. The service runs on donated machines in two regions and only four volunteers are available. A small origin setup is easier to operate, while replicas or a CDN can improve geographic delivery but require monitoring, synchronization, and recovery procedures. Performance improvements remain hypotheses until measured.

Decision. Two data-centre origins (A1); Two synchronized replicas (B1); Snapshot CDN and two origins (D1).

Two data-centre origins chosen in A1

Serving topology → Two data-centre origins

  • Uses the two existing sites with limited added machinery.
  • Distant contributors may see higher latency.

This keeps operations small while supporting two origin locations.

Two synchronized replicas chosen in B1

Serving topology → Two data-centre replicas

  • Enables regional reads and source redundancy.
  • Adds replication, monitoring, and recovery responsibilities.

It supports regional clones, with primary fallback guarding against lag.

Snapshot CDN and two origins chosen in D1

Serving topology → Snapshot CDN plus two origins

  • Can serve distant clones from a nearby edge.
  • Requires snapshot publication and cache operations.

It targets global clone distribution while maintaining origin backends.

Global edge cache with federated writes discarded

Serving topology → Global edge cache

  • Can place data near contributors.
  • Does not address canonical writes or strict freshness and expands operations.

Its global footprint and federation add complexity while missing Q2.

Round 1 · 3 points: seed A, seed B, seed C
#1 Seed of approach A strong

Thought A single push authority and direct CI reads should meet R1 and Q2; shallow filtered clones should help R2 and Q1 with low operational burden for C1.

Move
  • Write authority → Single canonical primary
  • Clone transfer → Shallow clone with blob filtering
  • Read freshness → CI fetches from primary
  • Serving topology → Two data-centre origins

Observed Shallow filtered transfer avoids full history and primary reads give CI a fresh source. No repository-size or Asia/South America latency measurements prove the two-minute target.

R1 meetsR2 meetsQ1 partlyQ2 meetsC1 meets
  • Shallow clone with blob filtering: gains R2 gives up Q1: Shallow filtered transfer avoids full history, but checkout still needs current blobs and can leave a large transfer on the path; the two-minute threshold remains unproven.

A single canonical primary accepts all writes. Two data-centre origins serve repository data, while CI fetches directly from the primary for current results and consumers obtain shallow clones with filtered blobs.

The point's trade-off This provides a consistent write source, fresh CI inputs, and geographically distributed serving, but sacrifices complete local history and unfiltered blob availability; the second origin must also stay synchronized rather than accept authoritative writes.

#2 Seed of approach B mixed

Thought Synchronous mirroring should preserve Q2 and improve durability while regional shallow clones help Q1 and R2; operating a replica pair may strain C1.

Move
  • Write authority → Single canonical primary
  • Clone transfer → Shallow clone from regional read replicas
  • Read freshness → Synchronous replication before push acceptance
  • Serving topology → Two data-centre replicas

Observed Synchronous replication provides a strong ordering rule, but it couples push availability to the donated second site. Regional delivery helps performance without evidence that the target is achieved.

R1 meetsR2 meetsQ1 partlyQ2 meetsC1 partly
  • Synchronous replication before push acceptance: gains Q2 gives up C1: Waiting for the remote replica before acknowledging pushes strengthens read freshness but adds failure handling and cross-site operations for the volunteers.
  • Shallow clone from regional read replicas: gains R2 gives up Q1: Regional shallow transfer reduces history and distance, but checkout still needs current blobs and the timing target is unmeasured.

A single canonical primary accepts all writes and waits for synchronous replication to the other data-centre replica before accepting a push. Regional read replicas serve shallow clone requests, reducing transfer size while keeping clone traffic close to users.

The point's trade-off This provides a clear write authority, strong push durability, and efficient regional cloning. It sacrifices write latency and availability when synchronous replication or the primary is unavailable, and shallow clones provide less history locally.

#3 Seed of approach C weak

Thought Federated writes and a global edge cache could improve geographical access and availability, but asynchronous propagation may undermine Q2 and complexity may violate C1.

Move
  • Write authority → Federated writable replicas
  • Clone transfer → CDN-hosted source snapshots
  • Read freshness → Asynchronous replication with cache invalidation
  • Serving topology → Global edge cache

Observed Cache invalidation cannot prove every CI fetch sees an accepted push if propagation is asynchronous. This approach also adds coordination work and has no single canonical write authority.

R1 missesR2 meetsQ1 partlyQ2 missesC1 misses
  • Federated writable replicas, Asynchronous replication with cache invalidation: gains Q1, R2 gives up R1, Q2: Local writes and edge delivery favor geographic speed, but independent writable copies conflict with a single canonical repository and asynchronous propagation cannot guarantee post-acceptance CI freshness; coordination adds volunteer burden.

Writes can be accepted by federated replicas, with updates propagated asynchronously and cache invalidation signaling freshness changes. Clones are delivered as source snapshots through a CDN, while a global edge cache serves ordinary reads close to users.

The point's trade-off This improves geographic performance, clone distribution, and write availability, but sacrifices immediate consistency: replicas, snapshots, and edge caches may temporarily be stale. It also makes replica coordination and cache invalidation operationally complex.

#4 Refined #1 (approach A) strong → A1

Thought Adding an explicit push-completion barrier should make the read-after-acceptance ordering unambiguous for Q2 without adding replica operations.

Move
  • change Read freshness: CI fetches from primary → CI uses primary with push-completion barrier

Observed The barrier makes the consistency guarantee explicit while keeping a low-complexity single write path. The two-minute clone target remains dependent on measured current-tree size and network conditions.

R1 meetsR2 meetsQ1 partlyQ2 meetsC1 meets
  • Shallow clone with blob filtering: gains R2 gives up Q1: The filtered shallow transfer helps quick starts, while the time threshold remains unmeasured.

All writes go to a single canonical primary. Repository clients are served by two data-centre origins using shallow clones with blob filtering, while CI uses the primary only after a push-completion barrier.

The point's trade-off This reduces clone transfer and prevents CI from observing an incomplete push, while the two origins provide serving-path redundancy. It gives up complete local history and readily available blobs, and the single primary remains a write bottleneck or failure point.

#5 Refined #2 (approach B) mixed

Thought Using filtered shallow clones with synchronous replication should lower transfer size while preserving replica freshness, improving Q1 and retaining Q2.

Move
  • change Clone transfer: Shallow clone from regional read replicas → Shallow clone with blob filtering

Observed Filtering improves the transfer strategy but cannot remove the operational cost and availability coupling of synchronous writes.

R1 meetsR2 meetsQ1 partlyQ2 meetsC1 partly
  • Synchronous replication before push acceptance: gains Q2 gives up C1: Synchronous cross-site acknowledgement is a direct freshness mechanism but raises operating and availability burden.
  • Shallow clone with blob filtering: gains R2 gives up Q1: Filtered shallow transfer limits history and unnecessary blobs; current tree transfer performance still needs measurement.

A single canonical primary accepts writes and synchronously replicates each accepted push to the second data-centre replica before reporting success. Clients receive shallow clones with blob filtering, while reads can be served from either replica after replication completes.

The point's trade-off This provides a clear write authority, strongly fresh replicas, and reduced clone transfer costs. It gives up write availability and latency when the primary or synchronous replica is unavailable, and shallow/blob-filtered clones may lack history or blobs needed later.

#6 New approach D mixed

Thought Immutable shallow snapshots at an edge cache may improve distant clone performance while direct CI reads preserve Q2; publication lag could leave ordinary contributors behind.

Move
  • Write authority → Single canonical primary
  • Clone transfer → Immutable shallow snapshots at CDN
  • Read freshness → CI fetches from primary
  • Serving topology → Snapshot CDN plus two origins

Observed The edge distribution addresses geography without making CI depend on cache freshness. It creates an extra publication path and still cannot establish the two-minute target from the supplied facts.

R1 meetsR2 meetsQ1 partlyQ2 meetsC1 partly
  • Immutable shallow snapshots at CDN: gains R2, Q1 gives up C1: Snapshots can reduce distant transfer latency, but snapshot generation, publication, and CDN invalidation add moving parts for volunteers; timing remains unmeasured.

A single canonical primary accepts all writes and produces immutable shallow snapshots that are distributed through a CDN backed by two origins. CI bypasses snapshots and fetches directly from the primary, while other consumers are served through the snapshot CDN.

The point's trade-off This provides authoritative writes, resilient and scalable snapshot delivery, and fresh CI inputs. It gives up deep clone history and may expose snapshot consumers to publication lag; the primary remains a dependency for CI and writes.

Round 3 · 3 points: refine A, refine B, refine D
#7 Refined #4 (approach A) mixed

Thought Adding replicas for clone reads while retaining primary fallback until catch-up should avoid stale fetches and reduce load on the primary when replicas are current.

Move
  • change Read freshness: CI uses primary with push-completion barrier → Primary fallback until replica catches up
  • change Serving topology: Two data-centre origins → Two data-centre replicas

Observed Fallback gives a clear safe read policy during lag, though it requires reliable lag detection and increases operational work over the primary-only approach. Clone timing remains unmeasured.

R1 meetsR2 meetsQ1 partlyQ2 meetsC1 partly
  • Two data-centre replicas, Primary fallback until replica catches up: gains Q1, Q2 gives up C1: Regional replicas can improve read locality and fallback protects freshness, but replica monitoring and recovery add volunteer operations.

All writes go to one canonical primary, while two data-centre replicas receive its data. Clients use shallow clones with blob filtering, and reads stay on the primary until a replica catches up, after which replicas can serve them.

The point's trade-off This provides simple write authority, lower clone-transfer cost, and protection from stale reads, while adding geographic redundancy. It gives up write scalability and may increase primary load or read latency during replication lag; filtered shallow clones provide less history or content.

#8 Refined #5 (approach B) mixed → B1

Thought Replacing synchronous replication with primary fallback during lag can reduce push coupling while regional shallow clones retain locality and the fallback maintains Q2.

Move
  • change Clone transfer: Shallow clone with blob filtering → Shallow clone from regional read replicas
  • change Read freshness: Synchronous replication before push acceptance → Primary fallback until replica catches up

Observed Serving reads regionally while falling back to the primary avoids synchronous push latency and stale replica reads, but still requires replica health and lag monitoring.

R1 meetsR2 meetsQ1 partlyQ2 meetsC1 partly
  • Primary fallback until replica catches up: gains Q2 gives up C1: Fallback avoids blocking push acceptance on remote replication while preserving current reads, though monitoring and routing still have an operating cost.
  • Shallow clone from regional read replicas: gains R2 gives up Q1: Regional shallow clones reduce history and distance; measured clone time is still needed.

A single canonical primary accepts all writes, while two replicas in separate data centres serve reads. Users can make shallow clones from a nearby regional replica, with reads falling back to the primary until that replica catches up.

The point's trade-off This reduces clone transfer cost and regional read latency while preserving a clear write authority. It gives up geographically distributed write capacity and may expose the primary to read load during replica lag or failures.

#9 Refined #6 (approach D) mixed → D1

Thought An explicit post-push barrier should strengthen CI freshness while CDN snapshots serve ordinary clones independently of CI reads.

Move
  • change Read freshness: CI fetches from primary → CI uses primary with push-completion barrier

Observed Separating CI's primary read path from snapshots removes cache freshness from the CI guarantee. The CDN still adds operational work, and the performance scenario needs an end-to-end measurement.

R1 meetsR2 meetsQ1 partlyQ2 meetsC1 partly
  • Immutable shallow snapshots at CDN: gains R2, Q1 gives up C1: The CDN improves geographic distribution but snapshot publication and cache operations add volunteer burden; the timing goal is unmeasured.

A single primary accepts all writes, while CI reads from it only after the push-completion barrier. Immutable shallow snapshots are published to a CDN backed by two origins, allowing repository consumers to fetch consistent snapshots without querying the primary.

The point's trade-off This provides centralized write authority, predictable post-push CI freshness, cacheable distribution, and origin redundancy. It gives up mutable or complete clone history at the edge, and snapshot publication can leave consumers temporarily behind the latest primary state.
