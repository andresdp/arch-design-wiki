Support-ticket routing

A software company receives about 20,000 support tickets a day in English, Spanish and Portuguese, through e-mail and a web form. Tickets must reach one of 25 teams. First-line staff currently forward tickets by hand, and a misrouted ticket waits a day on average. Products and support teams change a few times a year.

The solution

S · Ticket routing as built

A webhook-driven multilingual classifier assigns teams, captures corrections, retrains weekly from final-team labels, and uses lead-written rules for new-team cold starts. It runs in the EU and rolls accepted model files out quickly.

As a whole: Tickets arrive via the help-desk webhook, with recent same-customer/subject duplicates attached to the earlier ticket. Remaining tickets use fixed multilingual embeddings and one-class-per-team logistic regression; corrections feed weekly 90-day retraining, accepted models load from object storage into two EU Kubernetes replicas, and new teams initially use lead-written keyword rules while monitoring tracks moved-ticket shares.

ADR1 · Build an agent-correctable multilingual assignment path R1

Context. Tickets need a team assignment and agents need a way to correct mistakes. The stated intake covers a multilingual service, and the tool can show agents the basis and alternatives for a decision.

Decision. Webhook, multilingual embedding classifier, and agent correction.

Webhook, multilingual embedding classifier, and agent correction chosen

Ticket intake → Help desk webhookDuplicate handling → Same customer and subject within one hour attaches to earlier ticketText representation → Pretrained multilingual sentence embeddingsClassifier → Logistic regression with one class per teamAgent correction → Help desk records agent-selected teamAgent explanation → Show two runner-up teams and influential words

“The help desk tool sends every new ticket to the routing service through a webhook.”
“It first looks for duplicates: if the same customer sent a ticket with the same subject in the last hour, the service attaches the new ticket to the earlier one and does not classify it.”
“Otherwise the service turns the subject and the body into an embedding with a pretrained multilingual sentence-embedding model”
“and a logistic-regression classifier with one class per team picks the team.”
“When an agent moves a ticket, the help desk tool records the new team.”
“The service writes the team back to the help desk tool, with the two runner-up teams and the words that weighed most in the decision, which the tool shows to agents next to the ticket.”
  • Provides a concrete assignment path for multiple languages.
  • Records agent corrections for subsequent use.
  • Runner-up teams and influential words give agents context.
  • The duplicate rule may attach a distinct issue to an earlier ticket.
  • The solution does not provide evidence that the displayed words explain the embedding-based classification.

The assignment and correction functions directly answer R1. The specific webhook, representation, classifier, duplicate rule, and display choices are not shown to be forced.

ADR2 · Keep the service inside the EU region C1Q1

Context. Tickets can contain personal data and must remain in the company's EU cloud region. The service also has a stated peak-load latency target.

Decision. Two managed Kubernetes replicas behind a load balancer in the EU.

Two managed Kubernetes replicas behind a load balancer in the EU chosen

Runtime → Managed Kubernetes in EU region with two replicas behind load balancer

“The service runs on a managed Kubernetes cluster in the company's EU cloud region, with two replicas behind a load balancer.”
  • The service runs in the required EU region.
  • The load balancer distributes requests and replicas provide basic failover.
  • The target of 3,000 tickets an hour within 10 seconds has no stated capacity test or measurement.
  • Two replicas do not protect against a region-wide outage.

The EU location is forced by C1. Managed Kubernetes and two replicas are free implementation choices on the supplied evidence; their support for Q1 is plausible but unverified.

ADR3 · Turn agent moves into accepted classifier updates R2Q2

Context. Agent moves must inform learning. New products and teams arrive, so training and deployment need to make updated routing available, while new-team performance is important.

Decision. Weekly retraining with a recent-accuracy gate and rapid model loading.

Weekly retraining with a recent-accuracy gate and rapid model loading chosen

Agent correction → Help desk records agent-selected teamFeedback training → Weekly Sunday retraining on last 90 days of final-team ticketsEvaluation gate → Replace model if last-week accuracy is at least current modelEmbedding lifecycle → Embedding model remains fixedModel distribution → Model file in object storage, loaded within five minutesMonitoring → Per-team moved-ticket share with alert when share doubles week over week

“When an agent moves a ticket, the help desk tool records the new team.”
“Every Sunday a scheduled job exports the tickets of the last 90 days with their final teams, retrains the classifier”
“and evaluates it on the last week's tickets. If it is at least as accurate as the current model, the job replaces the model file in object storage”
“(the embedding model is never retrained)”
“the job replaces the model file in object storage, and the service loads the new file within five minutes.”
“A dashboard shows, per team, the share of tickets that agents moved, and sends an alert when that share doubles from one week to the next.”
  • Uses final-team labels from agent corrections for classifier retraining.
  • Checks candidate accuracy before replacing the current model.
  • Loads an accepted model within five minutes and monitors moved-ticket shares.
  • Retraining is weekly and the embedding model is fixed.
  • A last-week accuracy comparison does not establish the performance of a new team.
  • No measured Q2 result is supplied.

Recording and using agent moves fulfills R2. Weekly cadence, the 90-day window, aggregate gate, fixed embeddings, and distribution mechanism are implementation choices; they do not prove Q2, so they are not established as forced by its numerical target.

ADR4 · Provide a rule-based route before new-team examples exist Q2

Context. A new team has no training data until agents move tickets. It still needs tickets routed during the period in which examples are accumulating.

Decision. Lead-written keyword rules for cold start.

Lead-written keyword rules for cold start chosen

New-team cold start → Lead-written keyword rules until moves create training data

“A new team has no training data until agents move tickets to it. Until then, keyword rules written by the team's lead route its tickets.”
  • Allows routing before the new team has classifier training examples.
  • Rules can be inspected and maintained by the team lead.
  • Rule coverage and accuracy are not reported.
  • The 80% within two weeks target remains unverified.

The contrast with classifier-only routing shows that a no-example fallback is better supported for Q2, but the required threshold is not demonstrated, so this exact keyword-rule choice is not proven forced.

Use the classifier alone during cold start discarded

New-team cold start → Classifier alone until training examples arrive

  • Keeps routing on the existing classifier without a separate rule set.
  • With no examples for the new class, it has no team-specific basis for meeting Q2.

It continues to return a team but misses the new-team adaptation requirement in this evaluation, so the rule-based fallback is better supported.

R1 meets

A help desk webhook feeds tickets into a pipeline that attaches same-customer, same-subject tickets arriving within an hour to the earlier ticket. The system creates multilingual sentence embeddings, uses logistic regression to select a team, records the agent’s chosen team, and displays the two runner-up teams with influential words.

The point's trade-off This enables multilingual routing and simple team-level classification, but the deduplication rule may merge separate issues, and the model depends on team labels. Sentence embeddings also make “influential words” less direct to identify, weakening that explanation.

#5 A region of #4: part of the solution partial

Thought Q2 makes a no-example fallback useful: new teams need some route before agent moves have produced training examples.

Move
  • New-team cold start → Lead-written keyword rules until moves create training data

Observed Lead-written rules permit immediate routing without waiting for the classifier to learn a new class. No rule coverage, quality measure, or observed two-week result is supplied, so this is a plausible bridge rather than evidence that Q2 is met.

Q2 partly

The system initially routes support tickets using keyword rules written by team leads. As tickets are moved to different teams, those moves accumulate as training data for improving or eventually replacing the rules.

The point's trade-off This provides an immediate, interpretable way to route tickets without historical data, but depends on leads maintaining useful keywords and may route unfamiliar wording poorly until enough corrective moves accumulate.
