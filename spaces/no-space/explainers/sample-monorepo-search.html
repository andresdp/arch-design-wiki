Hosting an open-source monorepo

An open-source foundation hosts a 12-year, 40 GB monorepo with about 300 pushes a day and 2,000 contributors across five continents. Most clones come from CI and first-time contributors who need only the latest version. Four volunteers operate donated servers in data centres in Europe and North America.

How to read this page

A coding agent searched for designs that solve this problem. It combined decisions (dimensions) and their options (values) into design points, and judged each point against every requirement: meets, partly or misses. It proposes 4 alternatives. Every judgement here is the agent's; the page lays out its rationale file.

  • Decisions (ADRs) lists the alternatives, then one record per decision: the requirements that drive it, and every option weighed, with its pros and cons, chosen by an alternative or discarded.
  • Comparison puts the alternatives side by side, with the rows where they differ first.
  • Trajectory shows how the agent got there:
    • the lanes show each approach round by round, with every point coloured strong, mixed or weak;
    • a strip shows how each point met each requirement;
    • the story gives each point's thought, change, observation and trade-offs.

No design space was used. The agent named the decisions and options itself, so nothing was checked against a space and there are no gaps in one.

Alternatives

A1 · Canonical host with shallow Git clones

Keep one writable canonical repository, shallow Git clones, and CI on the primary. This is the simplest operating model, though global clone time is unverified.

Composed of 2 partial design points, one per ADR:

  • ADR1 · Single canonical host R1Q2C1 Topology → Single canonical hostCI route → Canonical primary
  • ADR2 · Shallow Git clone R2Q1C1 Clone delivery → Shallow Git clone

As a whole: A single canonical host serves as the authoritative repository for contributors and automation. Users and CI obtain shallow Git clones from that host, while CI runs against the canonical primary rather than a mirror or alternate source.

B1 · Synchronous mirrors with primary CI

Replicate reads synchronously and serve shallow bundles through a CDN, while routing CI to the canonical primary. This favors freshness and distribution at higher operational cost.

Composed of 2 partial design points, one per ADR:

  • ADR1 · Asynchronous read mirrors with primary CI R1Q2C1 Topology → Asynchronous read mirrorsCI route → Canonical primary
  • ADR2 · CDN-hosted shallow bundle R2Q1C1 Clone delivery → CDN-hosted shallow bundle

As a whole: The canonical primary accepts authoritative repository changes, while asynchronous read mirrors serve replicated read traffic. A CDN hosts a shallow clone bundle for fast initial cloning, with its contents ultimately derived from the canonical primary.

C1 · Canonical host with CDN bundles

Keep repository writes, contributor Git service, and CI on one canonical host, with shallow clone bundles distributed through a CDN. This avoids mirror management while adding artifact freshness work.

Composed of 2 partial design points, one per ADR:

  • ADR1 · Synchronous read mirrors with primary CI R1Q2C1 Topology → Synchronous read mirrorsCI route → Canonical primary
  • ADR2 · CDN-hosted shallow bundle R2Q1C1 Clone delivery → CDN-hosted shallow bundle

As a whole: The repository maintains synchronous read mirrors so users can read from replicated copies while writes remain coordinated. New users obtain a shallow clone bundle from a CDN, while CI runs against the canonical primary repository.

D1 · Canonical host with CDN bundles

Keep repository writes and CI on one canonical host, with shallow clone bundles distributed through a CDN. This avoids mirror management while adding artifact freshness work.

Composed of 2 partial design points, one per ADR:

  • ADR1 · Single canonical host R1Q2C1 Topology → Single canonical hostCI route → Canonical primary
  • ADR2 · CDN-hosted shallow bundle R2Q1C1 Clone delivery → CDN-hosted shallow bundle

As a whole: The monorepo has one authoritative host, and developers obtain its contents through a shallow bundle served from a CDN. CI uses the canonical primary as its source of truth and validates changes there.

ADR1 · Where repository reads come from and where CI fetches R1Q2C1

Context. Maintainers need one canonical write target, and CI must always see a push once it is accepted. Distributed read copies can reduce load and improve geography, but asynchronous copies can lag and synchronous copies add operational work for four volunteers.

Decision. Single canonical host (A1, D1); Asynchronous read mirrors with primary CI (B1); Synchronous read mirrors with primary CI (C1).

Single canonical host chosen in A1, D1

Topology → Single canonical hostCI route → Canonical primary

  • One source of truth for pushes and CI.
  • The origin serves global demand and is a single availability dependency.

Choose for the smallest operating footprint while CDN delivery handles first-clone distribution.

Asynchronous read mirrors with primary CI chosen in B1

Topology → Asynchronous read mirrorsCI route → Canonical primary

  • Mirrors can take contributor read load while CI sees accepted pushes at the primary.
  • Mirror freshness and operations need monitoring.

Choose when geographic read capacity justifies additional mirror maintenance.

Synchronous read mirrors with primary CI chosen in C1

Topology → Synchronous read mirrorsCI route → Canonical primary

  • Distributed reads are kept current and CI uses the authoritative source.
  • Synchronous replication adds coordination and operational burden.

Choose when mirror freshness matters enough to justify the extra work.

Asynchronous mirror as nearest CI source discarded

Topology → Asynchronous read mirrorsCI route → Nearest mirror

  • CI and contributors can use a nearby read endpoint.
  • Replication lag can hide a just-accepted push from CI.

Set aside because it misses the required read-after-push guarantee.

Synchronous mirror as nearest CI source discarded

Topology → Synchronous read mirrorsCI route → Nearest mirror

  • A nearby mirror can serve current CI reads.
  • Synchronous replication raises operational complexity.

The evaluated version couples CI to replicated service behavior; routing CI to the primary gives a simpler guarantee.

ADR2 · How first-time contributors obtain the latest source R2Q1C1

Context. First-time contributors need not download 12 years of history, and clones have a two-minute target on a limited connection. A shallow clone or bundle reduces history transfer, but the current tree size and delivery performance are not specified; a CDN may accelerate delivery while adding freshness work.

Decision. Shallow Git clone (A1); CDN-hosted shallow bundle (B1, C1, D1).

Shallow Git clone chosen in A1

Clone delivery → Shallow Git clone

  • Uses ordinary Git clone behavior while omitting full history.
  • Does not establish the two-minute target without current tree size and throughput measurements.

Choose for the direct Git workflow with no separate bundle publishing pipeline.

CDN-hosted shallow bundle chosen in B1, C1, D1

Clone delivery → CDN-hosted shallow bundle

  • A cacheable shallow artifact may reduce distance and repeated origin transfer.
  • Bundle freshness, size, and delivery time need validation; publication adds work.

Choose when measurements show the CDN path meets the target and bundle maintenance is manageable.

Sparse partial Git clone discarded

Clone delivery → Sparse partial Git clone

  • Can fetch only selected paths and reduce transferred content.
  • Contributor setup and selected content sizes affect usability and clone time.

Evaluated as a refinement, but retained as a possible variant pending evidence that the project layout makes partial checkout simple.

Round 1 · 3 points: seed A, seed B, seed C
#1 Seed of approach A strong → A1

Thought A single canonical Git endpoint and shallow clones should meet R1, R2 and Q2 while keeping C1 manageable; Q1 may improve, but checkout size is unknown.

Move
  • Topology → Single canonical host
  • Clone delivery → Shallow Git clone
  • CI route → Canonical primary

Observed A canonical source gives CI a direct path to every accepted push. Shallow history helps, but without latest-tree size and measured serving capacity the clone target remains unproven.

R1 meetsR2 meetsQ1 partlyQ2 meetsC1 meets
  • Shallow Git clone: gains R2 gives up Q1: Omitting history reduces transfer, but does not establish that the latest tree fits the two-minute target.

A single canonical host serves as the authoritative repository for contributors and automation. Users and CI obtain shallow Git clones from that host, while CI runs against the canonical primary rather than a mirror or alternate source.

The point's trade-off This centralizes source management and reduces clone time and storage, but shallow clones lack full history and the single canonical host becomes a concentrated availability dependency.

#2 Seed of approach B mixed

Thought Nearby shallow clones should help Q1 and R2, but asynchronous mirror lag can make a CI job miss the accepted push in Q2.

Move
  • Topology → Asynchronous read mirrors
  • Clone delivery → Shallow Git clone
  • CI route → Nearest mirror

Observed The regional reads help the intended audience, but CI routed to an asynchronous mirror has no guarantee it sees the newest accepted push. The four-person team also has to operate replica state.

R1 meetsR2 meetsQ1 partlyQ2 missesC1 partly
  • Asynchronous read mirrors, Nearest mirror: gains Q1 gives up Q2, C1: Geographic read distribution can lower clone latency, while mirror lag violates read-after-accepted-push and adds operational work.

Read-only mirrors asynchronously replicate the monorepo and serve clone requests. A client is directed to the geographically or network-nearest mirror, which provides a shallow Git clone containing limited history.

The point's trade-off This reduces clone latency and origin load while improving access for distributed contributors. It accepts replication staleness and limits history-dependent operations because the clone is shallow.

#3 Seed of approach C mixed

Thought Synchronous replicas should provide the accepted push to CI while a nearby bundle improves Q1 and avoids full-history transfer for R2; synchronous replica operations may strain C1.

Move
  • Topology → Synchronous read mirrors
  • Clone delivery → CDN-hosted shallow bundle
  • CI route → Nearest mirror

Observed This provides a consistency path and a globally distributable first-clone artifact. Neither bundle size nor CDN behavior is specified, and synchronous replica operations add work.

R1 meetsR2 meetsQ1 partlyQ2 meetsC1 partly
  • Synchronous read mirrors: gains Q2 gives up C1: Synchronous propagation supports read-after-write consistency but adds coordination and failure handling for the volunteer operators.
  • CDN-hosted shallow bundle: gains R2 gives up Q1: A cached bundle can reduce transfer work, but its size and refresh behavior are unmeasured, so the two-minute target is not proven.

The monorepo is replicated to read mirrors synchronously, while a CDN distributes a shallow clone bundle for fast checkout. CI jobs use the nearest mirror for repository reads and updates.

The point's trade-off This improves clone and CI read performance while reducing load on the primary repository. It gives up full-history availability through the bundle and requires synchronous mirror maintenance, which can add operational overhead or make mirror issues affect reads.

Round 2 · 3 points: refine B, refine B, new approach D
#4 Refined #2 (approach B) mixed

Thought Keep the shallow clone and read mirrors, but route CI to the canonical primary. This should restore Q2 while retaining geographic read distribution.

Move
  • change CI route: Nearest mirror → Canonical primary

Observed CI now reads the authoritative repository and can fetch every accepted push. Mirror clone performance remains unmeasured and the volunteer team must operate the copies.

R1 meetsR2 meetsQ1 partlyQ2 meetsC1 partly
  • Asynchronous read mirrors: gains Q1 gives up C1: Regional read copies may improve access, but require volunteer monitoring and maintenance.

Asynchronous read mirrors serve repository read and clone traffic, while clients use shallow Git clones to obtain only limited history. CI runs against the canonical primary, which remains the authoritative source for validation.

The point's trade-off This reduces read load on the primary and can improve clone responsiveness, but mirrors may lag and shallow clones cannot support operations requiring full history. CI remains dependent on the primary’s availability and capacity.

#5 Refined #2 (approach B) mixed → B1

Thought Keep asynchronous mirrors for contributor reads, but put CI on the canonical primary and use a shallow CDN bundle for first clones. This should restore Q2 and improve Q1 without synchronously coordinating replicas.

Move
  • change Clone delivery: Shallow Git clone → CDN-hosted shallow bundle
  • change CI route: Nearest mirror → Canonical primary

Observed Changing CI routing resolves the consistency failure without synchronous replication. The CDN and mirrors may both serve stale material unless their refresh path is managed; Q1 remains unproven without artifact size and throughput measurements.

R1 meetsR2 meetsQ1 partlyQ2 meetsC1 partly
  • Canonical primary: gains Q2 gives up Q1: Keeping CI on the authoritative primary ensures it sees accepted pushes but leaves CI dependent on the origin's capacity.
  • Asynchronous read mirrors, CDN-hosted shallow bundle: gains R2 gives up C1, Q1: Read replicas and cached bundles distribute load, but they add refresh and monitoring duties and their transfer performance remains unmeasured.

The canonical primary accepts authoritative repository changes, while asynchronous read mirrors serve replicated read traffic. A CDN hosts a shallow clone bundle for fast initial cloning, with its contents ultimately derived from the canonical primary.

The point's trade-off This improves read and clone distribution while reducing pressure on the primary, but mirrors and CDN bundles may lag behind it, and shallow clones omit repository history.

#6 New approach D mixed → D1

Thought Keep one canonical Git server and distribute only a shallow clone bundle through a CDN. This may improve Q1 while reducing operational burden compared with read mirrors; bundle size and freshness still need validation.

Move
  • Topology → Single canonical host
  • Clone delivery → CDN-hosted shallow bundle
  • CI route → Canonical primary

Observed This avoids replica operation and keeps CI consistent at the canonical host. CDN cache freshness and the latest snapshot size remain open, and the delivery layer adds some work for volunteers.

R1 meetsR2 meetsQ1 partlyQ2 meetsC1 partly
  • CDN-hosted shallow bundle: gains R2 gives up Q1, C1: The bundle could shorten first clones but has unmeasured size and introduces publication and invalidation work.

The monorepo has one authoritative host, and developers obtain its contents through a shallow bundle served from a CDN. CI uses the canonical primary as its source of truth and validates changes there.

The point's trade-off This centralizes governance and can make initial clones and CI access efficient, but shallow bundles omit repository history and the CDN introduces a delivery layer that must stay aligned with the canonical host.

Round 3 · 2 points: refine C, refine A
#7 Refined #3 (approach C) mixed → C1

Thought Keep synchronous mirrors for up-to-date distributed reads and CDN bundles for first clones, but route CI directly to the primary. This makes Q2 independent of mirror behavior.

Move
  • change CI route: Nearest mirror → Canonical primary

Observed Sending CI to the origin makes the acceptance guarantee explicit while retaining current mirrors for other reads. The added synchronization remains the main operational cost, and clone performance is still unverified.

R1 meetsR2 meetsQ1 partlyQ2 meetsC1 partly
  • Synchronous read mirrors: gains Q2 gives up C1: Coordinated copies provide current reads but require more operational coordination than four volunteers may comfortably sustain.
  • CDN-hosted shallow bundle: gains R2 gives up Q1: The shallow artifact avoids full history, but its size and measured delivery time are unknown.

The repository maintains synchronous read mirrors so users can read from replicated copies while writes remain coordinated. New users obtain a shallow clone bundle from a CDN, while CI runs against the canonical primary repository.

The point's trade-off This combines fast, geographically efficient cloning with consistent read mirrors and a single authoritative CI path. It gives up convenient access to full repository history through the CDN bundle and concentrates CI’s dependency on the primary.

#8 Refined #1 (approach A) strong

Thought Keep one authoritative host and CI path, while fetching only selected content through a sparse partial clone. This may reduce first-clone transfer while preserving a simple server topology.

Move
  • change Clone delivery: Shallow Git clone → Sparse partial Git clone

Observed Selective content retrieval may help contributors who need only part of the monorepo, with no extra server topology. The target remains unproven because repository layout, selected content size, and measured transfer time are unknown.

R1 meetsR2 meetsQ1 partlyQ2 meetsC1 meets
  • Sparse partial Git clone: gains R2 gives up Q1: Fetching selected content can reduce transfer, but the clone time still depends on selected tree size and contributor configuration.

A single canonical host serves as the authoritative repository and source for all development and automation. Developers and CI use sparse partial clones to retrieve only needed content, while CI runs through the canonical primary route.

The point's trade-off This reduces clone and CI transfer costs and avoids synchronization ambiguity, but concentrates availability and load on one host and can make workflows requiring omitted files or history more complex.
