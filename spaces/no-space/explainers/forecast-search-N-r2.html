Retail demand forecasting

A retailer forecasts weekly demand per store and product: 400 stores and 30,000 products. Every Monday the forecasts for the next eight weeks feed the replenishment system, which orders stock. Sales from the tills reach the company's data warehouse every night; promotions and public holidays move demand strongly. A team of three data scientists owns the forecasting pipeline end to end. The data warehouse is run by the central IT department, which the team cannot change.

Alternatives

A1 · Autoscaled managed replay pipeline

Run containerized forecasts in a managed orchestrator, retain complete immutable run inputs and artifacts, evaluate candidates automatically, and publish only complete staged partitions.

Composed of 4 partial design points, one per ADR:

  • ADR1 · Autoscaled managed orchestrator R1Q4C1C2 Execution → Managed workflow orchestrator with autoscaled container jobs
  • ADR2 · Immutable complete run record R2Q1 Historical replay → Immutable input snapshots, code versions, and model artifacts
  • ADR3 · Automated evaluation with approval gate R3Q2 Model promotion → Automated evaluation and approval-gated releases
  • ADR4 · Staged partition atomic publish R1Q3 Forecast delivery → Staged partitions with completeness checks and atomic publish

As a whole: A managed workflow orchestrator runs autoscaled container jobs to generate forecasts, using immutable input snapshots, code versions, and model artifacts so runs can be replayed. Automated evaluation gates model promotion, while outputs are written to staged partitions, checked for completeness, and atomically published.

B1 · Scheduled container pipeline

Use scheduled managed containers with immutable replay artifacts, automated backtests and approval, and an atomic staging-table swap for delivery.

Composed of 4 partial design points, one per ADR:

  • ADR1 · Scheduled managed containers R1Q4C1C2 Execution → Managed container workflow with scheduled runs
  • ADR2 · Immutable complete run record R2Q1 Historical replay → Immutable input snapshots, code versions, and model artifacts
  • ADR3 · Automated evaluation with approval gate R3Q2 Model promotion → Automated evaluation and approval-gated releases
  • ADR4 · Staging table atomic swap R1Q3 Forecast delivery → Staging tables with completeness checks and atomic swap

As a whole: A scheduled managed-container workflow runs forecasting jobs against immutable input snapshots, versioned code, and model artifacts, enabling exact historical replay. Candidate models are automatically evaluated, released only after approval, and their forecasts written to staging tables before completeness checks and an atomic production swap.

D1 · Lightweight registry batch

Run managed batch containers from a lightweight scheduler, preserve immutable data, code, and model artifacts, then activate validated versioned forecast tables.

Composed of 4 partial design points, one per ADR:

  • ADR1 · Lightweight managed batch R1Q4C1C2 Execution → Managed container batch with a lightweight scheduler
  • ADR2 · Immutable extract, code, and model artifacts R2Q1 Historical replay → Immutable warehouse extracts, versioned code, and model artifacts
  • ADR3 · Automated champion-challenger with registry R3Q2 Model promotion → Automated champion-challenger evaluation with approval
  • ADR4 · Versioned tables with pointer swap R1Q3 Forecast delivery → Versioned forecast tables with validated pointer swap

As a whole: A lightweight scheduler launches managed container batch jobs against immutable, versioned warehouse extracts, code, and model artifacts, making runs reproducible. Candidate models undergo automated champion-challenger evaluation with approval, after which validated versioned forecast tables become active through a pointer swap.

E1 · Declarative replay workflow

Define forecast stages as a managed container workflow, pin point-in-time data and code, compare models through one replay harness, and atomically publish versioned outputs.

Composed of 4 partial design points, one per ADR:

  • ADR1 · Declarative managed workflow R1Q4C1C2 Execution → Managed declarative workflow for containerized forecast stages
  • ADR2 · Point-in-time extract with pinned commit and model R2Q1 Historical replay → Point-in-time warehouse extracts, code commits, and model artifacts
  • ADR3 · Automated replay comparison and registry promotion R3Q2 Model promotion → Automated replay comparison with approval-gated registry promotion
  • ADR4 · Staged versioned atomic publication R1Q3 Forecast delivery → Staged versioned outputs with atomic publication

As a whole: A managed declarative workflow runs containerized forecasting stages using point-in-time warehouse extracts, code commits, and model artifacts to reproduce historical runs. Automated replay comparisons evaluate candidates before approval-gated registry promotion, after which staged, versioned forecasts are atomically published.

ADR1 · Where should weekly forecast jobs run? R1Q4C1C2

Context. The pipeline must run every week within a six-hour window and remain manageable by three data scientists. A local path helps onboarding, while managed execution reduces infrastructure work; none of the candidate platforms has yet been benchmarked on the full workload.

Decision. Autoscaled managed orchestrator (A1); Scheduled managed containers (B1); Lightweight managed batch (D1); Declarative managed workflow (E1).

Autoscaled managed orchestrator chosen in A1

Execution → Managed workflow orchestrator with autoscaled container jobs

  • Managed scheduling and autoscaling reduce routine operations and provide capacity headroom.
  • The complete workload still needs a measured six-hour run and a documented local setup.

Choose this when capacity headroom and managed orchestration are the priority.

Scheduled managed containers chosen in B1

Execution → Managed container workflow with scheduled runs

  • A simple scheduled container avoids a serverless duration ceiling and remains operationally small.
  • Local execution and end-to-end runtime need acceptance checks.

Choose this for a straightforward batch container workflow.

Lightweight managed batch chosen in D1

Execution → Managed container batch with a lightweight scheduler

  • A lean scheduler and managed workers limit the team's infrastructure burden.
  • Peak workload capacity and the six-hour objective need measurement.

Choose this when a small batch control plane is preferred.

Declarative managed workflow chosen in E1

Execution → Managed declarative workflow for containerized forecast stages

  • The declared stages can support both local runs and scheduled managed execution.
  • The declarative workflow adds setup and still requires runtime evidence.

Choose this when portability and repeatable stages matter most.

Team-managed VM discarded

Execution → Team-managed single VM running scheduled containers

  • A single host is conceptually easy to inspect and may be simple to run locally.
  • It places operations on a small science team and does not resolve replay, automation, or publication safety.

Dropped after the seed left several stressed requirements unresolved.

ADR2 · What must be retained for historical replay? R2Q1

Context. The team must reproduce a forecast from up to two years earlier within one working day. Retaining output numbers alone is insufficient to rerun the computation; the input data, code, and model state need to be tied to each run.

Decision. Immutable complete run record (A1, B1); Immutable extract, code, and model artifacts (D1); Point-in-time extract with pinned commit and model (E1).

Immutable complete run record chosen in A1, B1

Historical replay → Immutable input snapshots, code versions, and model artifacts

  • Pins the source data, code, and model state needed to reconstruct the run.
  • Requires storage lifecycle management and snapshot capture.

Chosen by the managed workflow and container alternatives for complete replay provenance.

Immutable extract, code, and model artifacts chosen in D1

Historical replay → Immutable warehouse extracts, versioned code, and model artifacts

  • Provides the input extract and executable model state required for reruns.
  • The extract process and two-year retention need operational ownership.

Chosen for the lightweight batch option because it creates an explicit run record.

Point-in-time extract with pinned commit and model chosen in E1

Historical replay → Point-in-time warehouse extracts, code commits, and model artifacts

  • Ties each replay to point-in-time data, an exact source commit, and model state.
  • Point-in-time extraction and retention add storage and pipeline complexity.

Chosen for the declarative workflow's reproducible shared replay harness.

Versioned inputs and saved outputs discarded

Historical replay → Versioned source snapshots and saved forecast outputs

  • Preserves outputs that replenishment actually received.
  • Does not ensure full immutable inputs and model artifacts for rerunning the calculation.

Set aside after the seed showed that retained results alone leave replay incomplete.

Retain only models and forecasts discarded

Historical replay → Retain model versions and forecast outputs only

  • Uses less storage and preserves delivered values for inspection.
  • Cannot reconstruct the source data and complete computation.

Dropped because it misses exact historical rerun requirements.

ADR3 · How should candidate models reach production? R3Q2

Context. Candidates need comparison on past weeks and a winning model must reach production within a week, with approval as the only manual step. Automated replay evaluation shortens comparisons, but approval remains deliberate and must be integrated into promotion.

Decision. Automated evaluation with approval gate (A1, B1); Automated champion-challenger with registry (D1); Automated replay comparison and registry promotion (E1).

Automated evaluation with approval gate chosen in A1, B1

Model promotion → Automated evaluation and approval-gated releases

  • Automates candidate scoring and leaves approval as the release decision.
  • The approval notification and deployment integration need implementation.

Chosen for managed workflow and scheduled containers to reduce manual model release work.

Automated champion-challenger with registry chosen in D1

Model promotion → Automated champion-challenger evaluation with approval

  • Provides repeatable comparisons and a governed model identity.
  • The approval path remains and must meet the one-week interval.

Chosen for the registry-centered batch alternative.

Automated replay comparison and registry promotion chosen in E1

Model promotion → Automated replay comparison with approval-gated registry promotion

  • Reuses the replay harness to compare candidates and prepares a governed promotion.
  • Harness upkeep and approval integration add workflow complexity.

Chosen for the declarative approach to make comparisons part of the pipeline.

Manual notebook comparison discarded

Model promotion → Manual notebook comparison and replacement

  • Scientists can explore candidates with familiar tools.
  • Manual comparison and replacement exceed the permitted manual approval step.

Dropped because it does not meet the development velocity scenario.

ADR4 · How should forecasts become visible to replenishment? R1Q3

Context. The replenishment system must receive the weekly forecast by its deadline and must never see a partial result. A staging area with completeness validation and a single publication action creates a clear all-or-nothing boundary; the workflow also needs a separate failure alert within 15 minutes.

Decision. Staged partition atomic publish (A1); Staging table atomic swap (B1); Versioned tables with pointer swap (D1); Staged versioned atomic publication (E1).

Staged partition atomic publish chosen in A1

Forecast delivery → Staged partitions with completeness checks and atomic publish

  • Checks partition completeness before exposing the result and supports batch-scale delivery.
  • Validation and the publication action must fit the deadline; alerts are a separate configuration.

Chosen for the autoscaled orchestrator's partitioned output.

Staging table atomic swap chosen in B1

Forecast delivery → Staging tables with completeness checks and atomic swap

  • Keeps incomplete writes out of the active table and gives replenishment one complete version.
  • The destination's swap semantics and failure alerts must be verified.

Chosen for the scheduled container alternative's simple consumer handoff.

Versioned tables with pointer swap chosen in D1

Forecast delivery → Versioned forecast tables with validated pointer swap

  • Activates one validated forecast version and allows rollback by changing the pointer.
  • The pointer update and consumer read behavior must be coordinated.

Chosen for registry batch delivery with explicit versions.

Staged versioned atomic publication chosen in E1

Forecast delivery → Staged versioned outputs with atomic publication

  • Preserves prior versions and makes each published forecast visible as one complete result.
  • Staging and retention add storage, and failure alerts still need a monitored path.

Chosen for the declarative workflow's versioned output boundary.

Direct replenishment write discarded

Forecast delivery → Direct write to replenishment table after run

  • Avoids a staging and publication layer.
  • A failed run can leave partial data visible to replenishment.

Dropped because it conflicts with the never-partial reliability requirement.

#1 Seed of approach A strong

Thought Immutable inputs and artifacts should meet R2 and Q1; automated comparison should support R3 and Q2, and staged atomic publication should prevent partial forecasts for Q3.

Move

  • Historical replay → Immutable input snapshots, code versions, and model artifacts
  • Model promotion → Automated evaluation and approval-gated champion switch
  • Forecast delivery → Write to staging, validate completeness, then atomically publish

Observed The combination covers replay, comparison, and atomic publication, but the design does not specify failure alerts or establish actual runtime; local execution and release automation also need implementation details.

A managed orchestrator runs containerized Python forecasting jobs against immutable input snapshots, recorded code versions, and model artifacts, enabling exact historical replay. The point's trade-off This gains reproducibility, controlled promotion, and protection against partial or incomplete delivery. It gives up operational simplicity and may require extra storage and compute for immutable artifacts, while approval and validation add latency to releases.
