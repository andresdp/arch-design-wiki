On-device visual inspection

A manufacturer inspects parts using cameras on 40 lines across three plants. Each line has two to four cameras and an ARM edge computer with a small neural accelerator. Networks can be unavailable for days. Inspectors label about 5,000 defect images weekly, and models are retrained weekly and pushed to devices. The team is two ML engineers and one half-time operations engineer, with a tight infrastructure budget.

Requirements

Alternatives

A1 · Local inference with scheduled retraining

Keep prediction close to each line, and use shared versioned training data, weekly automated training with quality checks, CI/CD, and rollback. This is the lower-complexity candidate for the fixed edge fleet.

Composed of 3 partial design points, one per ADR:

  • ADR1 · Local model module and service R1Q1 ML model integration into the application → Model as module in modular monolithModel serving → Local service/API based model serving
  • ADR2 · Scheduled automated batch pipeline with rollback R2Q3C1 Automated integration and delivery for ML → CI/CD pipelineModel versions in production → Rollback to previous model versionPipeline and orchestrator triggering → On-schedule triggerModel building approach → Model building pipelineModel training timing and mode → Batch-based learningTesting scope in ML pipelines → Testing trained model quality
  • ADR3 · Shared versioned batch corpus with prediction logs R2R3 Data storage for ML applications → Shared data storeData ingestion → Data ingestion in batchesData versioning → Data version repositoryModel monitoring and tracking in production → Monitoring or logging data and predictions

As a whole: The model runs as a module within a modular monolith and exposes predictions through a local service/API. A scheduled pipeline ingests batch data into a shared store, versions it, trains and validates models, tests quality, and delivers them through CI/CD, with monitoring and rollback to a prior version.

D1 · Canary controlled model service

Deploy distinct model services through CI/CD, check a release with prediction performance testing and canary traffic, monitor quality, and roll back when needed. This strengthens release control at the cost of more services to operate.

Composed of 3 partial design points, one per ADR:

  • ADR1 · Separate real-time model service R1Q1 ML model integration into the application → Model as a serviceModel serving → Microservice based model serving
  • ADR2 · Canary release with automated rollback R2Q3C1 Automated integration and delivery for ML → CI/CD pipelineDelivery pipeline tasks → Canary testingModel versions in production → Rollback to previous model versionModel building approach → Model building pipelineModel training timing and mode → Batch-based learningTesting scope in ML pipelines → Prediction service performance testing
  • ADR3 · Batch corpus with performance monitoring R2R3 Data ingestion → Data ingestion in batchesModel monitoring and tracking in production → Model performance monitoring

As a whole: A separate service serves each model’s real-time predictions, while batched data feeds an automated training, evaluation, and validation pipeline. CI/CD deploys tested models through canary releases, monitors their performance, and can roll back to the previous version when needed.

Left open: Data storage for ML applications (No requirement settles the store form for this service topology; image buffering and retention remain unspecified.) · Data versioning (The requirement calls for weekly labels but does not settle the data versioning mechanism.) · Pipeline and orchestrator triggering (Weekly timing is needed, but this trajectory did not include a trigger value in the canary approach.)

ADR1 · Where and how to serve line predictions R1Q1

Context. Every passing part needs an immediate decision. Locality is relevant to latency, while the space does not establish hardware compatibility, numeric latency, or offline continuity.

Decision. Local model module and service (A1); Separate real-time model service (D1).

Local model module and service chosen in A1

ML model integration into the application → Model as module in modular monolithModel serving → Local service/API based model serving

  • Avoids a network call for each line prediction.
  • Keeps the model close to the line application.
  • ARM accelerator compatibility and the latency target require measurement.
  • Seven day offline behavior is not specified by these values.

A1 prioritizes local inference on the fixed line equipment.

ADR3 · How to manage training images and production feedback R2R3

Context. The workflow needs new labeled images for weekly training and images that reveal model uncertainty or mistakes. The space covers batch ingestion, shared storage, data versioning, and prediction logging, but it does not define uncertainty selection, error queues, or outage buffering.

Decision. Shared versioned batch corpus with prediction logs (A1); Batch corpus with performance monitoring (D1).

Shared versioned batch corpus with prediction logs chosen in A1

Data storage for ML applications → Shared data storeData ingestion → Data ingestion in batchesData versioning → Data version repositoryModel monitoring and tracking in production → Monitoring or logging data and predictions

  • Centralizes training images and labels.
  • Makes training inputs traceable and captures prediction records.
  • Does not specify which images are uncertain or wrong.
  • Does not guarantee edge buffering during a network outage.

A1 gives priority to a traceable shared training corpus and leaves image selection policy as a separate implementation gap.

Batch corpus with performance monitoring chosen in D1

Data ingestion → Data ingestion in batchesModel monitoring and tracking in production → Model performance monitoring

  • Fits weekly labels and monitors model quality during release.
  • Does not provide a shared versioned store or identify images for labeling.

D1 uses performance monitoring to assess canary behavior, accepting less explicit data traceability.

Streamed ingestion with detailed production tracking discarded

Data ingestion → Streamed data ingestionModel monitoring and tracking in production → Model in-production tracking

  • Supports continuous feedback and broad usage tracking.
  • The seed paired it with no delivery automation and incremental training, increasing team workload.

The continuous approach did not establish reliable weekly rollout or operator recovery.
