Large-scale document classification

An insurer receives between two and eight million documents a day (scanned forms, e-mails, PDFs) and classifies each one into one of 60 claim types with an LLM-based classifier. Volume varies strongly over the year: storm season brings four times the usual load. Three teams use the results: claims handling, fraud investigation and analytics. The documents contain personal data.

Alternatives

A1 · Shared store with scheduled scoring

Use a shared repository and service interface with batch intake and hybrid online/offline scoring. Notify consumers when results are available and retain detailed model tracking with human-reviewed adjustment.

Composed of 2 partial design points, one per ADR:

  • ADR1 · Shared store with hybrid serving and subscriptions R1R2Q1Q4 Data storage for ML applications → Shared data storeData access interface → Pub/sub data access APIModel serving → Hybrid online/offline model servingNotification of prediction results → Push notificationData ingestion → Data ingestion in batches
  • ADR2 · Detailed production tracking with human adjustment Q2R3 Model monitoring and tracking in production → Model in-production trackingModel adjustment from monitoring results → Manual model adjustment

As a whole: A shared data store holds ingested batches and serves as the common repository for data, predictions, and scores. Data-access services expose the store, scheduled batch jobs write predictions there, and push notifications tell clients when results are available; monitoring logs data and predictions for human-led model adjustment and redeployment.

B1 · Event-driven hybrid scoring

Ingest documents as a stream into an event store and expose them through a queue. Hybrid serving provides online and batch paths, with push delivery and detailed production tracking for human review.

Composed of 2 partial design points, one per ADR:

  • ADR1 · Event store with queued hybrid serving R1R2Q1Q4 Data storage for ML applications → Event storeData access interface → Message/event queueing-based data access APIModel serving → Hybrid online/offline model servingNotification of prediction results → Push notificationData ingestion → Streamed data ingestion
  • ADR2 · Detailed production tracking with human adjustment Q2R3 Model monitoring and tracking in production → Model in-production trackingModel adjustment from monitoring results → Manual model adjustment

As a whole: An event store captures exchanged data as a durable event history, while streamed ingestion and a message-based API make new data available through queued events. Hybrid serving computes predictions online or in batches, pushes results to clients, and tracks model usage, inputs, outputs, interpretability, and fairness for human review and redeployment.

D1 · Shared stream with pub/sub

Use a shared repository with publish/subscribe access, streamed intake, and hybrid serving. Log inputs and outputs for investigation and rely on human-reviewed model adjustment.

Composed of 2 partial design points, one per ADR:

  • ADR1 · Shared streaming store with subscriptions and hybrid serving R1R2Q1Q4 Data storage for ML applications → Shared data storeData access interface → Pub/sub data access APIModel serving → Hybrid online/offline model servingNotification of prediction results → Push notificationData ingestion → Streamed data ingestion

As a whole: A shared data store receives a continuous stream through a pub/sub API, with publishers announcing newly available data to subscribers. Services provide online predictions while batch jobs provide offline scores, and clients receive push notifications; system data and predictions are logged for monitoring, with humans manually adjusting and redeploying models.

ADR1 · How to ingest, serve, and distribute classification results R1R2Q1Q4

Context. The design must classify a highly variable document stream and deliver results to three teams that need independent processing. Batch patterns can simplify high volume, while event and subscription patterns reduce coupling and online paths improve freshness. The design space has no values that prove the stated capacity, confidence format, cost, or data residency.

Decision. Shared store with hybrid serving and subscriptions (A1); Event store with queued hybrid serving (B1); Shared streaming store with subscriptions and hybrid serving (D1).

Shared batch repository with service access discarded

  • Centralized result storage and scheduled processing are operationally straightforward.
  • Push notifications improve result awareness compared with polling.
  • Pure batch serving limits freshness.
  • Service access does not provide the same consumer subscription decoupling as pub/sub.

Set aside after testing hybrid serving and publish/subscribe access, which preserve a batch path while giving teams more flexible delivery.

  • Subscriptions and push notifications support independent consumer workflows.
  • Combining batch and online paths adds operational coordination.
  • No value provides capacity or cost evidence for the targets.

Event store with queued hybrid serving chosen in B1

  • Continuous intake and queued access isolate producers and consumers.
  • Hybrid serving provides both online and batch paths.

  • Continuous intake, shared results, and subscriptions give consumers flexible access.
  • Hybrid serving can support both immediate and bulk workloads.
  • Streaming, shared storage, and hybrid serving create operational complexity.
  • No tested evidence establishes cost or throughput targets.

Chosen as the compromise combining a durable shared result source with streaming and flexible serving.

ADR2 · How to monitor quality and respond to model issues Q2R3

Context. Operators need to find class-specific quality drops within a day, and uncertain documents need human review whose corrections improve the classifier. Production monitoring and adjustment values offer partial support, but the space does not represent per-class alerting, review queues, confidence thresholds, or feedback-driven retraining.

Decision. Detailed production tracking with human adjustment (A1, B1); Prediction logging with human adjustment (D1).

Performance monitoring with manual adjustment discarded

Model monitoring and tracking in production → Model performance monitoringModel adjustment from monitoring results → Manual model adjustment

  • Observes model performance parameters.
  • Keeps adjustment under human control.
  • Does not specify data and prediction records for investigation.
  • Does not encode reviewer corrections or an alert deadline.

Set aside in favor of broader production tracking or prediction logging, which gives operators more diagnostic context.

Detailed production tracking with human adjustment chosen in A1, B1

Model monitoring and tracking in production → Model in-production trackingModel adjustment from monitoring results → Manual model adjustment

  • Tracks model usage, inputs, outputs, interpretability, and fairness.
  • Human adjustment allows review before model changes.
  • Tracking does not guarantee the one-day class-specific alert.
  • Manual adjustment is not the reviewer feedback loop required for classifier improvement.

Chosen by the two alternatives that prioritize diagnostic breadth and human oversight.

Prediction logging with human adjustment chosen in D1

Model monitoring and tracking in production → Monitoring or logging data and predictionsModel adjustment from monitoring results → Manual model adjustment

  • Logs data and predictions for later investigation.
  • Retains human control of model changes.
  • Logging does not guarantee class-level quality monitoring or timely alerts.
  • Correction-driven retraining is not represented.

Chosen where records of inputs and outputs are the main investigation aid.

No monitoring with automated adjustment discarded

Model monitoring and tracking in production → No in-production monitoringModel adjustment from monitoring results → Automated model adjustment

  • Avoids explicit monitoring infrastructure.
  • Automated adjustment could reduce manual work if a signal existed.
  • No monitoring signal exists to trigger adjustment.
  • Misses the observability requirement and offers no human correction loop.

Dropped because the combination has no signal for model adjustment and cannot surface quality degradation.
