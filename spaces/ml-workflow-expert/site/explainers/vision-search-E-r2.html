On-device visual inspection

A manufacturer inspects parts for defects with cameras along 40 lines across three plants. Each line has two to four cameras and a fixed ARM edge computer with a small neural accelerator. Plant network links can be unavailable for days. Inspectors label about 5,000 images per week, and the model is retrained weekly and deployed to devices. The team is two ML engineers and a half-time operations engineer, with a tight infrastructure budget.

Alternatives

A1 · Monolithic edge inference with controlled weekly releases

Run the model in the line application through a local API, and use scheduled batch training, automated deployment, canary checks, performance tests, monitoring, and rollback. This minimizes edge service boundaries while retaining a repeatable release process.

CI/CD deploys models, canary testing and prediction-service performance tests protect releases, while monitoring logs data and predictions and rollback restores a previous version when needed.

B1 · Independently deployed local model service

Package each model as its own local service so inference remains available during plant outages, while CI/CD, canary checks, monitoring, and rollback control frequent model releases. This allows model delivery to remain independent from the host application at the cost of additional operations.

This provides a flexible scoring path, though it leaves edge buffering and hybrid-mode behavior to be designed.

ADR1 · How should line inference and image collection work? R1R3Q1Q2

Context. Every part needs a timely prediction, including during long network outages. Capturing images for later labeling also requires local persistence and reconnect upload behavior, but the design space names serving and batch ingestion without a value for edge buffering or uncertainty-based selection.

Decision. Monolithic local API (A1); Independent local service (B1); Hybrid online and offline serving (D1).

Monolithic local API chosen in A1

ML model integration into the application → Model in monolithModel serving → Local service/API based model servingData ingestion → Data ingestion in batches

  • Supports local real-time inference.
  • Keeps the model deployment boundary simple.
  • Batch ingestion does not specify offline buffering or selective image capture.

Chosen for a direct local inference path and small edge footprint; implement the missing image queue explicitly.

Independent local service chosen in B1

ML model integration into the application → Model as a serviceModel serving → Local service/API based model servingData ingestion → Data ingestion in batches

  • Local inference remains available without plant connectivity.
  • Model deployment can be separated from the host application.
  • Adds another service to deploy and operate.
  • The data collection mechanism remains unspecified.

Chosen where independent model releases justify a separate local service.

Hybrid online and offline serving chosen in D1

ML model integration into the application → Model as module in modular monolithModel serving → Hybrid online/offline model servingData ingestion → Data ingestion in batches

  • Covers online prediction and offline batch processing.
  • Supports a modular application structure.
  • Does not define that online predictions stay local through outages or how images are buffered.

Chosen when batch scoring complements line inference and the team can define the edge fallback explicitly.

Network-dependent microservice discarded

ML model integration into the application → Model as a serviceModel serving → Microservice based model servingData ingestion → Streamed data ingestion

  • A network-dependent inference path risks stopping inspection during a plant outage.

Decision. Scheduled batch training with logged predictions (A1, B1, D1).

Scheduled batch training with logged predictions chosen in A1, B1, D1

  • Logging gives a starting point for inspector review.
  • Logging does not itself select uncertain images or guarantee delayed upload after an outage.

Chosen to meet the known weekly cadence and provide useful production records, with the capture queue specified as a required implementation gap.
