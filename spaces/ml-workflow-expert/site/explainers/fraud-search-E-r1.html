Card-fraud scoring service

A payments company needs in-environment real-time fraud scoring at up to 15,000 transactions per second, with delayed labels, historical auditability and a seven-person delivery team.

How to read this page

A coding agent searched for designs that solve this problem. It combined decisions (dimensions) and their options (values) into design points, and judged each point against every requirement: meets, partly or misses. It proposes 4 alternatives. Every judgement here is the agent's; the page lays out its rationale file.

  • Decisions (ADRs) lists the alternatives, then one record per decision: the requirements that drive it, and every option weighed, with its pros and cons, chosen by an alternative or discarded.
  • Comparison puts the alternatives side by side, with the rows where they differ first.
  • Trajectory shows how the agent got there:
    • the lanes show each approach round by round, with every point coloured strong, mixed or weak;
    • a strip shows how each point met each requirement;
    • the story gives each point's thought, change, observation and trade-offs.

Gaps in the space, at the bottom, lists where the design space fell short: requirements no dimension bears on, and values that only roughly fit. Every dimension and value links to its page in the space's wiki.

A1 · Lean local scorer

A local API, batch training, CI/CD, rollback, versioned data and production tracking favor a focused operating footprint; numeric targets still need validation.

Composed of 4 partial design points, one per ADR:

  • ADR1 · Local API and general stores R1Q1 Model serving → Local service/API based model servingFeature persistence and access → Store features in data stores without specific support
  • ADR2 · Batch build with CI/CD R2Q4C2 Model training timing and mode → Batch-based learningModel building approach → Model building pipelineAutomated integration and delivery for ML → CI/CD pipelineAdoption of MLOps → No MLOps
  • ADR3 · Rollback and quality testing Q4R3 Model versions in production → Rollback to previous model versionTesting scope in ML pipelines → Testing trained model quality
  • ADR4 · Versioned data and production tracking R3Q3 Data versioning → Data version repositoryModel monitoring and tracking in production → Model in-production tracking

As a whole: This system trains models in batches through an automated build pipeline, tests trained-model quality, versions training data in a dedicated repository, and delivers deployments through CI/CD. A local prediction API serves real-time scores from features in general-purpose data stores; production usage, inputs, outputs, interpretability, and fairness are tracked, with rollback available to restore the prior model.

Left open: Model serving (The space does not decide failure fallback behavior.)
