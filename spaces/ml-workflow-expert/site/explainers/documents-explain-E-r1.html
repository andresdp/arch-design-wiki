Large-scale document classification

An insurer receives between two and eight million documents a day (scanned forms, e-mails, PDFs) and classifies each one into one of 60 claim types with an LLM-based classifier. Volume varies strongly over the year: storm season brings four times the usual load. Three teams use the results: claims handling, fraud investigation and analytics. The documents contain personal data.

The solution

S · Document classification as built

A continuous, partitioned document pipeline delivers results through independent subscriptions, with production monitoring and human-led prompt corrections.

Composed of 3 partial design points, one per ADR:

  • ADR1 · Publish results for independent subscribers R2Q4 Data access interface → Pub/sub data access API
  • ADR2 · Streamed ingestion with partitioned processing R1Q1 Data ingestion → Streamed data ingestionData processing parallelization → Data partitioning in data pipeline
  • ADR3 · Monitor performance and adjust manually R3Q2 Model monitoring and tracking in production → Model performance monitoringModel adjustment from monitoring results → Manual model adjustment

As a whole: A pub/sub API lets applications subscribe to data and receive publisher notifications as a continuous stream. The pipeline partitions that stream for parallel processing, while monitoring observes model-performance parameters and humans manually adjust and redeploy models when needed.

ADR1 · Deliver classifications through independent event consumers R2Q4

Context. Three teams need results, and each must be able to change its processing independently.

Decision. Publish results for independent subscribers.

Publish results for independent subscribers chosen

Data access interface → Pub/sub data access API

“Results go to a second Kafka topic. Each consuming team has its own consumer group and reads at its own pace; analytics also loads the topic into the data warehouse every hour.”
  • Teams consume at their own pace without coupling changes to the classifier or one another.
  • Consumers must handle asynchronous delivery and manage their own subscriptions.

Chosen and supported by the pub/sub region; the requirements strongly favor independent consumption.

ADR2 · Ingest continuously and parallelize the pipeline R1Q1

Context. Documents arrive continuously and storm-season volume requires high throughput within a two-hour bound.

Decision. Streamed ingestion with partitioned processing.

Streamed ingestion with partitioned processing chosen

Data ingestion → Streamed data ingestionData processing parallelization → Data partitioning in data pipeline

“each upload puts a message on a Kafka topic.”
“The number of classifier workers scales with the length of the Kafka topic's backlog, from 4 to 120.”
  • Supports continuous arrival and parallel throughput.
  • Adds coordination overhead; no measured evidence here establishes the two-hour target.

The requirements call for continuous, scalable processing, so these choices are directionally forced; precise worker counts, batch size and achieved latency remain implementation questions.

ADR3 · Monitor signals and use human corrections to adjust the classifier R3Q2

Context. Uncertain documents must receive human review, corrections must improve future classifications, and quality problems should become visible quickly.

Decision. Monitor performance and adjust manually.

Monitor performance and adjust manually chosen

Model monitoring and tracking in production → Model performance monitoringModel adjustment from monitoring results → Manual model adjustment

“A dashboard shows, per claim type, the share of documents sent to review and the mean confidence; an alert fires when the share sent to review for a claim type doubles from one week to the next.”
“Every month the team replaces the prompt's examples with recent corrected documents, and checks the new prompt against 2,000 reviewed documents before switching to it.”
  • Keeps reviewers in the correction loop and lets staff update examples deliberately.
  • Requires labor and can respond slowly; monitoring proxies may not reveal every quality drop.

Manual adjustment is forced by the explicit human-correction loop in R3. The monitoring choice is a reasonable fit, but the design does not prove Q2's one-day detection requirement.

Monitor performance and adjust automatically discarded

Model monitoring and tracking in production → Model performance monitoringModel adjustment from monitoring results → Automated model adjustment

  • Could react faster and reduce routine manual work.
  • Does not itself incorporate the required reviewer corrections.

The contrast weakens the R3 fit because automated adjustment alone omits the explicit correction loop.

The system monitors selected model performance parameters in production and records their status over time. When monitoring indicates a problem or degradation, human operators assess the results, modify the model, and redeploy the updated version.

The point's trade-off This provides human oversight and deliberate, context-aware adjustments, but requires ongoing labor and can slow responses to changing conditions. Manual decisions and redeployments may also introduce inconsistency or operational error.
