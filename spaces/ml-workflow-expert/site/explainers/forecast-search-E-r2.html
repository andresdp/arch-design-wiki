Retail demand forecasting

Forecast weekly demand for 400 stores and 30,000 products, with forecasts for the next eight weeks delivered to replenishment by Monday 06:00. Nightly sales data is in a centrally managed warehouse; promotions and holidays strongly affect demand. Three data scientists own the pipeline.

Requirements

Alternatives

A1 · Orchestrated reproducible batch

Schedule versioned input through an orchestrated, provisioned workflow with model quality checks and monitored batch outputs.

Composed of 3 partial design points, one per ADR:

  • ADR1 · Scheduled batch outputs R1C2 Model serving → Data batch based model servingPipeline and orchestrator triggering → On-schedule trigger
  • ADR2 · Orchestrated versioned pipelines R2R3Q1Q2Q4 Automated integration and delivery for ML → Machine learning orchestratorData versioning → Data version repositoryAutomated environment provisioning → Automated provisioningScope of CI/CD automation → Build, test, and deploy machine learning pipelines and components needed during pipeline runsTesting scope in ML pipelines → Testing trained model quality
  • ADR3 · Monitor batch data and predictions Q3 Model monitoring and tracking in production → Monitoring or logging data and predictions

As a whole: A scheduled ML orchestrator retrieves versioned data, provisions environments, and runs CI/CD-built pipelines and components. It tests trained-model quality, writes batch predictions to storage, and monitors both system behavior and predictions in production.

B1 · CI/CD precomputed forecasts

Use versioned data, a scheduled run, CI/CD model delivery and monitored precomputed forecast reports.

Composed of 3 partial design points, one per ADR:

  • ADR1 · Precomputed reports R1C2 Model serving → Precompute servingPipeline and orchestrator triggering → On-schedule trigger
  • ADR2 · CI/CD versioned models R2R3Q1Q2Q4 Automated integration and delivery for ML → CI/CD pipelineData versioning → Data versioning in code repositoryAutomated environment provisioning → Automated provisioningScope of CI/CD automation → Build, test, and deploy models to be served and other system componentsTesting scope in ML pipelines → Testing trained model quality
  • ADR3 · Monitor batch data and predictions Q3 Model monitoring and tracking in production → Monitoring or logging data and predictions

As a whole: A scheduled pipeline uses versioned data to train models in automatically provisioned environments, tests model quality, and lets CI/CD build and deploy the models and supporting components. Predictions are precomputed and delivered as reports, while production data and predictions are logged and monitored.

ADR1 · How to deliver weekly forecasts R1C2

Context. Weekly, large volume forecast reports must be ready in a fixed six-hour window. Batch delivery fits the cadence; the space does not represent deadline scheduling precision or atomic publication.

Decision. Scheduled batch outputs (A1); Precomputed reports (B1).

Scheduled batch outputs chosen in A1

Model serving → Data batch based model servingPipeline and orchestrator triggering → On-schedule trigger

  • Scheduled output is aligned with weekly replenishment.
  • No value guarantees Monday 06:00 or atomic completeness.

Retains an explicit batch run and schedule.

Precomputed reports chosen in B1

Model serving → Precompute servingPipeline and orchestrator triggering → On-schedule trigger

  • Precomputation matches forecast report delivery.
  • Can be stale and has no explicit atomic delivery guarantee.

Makes the forecast report a precomputed artifact.

ADR2 · How to reproduce and promote models R2R3Q1Q2Q4

Context. Historical reruns and approval-led model updates require preserved inputs, repeatable environments and automated checks/deployment. These choices add operating complexity for a small team.

Decision. Orchestrated versioned pipelines (A1); CI/CD versioned models (B1).

Orchestrated versioned pipelines chosen in A1

Automated integration and delivery for ML → Machine learning orchestratorData versioning → Data version repositoryAutomated environment provisioning → Automated provisioningScope of CI/CD automation → Build, test, and deploy machine learning pipelines and components needed during pipeline runsTesting scope in ML pipelines → Testing trained model quality

  • Supports traceable reruns and repeatable execution.
  • Several operational components increase team burden.

Emphasizes reproducible pipeline runs and model quality checks.

CI/CD versioned models chosen in B1

Automated integration and delivery for ML → CI/CD pipelineData versioning → Data versioning in code repositoryAutomated environment provisioning → Automated provisioningScope of CI/CD automation → Build, test, and deploy models to be served and other system componentsTesting scope in ML pipelines → Testing trained model quality

  • Automates model artifact deployment and candidate evaluation.
  • Data versioning in the code repository may be less suitable for large warehouse datasets.

Emphasizes low-friction promotion after an approval gate.

ADR3 · How to observe weekly run health Q3

Context. The team needs fast failure awareness and complete outputs. Monitoring/logging can expose behavior, but notification thresholds and atomic publication are absent from the space.

Decision. Monitor batch data and predictions (A1, B1).

Monitor batch data and predictions chosen in A1, B1

Model monitoring and tracking in production → Monitoring or logging data and predictions

  • Provides production data and prediction visibility.
  • Does not specify a 15-minute alert or prevent partial delivery.

Closest available monitoring choice.

**Solution:** The system runs model scoring in scheduled data batches and writes predictions to storage. Pipelines are launched on demand, while build/deployment scripts are run manually; environments, data, tests, monitoring, and CI/CD deployment are not automated. **
