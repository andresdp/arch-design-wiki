Support-ticket routing

A software company routes about 20,000 daily support tickets in English, Spanish and Portuguese to 25 teams. Human forwarding delays misrouted tickets by a day on average, and products and teams change several times a year.

The solution

S · Ticket routing as built

A real-time routing service assigns tickets, and a weekly automated pipeline retrains and evaluates the classifier from recent final team assignments.

Composed of 2 partial design points, one per ADR:

  • ADR1 · Routing service with microservice model serving R1Q1 ML model integration into the application → Model as a serviceModel serving → Microservice based model serving
  • ADR2 · Automated batch retraining and evaluation R2Q2 Model building approach → Model building pipelineModel training timing and mode → Batch-based learning

As a whole: A separate service encapsulates each model, exposing real-time predictions through a distributed microservice serving layer. An automated pipeline trains, evaluates, and validates models in batches, while production services log system data and predictions for monitoring and tracking.

ADR1 · Serve ticket predictions in real time R1Q1

Context. Every arriving ticket needs an assigned team, and the stated peak target is assignment within 10 seconds. A live prediction path fits that requirement, although the space cannot confirm the numeric latency or the agent correction workflow.

Decision. Routing service with microservice model serving.

Routing service with microservice model serving chosen approximate fit

ML model integration into the application → Model as a serviceModel serving → Microservice based model serving

“The service runs on a managed Kubernetes cluster in the company's EU cloud region, with two replicas behind a load balancer.”
“The help desk tool sends every new ticket to the routing service through a webhook. Otherwise the service turns the subject and the body into an embedding with a pretrained multilingual sentence-embedding model, and a logistic-regression classifier with one class per team picks the team.”
  • Returns model predictions in real time, supporting automatic assignment.
  • Distributed serving adds network and operations overhead; the space does not establish the target latency.

The requirement forces real-time serving over scheduled batch serving, but it does not force microservice serving over a local API. The integration mapping is approximate because the described routing service is not necessarily one service per model.

Approximate fit. The solution's single routing service includes model inference, while v:1.1 describes one service per model.

ADR2 · Train from agent corrections in validated batches R2Q2

Context. Agent moves must inform the classifier, and a new product team needs to become effective quickly. The solution periodically collects recent final-team labels, retrains, evaluates, and promotes only a model that is at least as accurate as the current one; keyword rules cover a new team's initial lack of examples.

Decision. Automated batch retraining and evaluation.

Automated batch retraining and evaluation chosen

Model building approach → Model building pipelineModel training timing and mode → Batch-based learning

“Every Sunday a scheduled job exports the tickets of the last 90 days with their final teams, retrains the classifier (the embedding model is never retrained) and evaluates it on the last week's tickets. If it is at least as accurate as the current model, the job replaces the model file in object storage, and the service loads the new file within five minutes.”
  • Uses accumulated agent corrections in a repeatable training and evaluation cycle.
  • Corrections wait for a scheduled run, and batch training alone does not establish the new-team accuracy target.

The solution implements this option and it serves R2. It is not forced: incremental learning could adapt sooner, while the solution's keyword rules independently cover the initial cold start.

Automated incremental learning and evaluation discarded

Model building approach → Model building pipelineModel training timing and mode → Incremental learning

  • Can use newly available corrections sooner, which may help adaptation.
  • Still needs examples for the new team and adds ongoing update complexity; it does not prove the 80% target.

This is a contrast offered by the design space, not an option named as considered in the solution. The requirement does not force incremental training because the design uses a keyword fallback and no numeric outcome is established.
