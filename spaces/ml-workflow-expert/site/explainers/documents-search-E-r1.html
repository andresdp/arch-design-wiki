Large-scale document classification

An insurer receives two to eight million personal documents per day, with storm season bringing four times the usual load. An LLM classifier from the insurer's approved EU provider assigns each document to one of 60 claim types. Claims handling, fraud investigation, and analytics consume the results.

How to read this page

A coding agent searched for designs that solve this problem. It combined decisions (dimensions) and their options (values) into design points, and judged each point against every requirement: meets, partly or misses. It proposes 4 alternatives. Every judgement here is the agent's; the page lays out its rationale file.

  • Decisions (ADRs) lists the alternatives, then one record per decision: the requirements that drive it, and every option weighed, with its pros and cons, chosen by an alternative or discarded.

Alternatives

A1 · Partitioned hybrid serving

Use partitioned batch processing with online/offline serving, event queues, and push delivery. This balances bulk throughput and timely results, subject to measuring batch delay and operating both serving paths.

Composed of 4 partial design points, one per ADR:

  • ADR1 · Partitioned batches with hybrid serving R1Q1 Batch or real-time data processing → Batch-based data processingModel serving → Hybrid online/offline model serving
  • ADR1 · Partitioned pipeline parallelism R1Q1 Data processing parallelization → Data partitioning in data pipeline
  • ADR2 · Event queue with push notifications R2Q4 Data access interface → Message/event queueing-based data access APINotification of prediction results → Push notification
  • ADR3 · Log data and predictions Q2 Model monitoring and tracking in production → Monitoring or logging data and predictions

As a whole: Incoming data is placed on a message/event queue and processed in partitioned batches for parallelism. Offline batches produce scores while services handle online computations; clients receive push notifications when results are available, and system data and predictions are logged and monitored.

B1 · Event-driven low latency

Stream and partition incoming work, serve predictions through microservices, and notify subscribed consumers. It best fits fresh delivery and loose coupling, with greater operational cost and complexity to validate.

Composed of 3 partial design points, one per ADR:

  • ADR1 · Continuous stream and microservice serving R1Q1 Batch or real-time data processing → Real-time, stream-based data processingModel serving → Microservice based model servingData processing parallelization → Hybrid data processing parallelization
  • ADR2 · Pub/sub with push notifications R2Q4 Data access interface → Pub/sub data access APINotification of prediction results → Push notification
  • ADR3 · Track production usage and inputs/outputs Q2 Model monitoring and tracking in production → Model in-production tracking

As a whole: A real-time stream-processing pipeline uses hybrid parallelization to handle incoming data and a pub/sub API to distribute it to model-serving microservices. The services return predictions in real time and push result-availability notifications to clients, while in-production tracking records model usage, inputs, outputs, interpretability, and fairness.

C1 · Dataset-isolated hybrid path

Keep dataset-specific pipelines and hybrid online/offline serving with event queues and push delivery. Dataset isolation and broad tracking support operations but require more paths to manage.

Composed of 4 partial design points, one per ADR:

  • ADR1 · Partitioned batches with hybrid serving R1Q1 Batch or real-time data processing → Batch-based data processingModel serving → Hybrid online/offline model serving
  • ADR1 · Hybrid pipeline parallelism R1Q1 Data processing parallelization → Hybrid data processing parallelization
  • ADR2 · Event queue with push notifications R2Q4 Data access interface → Message/event queueing-based data access APINotification of prediction results → Push notification
  • ADR3 · Track production usage and inputs/outputs Q2 Model monitoring and tracking in production → Model in-production tracking

As a whole: The system processes data in batches, using hybrid parallelization, while combining offline batch predictions with online service computations. A message/event-based API queues newly available data, and clients receive push notifications when prediction results are ready; production tracking records usage, inputs, outputs, interpretability, and fairness.

D1 · Streaming intake with immediate serving

Use continuous intake, partitioned work, and real-time model-serving services behind an event queue. This removes batch scoring delay while retaining the operational overhead of a distributed path.

Composed of 3 partial design points, one per ADR:

  • ADR1 · Streaming intake with partitioned immediate serving R1Q1 Batch or real-time data processing → Real-time, stream-based data processingModel serving → Microservice based model servingData processing parallelization → Data partitioning in data pipeline
  • ADR2 · Event queue with push notifications R2Q4 Data access interface → Message/event queueing-based data access APINotification of prediction results → Push notification
  • ADR3 · Monitor model performance parameters Q2 Model monitoring and tracking in production → Model performance monitoring

As a whole: 1. A real-time stream is partitioned within the pipeline for parallel processing and sent to distributed model-serving microservices. An event queue provides the data-access interface, while push notifications deliver prediction results to clients and performance monitoring tracks the deployed model. 2.

ADR1 · Choose the processing and scoring cadence R1Q1

Context. The classifier must complete work promptly at storm-season volume while keeping annual unit cost below the stated cap. The design space offers batch, streaming, and hybrid-serving patterns but provides no benchmark to prove either numeric target.

Decision. Partitioned batches with hybrid serving (A1, C1); Continuous stream and microservice serving (B1); Streaming intake with partitioned immediate serving (D1); Partitioned pipeline parallelism (A1); Hybrid pipeline parallelism (C1).

Partitioned batches with hybrid serving chosen in A1, C1

Batch or real-time data processing → Batch-based data processingModel serving → Hybrid online/offline model serving

  • Partitions work for parallel batch throughput.
  • Online and offline paths cover both immediate and bulk requests.
  • Batch schedules can delay some documents.
  • Two serving paths add operating cost.

Chosen by A1 and C1 to balance the storm load with fresher results; capacity and cost require measurement.

Continuous stream and microservice serving chosen in B1

Batch or real-time data processing → Real-time, stream-based data processingModel serving → Microservice based model servingData processing parallelization → Hybrid data processing parallelization

  • Continuous processing and distributed serving favor low latency.
  • Hybrid parallelism can distribute work.
  • More distributed components increase operational complexity and potentially cost.

B1 prioritizes freshness and team independence, accepting operational cost uncertainty.

Streaming intake with partitioned immediate serving chosen in D1

Batch or real-time data processing → Real-time, stream-based data processingModel serving → Microservice based model servingData processing parallelization → Data partitioning in data pipeline

  • Avoids scheduled scoring delay while partitioning work for parallel execution.
  • Service capacity, scaling behavior and cost are unmeasured.

D1 resolves the mismatch between streaming intake and batch scoring observed during exploration.

Streaming intake with batch scoring discarded

Batch or real-time data processing → Real-time, stream-based data processingModel serving → Data batch based model servingData processing parallelization → Data partitioning in data pipeline

  • Continuous intake and partitioned work can absorb bursts.
  • Scheduled batch serving can miss the two-hour freshness target.

The exploration exposed that real-time intake does not help a document whose scoring waits for a batch.

Partitioned pipeline parallelism chosen in A1

Data processing parallelization → Data partitioning in data pipeline

  • Partitions data within the pipeline for parallel work.
  • Requires tuning and monitoring partitioned jobs.

A1 uses partitioning to support the batch path.

Hybrid pipeline parallelism chosen in C1

Data processing parallelization → Hybrid data processing parallelization

  • Combines parallelization approaches for different workloads.
  • Adds choices and coordination to pipeline operations.

C1 retains dataset isolation while allowing hybrid distribution of burst work.

ADR2 · Decouple result consumers R2Q4

Context. Three teams need results, and each should be able to change its processing independently. Event queues, subscriptions, and push or polling provide alternatives for result access and notification.

Decision. Event queue with push notifications (A1, C1, D1); Pub/sub with push notifications (B1).

Event queue with push notifications chosen in A1, C1, D1

Data access interface → Message/event queueing-based data access APINotification of prediction results → Push notification

  • Asynchronous queues decouple producer and consumer timing.
  • Push signals availability without repeated polling.
  • Queue and notification delivery need reliability management.

Provides an asynchronous contract for all consuming teams and notification on availability.

Pub/sub with push notifications chosen in B1

Data access interface → Pub/sub data access APINotification of prediction results → Push notification

  • Subscriptions decouple teams and push alerts them when predictions are available.
  • Subscription and notification coordination adds operational work.

Fits independently evolving subscribers in the low-latency event-driven path.

Event queue with polling discarded

Data access interface → Message/event queueing-based data access APINotification of prediction results → Polling

  • Consumers can request results when convenient.
  • Repeated polling can add load and delay result discovery.

Set aside in favor of proactive result notification for the stated availability needs.

ADR3 · Monitor model behavior in production Q2

Context. Operators need to notice quality drops for a particular claim type within one day. Performance monitoring, prediction logging, and model tracking provide operational evidence, but the space does not define claim-type metrics, alert thresholds, or alert timing.

Decision. Monitor model performance parameters (D1); Log data and predictions (A1); Track production usage and inputs/outputs (C1, B1).

Monitor model performance parameters chosen in D1

Model monitoring and tracking in production → Model performance monitoring

  • Directly observes model performance parameters.
  • Does not specify per-claim-type quality metrics or one-day alerts.

Best conceptual match for direct quality monitoring; explicit per-type alerting must be designed outside the available choices.

Log data and predictions chosen in A1

Model monitoring and tracking in production → Monitoring or logging data and predictions

  • Inputs and outputs enable investigations of quality changes.
  • Logs alone do not detect or alert on a per-type drop.

Provides diagnostic evidence through logged inputs and outputs for the hybrid batch and online path.

Track production usage and inputs/outputs chosen in C1, B1

Model monitoring and tracking in production → Model in-production tracking

  • Broad tracking provides context about model use, inputs and outputs.
  • Tracking does not define a quality alert or its timing.

Provides broad operational context for the dataset-isolated and event-driven paths.
