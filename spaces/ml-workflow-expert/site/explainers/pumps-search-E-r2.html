Pump failure prediction

A water utility operates about 400 pumps at 12 stations. Vibration, temperature, and pressure sensors report every second; rural stations have unreliable mobile connections. The utility has two data scientists and depends on IT for servers and networks.

Alternatives

A1 · Local modular prediction with controlled retraining

Serve predictions from a local API, stream sensor data, and use versioned batch retraining from new inspection data with monitored, human-reviewed changes. This reduces dependence on central connectivity while keeping the workflow familiar to a small team.

Composed of 2 partial design points, one per ADR:

  • ADR2 · Versioned batch learning with human review R2Q2 Data storage for ML applications → Shared data storeData versioning → Data versioning in code repositoryPipeline and orchestrator triggering → On availability of new training data triggerModel building approach → Model building pipelineModel training timing and mode → Batch-based learningModel monitoring and tracking in production → Monitoring or logging data and predictionsModel adjustment from monitoring results → Manual model adjustmentAdoption of MLOps → MLOpsAutomated integration and delivery for ML → CI/CD pipelineScope of CI/CD automation → Build, test, and deploy models to be served and other system components

As a whole: The application contains the model as a modular-monolith module, using a shared data store and local API to serve predictions. Streaming inputs are stored and versioned in the code repository; newly available training data triggers a batch training, evaluation, and validation pipeline, while clients receive push notifications and production data and predictions are monitored.

B1 · Event-driven, continuously adapting prediction

Capture data and feedback as events, serve locally through an event-driven model interface, and use hybrid learning with automated adjustment and orchestrated delivery. It favors fast adaptation and decoupled components at the cost of operational complexity.

Composed of 2 partial design points, one per ADR:

  • ADR1 · Event-driven local serving R1Q1 ML model integration into the application → Event-driven model as a serviceModel serving → Local service/API based model servingNotification of prediction results → Push notificationData ingestion → Streamed data ingestion
  • ADR2 · Event-driven hybrid learning with a builder component R2Q2 Data storage for ML applications → Event storeModel building approach → Model builder componentModel training timing and mode → Hybrid batch-based and incremental learningModel adjustment from monitoring results → Automated model adjustmentAdoption of MLOps → MLOpsAutomated integration and delivery for ML → Machine learning orchestratorScope of CI/CD automation → Build, test, and deploy machine learning pipelines and components needed during pipeline runs

As a whole: Streaming data is captured in an event store and delivered through an event-driven pub/sub or queue interface to a locally served model API; prediction availability is pushed to clients. An MLOps orchestrator coordinates model building, hybrid batch/incremental training, monitoring-triggered automated adjustment, and CI/CD pipelines that build, test, and deploy the required components.

D1 · Hybrid online and batch prediction

Combine event-driven online serving with offline batch work and hybrid training, with CI/CD and automated monitoring adjustments. This spans fast and large-scale workloads but has the highest coordination burden.

Composed of 2 partial design points, one per ADR:

  • ADR1 · Hybrid online and offline serving R1Q1 ML model integration into the application → Event-driven model as a serviceModel serving → Hybrid online/offline model servingNotification of prediction results → Push notificationData ingestion → Streamed data ingestion
  • ADR2 · Hybrid online and offline learning with automated delivery R2Q2 Data storage for ML applications → Event storeModel building approach → Model building pipelineModel training timing and mode → Hybrid batch-based and incremental learningModel adjustment from monitoring results → Automated model adjustmentAdoption of MLOps → MLOpsAutomated integration and delivery for ML → Machine learning orchestratorScope of CI/CD automation → Build, test, and deploy models to be served and other system components

As a whole: An event-driven application ingests continuous data through streams, records exchanged data in an event store, and invokes model services through pub/sub or queues. An MLOps orchestrator automates training, evaluation, validation, hybrid batch/incremental learning, monitoring-triggered adjustment, and CI/CD deployment; hybrid serving computes predictions online and offline, then pushes results to clients.

ADR1 · Prediction serving and warning delivery R1Q1

Context. The utility needs pump-specific warnings in time to act and needs them to reach station technicians during mobile outages. Local or hybrid prediction paths and push notification help with responsiveness, but the design space does not define the forecasting model, warning horizon, probable-cause explanation, station-local buffering, or delivery guarantees.

Decision. Local modular serving (A1); Event-driven local serving (B1); Hybrid online and offline serving (D1).

Local modular serving chosen in A1

ML model integration into the application → Model as module in modular monolithModel serving → Local service/API based model servingNotification of prediction results → Push notificationData ingestion → Streamed data ingestion

  • Local real-time serving can continue without a central mobile connection.
  • Streaming inputs and push notifications support prompt workflows.
  • The design space does not establish the predictive horizon, cause identification, or durable offline notification delivery.

Choose this when operational simplicity and station-proximate inference are priorities.

Event-driven local serving chosen in B1

ML model integration into the application → Event-driven model as a serviceModel serving → Local service/API based model servingNotification of prediction results → Push notificationData ingestion → Streamed data ingestion

  • Decoupled event integration fits continuous sensor and inspection inputs.
  • Local serving reduces dependence on a remote inference service.
  • Event infrastructure and automated changes increase operating and governance demands; outage alert delivery remains unspecified.

Choose this for fast feedback and component separation when the utility can support the added operating complexity.

Hybrid online and offline serving chosen in D1

  • Combines online prediction with offline batch calculations.
  • Event-driven inputs and push notification cover continuous workflows.
  • Coordination between online and offline paths increases complexity and does not guarantee station-side alert delivery during an outage.

Choose this where both responsive calculation and batch processing are important and the team can manage two paths.
