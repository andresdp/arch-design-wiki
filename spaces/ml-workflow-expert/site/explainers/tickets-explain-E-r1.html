Support-ticket routing

A software company receives about 20,000 support tickets a day, in English, Spanish and Portuguese, by e-mail and through a web form. Each ticket must reach one of 25 support teams. Today a first-line team reads every ticket and forwards it by hand, and a ticket sent to the wrong team waits a day on average before it reaches the right one. Products, and the teams that support them, change a few times a year.

The solution

S · Ticket routing as built

A real-time routing service classifies incoming tickets and a scheduled pipeline learns from agents' final team assignments, with human-authored rules covering new-team cold starts.

Composed of 3 partial design points, one per ADR:

As a whole: A dedicated service integrates each model, while microservices deliver real-time predictions from continuously ingested streams. On a schedule, an automated pipeline trains, evaluates, and validates models in batches; one selected version runs in production, with performance monitoring triggering automated adjustments.

ADR1 · Serve ticket assignments in real time R1Q1

Context. Every arriving ticket needs a team assignment, and the latency scenario sets a 10-second target. A live prediction path supports those drivers; the target still requires a load measurement at peak volume.

Decision. Dedicated real-time service with webhook ingestion.

ADR2 · Learn from agent corrections and promote retrained models R2Q2

Context. Agent moves need to become training feedback. New product teams also need adequate routing within two weeks, but the solution has no labels for a new team until agents make corrections, and it gives no measured result for the 80% target.

Decision. Weekly batch training and automatic replacement.

Weekly batch training and automatic replacement chosen

Model building approach → Model building pipelineModel training timing and mode → Batch-based learningPipeline and orchestrator triggering → On-schedule triggerModel versions in production → Single model in productionModel adjustment from monitoring results → Automated model adjustment

“Every Sunday a scheduled job exports the tickets of the last 90 days with their final teams, retrains the classifier (the embedding model is never retrained) and evaluates it on the last week's tickets.”
“If it is at least as accurate as the current model, the job replaces the model file in object storage, and the service loads the new file within five minutes.”
  • The scheduled job uses agents' final teams as labels and retrains the classifier.
  • Evaluation against current accuracy gates automatic replacement.
  • Weekly updates are less immediate than incremental learning.
  • The single-model replacement path does not document rollback or parallel comparison.
  • The rule-based cold-start path has no demonstrated accuracy against Q2.

The combination implements learning from moves and maintains an automated evaluation gate. Batch learning and automated replacement are free choices relative to R2, and the solution does not prove Q2.

ADR3 · Track agent corrections as a routing-quality signal R2

Context. Agent moves are feedback that the classifier can learn from. The solution also watches the rate of moves by team, while the design-space monitoring value describes model-performance parameters.

Decision. Monitor correction share and automate model adjustment.

Monitor correction share and automate model adjustment chosen approximate fit

The dashboard helps surface correction patterns, but R2 is met by the training loop and does not force this monitoring choice or automated adjustment.
