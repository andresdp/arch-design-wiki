Large-scale document classification

An insurer receives two to eight million documents a day, classifies them into 60 claim types with an LLM, serves three teams, sees fourfold seasonal peaks, and handles personal data.

Requirements

The solution, then its decisions as architecture decision records: each ADR addresses a few related requirements, with the solution's option and the options it was contrasted with. Select an alternative or an option to see it in the graph.

The solution

S · Document classification as built

An event-driven LLM classification pipeline uses Kafka, parallel Kubernetes workers and independent consumers, with a human correction loop and prompt review process.

Composed of 3 partial design points, one per ADR:

  • ADR0 · Shared data store R2 Data storage for ML applications → Shared data store
  • ADR1 · Streamed, partitioned, event-driven pipeline R2Q1Q4 ML model integration into the application → Event-driven model as a serviceData access interface → Message/event queueing-based data access APIData ingestion → Streamed data ingestionData processing parallelization → Data partitioning in data pipeline
  • ADR2 · Manual correction and prompt refresh with reviewed-set check R3Q2 Model monitoring and tracking in production → Model performance monitoringModel adjustment from monitoring results → Manual model adjustmentTesting scope in ML pipelines → Testing trained model quality

As a whole: A continuous data stream is partitioned through the pipeline and stored in a shared data store, with message or event notifications exposing newly available data. An event-driven model service consumes these events, while trained-model quality tests and production performance monitoring inform humans who manually adjust and redeploy models.

ADR0 · Store documents and results in a shared store R2

Context. The pipeline needs to retain incoming documents and make processed data available to the classification and downstream flow.

Decision. Shared data store.

Shared data store chosen

Data storage for ML applications → Shared data store

“Incoming documents land in an object storage bucket in the EU region”
  • The object storage bucket and stored result records provide shared persisted data.
  • The space does not distinguish object storage or assess its jurisdiction and access controls.

Chosen as the closest space value for object storage and stored results; this mapping does not establish compliance with the EU residency constraint.

ADR1 · Ingest and distribute classification work through events R2Q1Q4

Context. The pipeline must absorb highly variable volume and let each of three teams consume results independently.

Decision. Streamed, partitioned, event-driven pipeline.

Streamed, partitioned, event-driven pipeline chosen

ML model integration into the application → Event-driven model as a serviceData access interface → Message/event queueing-based data access APIData ingestion → Streamed data ingestionData processing parallelization → Data partitioning in data pipeline

“A classifier service, running on Kubernetes, sends the text to the approved provider's LLM in its EU region.”
“Results go to a second Kafka topic. Each consuming team has its own consumer group and reads at its own pace”
“each upload puts a message on a Kafka topic”
“The number of classifier workers scales with the length of the Kafka topic's backlog, from 4 to 120.”
  • Queueing and separate consumer groups support independently paced consumers.
  • Streaming and partitioning support continuous parallel work.
  • Queues add asynchronous coordination; actual two-hour throughput is not established.

Chosen because it meets R2 and Q4 and fits Q1's variable high volume; Q1 is a target to validate, not a demonstrated result.

Batched ingestion with event delivery discarded

ML model integration into the application → Event-driven model as a serviceData access interface → Message/event queueing-based data access APIData ingestion → Data ingestion in batchesData processing parallelization → Data partitioning in data pipeline

  • Batching can process accumulated work in parallel.
  • The point description indicates less immediate responsiveness.

The contrast did not show a failure against the two-hour target, so the stream choice is not forced by the evidence; the solution's continuous upload path is the closer fit.

ADR2 · Use human corrections to improve the classifier R3Q2

Context. Uncertain documents need human review, corrections must improve the classifier, and operators need timely visibility of quality drops.

Decision. Manual correction and prompt refresh with reviewed-set check.

Manual correction and prompt refresh with reviewed-set check chosen

  • Manual monthly updates may lag changes.

Manual adjustment is forced by R3 among the two adjustment alternatives tested because the automated contrast does not specify use of human corrections. Monitoring and testing are approximate fits to the implemented metrics and prompt evaluation.

R2 meetsQ1 partlyQ4 meets
  • Event-driven model as a service, Message/event queueing-based data access API, Streamed data ingestion, Data partitioning in data pipeline: gains R2, Q4 gives up Q1: Queues and independent consumers decouple result handling; the required throughput remains unverified without timing measurements.

The system ingests a continuous stream, partitions it across parallel pipeline workers, and publishes newly available data through messages or events. An event-driven model service subscribes to those events or a queue, processes the data, and returns results through the same asynchronous interface.

The point's trade-off This supports scalable, decoupled, continuously processed data flows, but introduces queueing and event-management complexity, including asynchronous coordination and potentially less immediate access to results.

The application ingests data in batches, partitions each batch within the pipeline, and publishes resulting work or data-availability events. A model service subscribes to the queue or pub/sub interface, processes requests asynchronously, and emits prediction results as events.

The point's trade-off This combination improves decoupling, throughput, and scalable parallel processing. It gives up immediate responsiveness and introduces queueing, batching, and asynchronous coordination overhead, including potentially more complex tracking of processing status and results.

#4 A region of #1: part of the solution partial

Thought R3 and Q2 call for review feedback, quality checks and visibility into per-type performance.

Move
  • Model monitoring and tracking in production → Model performance monitoring
  • Model adjustment from monitoring results → Manual model adjustment
  • Testing scope in ML pipelines → Testing trained model quality

Observed The review queue, monthly prompt example refresh, reviewed-set check and per-type dashboard support the feedback and quality-control region. Model performance monitoring is only an approximate fit for the particular indicators used, and testing trained-model quality is approximate because the solution checks a prompt against reviewed examples rather than testing a newly trained model. The point has no source attestations.

R3 meetsQ2 partly
  • Model performance monitoring, Manual model adjustment, Testing trained model quality: gains R3 gives up Q2: Manual correction and prompt updating close the feedback loop; the monitoring cadence does not guarantee one-day detection.

The system monitors selected model-performance parameters in production and uses the observations to identify potential degradation. When adjustment is needed, humans modify and redeploy the model, while pipeline tests assess the quality of each trained model before release.

The point's trade-off This combines targeted operational visibility with human judgment and quality checks, but manual adjustment and redeployment can be slower and less scalable than automated responses. Testing trained-model quality may not detect every production issue reflected in the monitored parameters.

No source attests this combination.

Move
  • change Model adjustment from monitoring results: Manual model adjustment → Automated model adjustment

Observed The automated adjustment contrast does not specify a human correction path, so it misses R3 as stated. That makes the manual feedback choice forced among these two adjustment values for R3. This contrast is an option offered by the space, not an option named in the solution. Neither option resolves the one-day monitoring gap.

R3 missesQ2 partly
  • Automated model adjustment: gains Q2 gives up R3: Automated adjustment may respond to monitored performance, but does not by itself use human reviewers' corrections as R3 requires.

The pipeline tests the quality of each trained model before it is used. In production, it monitors specified performance parameters and automatically triggers model adjustments when monitored results indicate they are needed.

The point's trade-off This provides continuous oversight and faster response to performance changes, reducing reliance on manual intervention. It gives up some human review and control, and automated adjustments may respond inappropriately if the monitored parameters or triggers are poorly chosen.
