Hosting an open-source monorepo

An open-source foundation hosts a 12-year, 40 GB monorepo for about 2,000 contributors across five continents. Most clones come from CI and first-time contributors who need only the latest version. Four volunteers operate donated servers in Europe and North America.

The solution

S · Monorepo hosting as built

A central on-disk Git origin serializes pushes and has a manually activated disk replica. Regional caches serve most reads, while contributor guidance uses partial clone and sparse checkout. CI reads the origin directly.

Composed of 4 partial design points, one per ADR:

  • ADR1 · On-disk origin with serialized updates R1Q2 Source of truth for repository state → Repository files on server disksReference update coordination → One server serializes the updates
  • ADR2 · Paired block-level disk copy Q2 Replication for durability → Block-level filesystem replication
  • ADR3 · Partial clone with sparse checkout R2Q1 Client data transfer → Partial clone with sparse checkout
  • ADR4 · Cache servers near clients Q1 Serving reads → Cache servers near the clients

As a whole: 1. Plain Git repositories on server disks remain authoritative, with one file server serializing reference updates. Paired machines replicate those files block-by-block, while regional caches serve reads and clients use partial clone with sparse checkout to limit transferred data. 2. **

ADR1 · Canonical repository and push ordering R1Q2

Context. Maintainers need one standard Git push destination, and CI starting after an accepted push must fetch that state. The design uses the origin as the authority and serializes its updates; CI bypasses caches and fetches the origin.

Decision. On-disk origin with serialized updates.

On-disk origin with serialized updates chosen

Source of truth for repository state → Repository files on server disksReference update coordination → One server serializes the updates

“It holds the repository as a plain Git repository on its local disk”
“applies pushes one at a time”
  • Provides one canonical Git repository and a clearly ordered state for direct CI reads.
  • Makes writes and reads dependent on one server and its local storage.

Chosen to provide the requested canonical endpoint and a stable post-acceptance state. Serialization is free relative to Q2 because three-phase commit also meets it.

On-disk origin with three-phase commit discarded

Source of truth for repository state → Repository files on server disksReference update coordination → Three-phase commit across replicas

  • Coordinates atomic ordered updates across replicas.
  • Adds distributed coordination and its availability/latency costs.

The contrast also meets R1 and Q2, so the requirements do not force the chosen single-server coordination.

ADR2 · Repository durability and manual failover Q2

Context. The design keeps a second copy of the origin disk and allows hand takeover. This supports keeping the canonical repository available after origin failure, which bears on CI fetching accepted state; the stated requirements do not set a recovery-time target, and the space does not assess volunteer workload.

Decision. Paired block-level disk copy.

Paired block-level disk copy chosen

Replication for durability → Block-level filesystem replication

“A second server in the same data centre receives a block-by-block copy of the origin's disk and can take over by hand if the origin fails”
  • Provides a second disk copy and a manual takeover path.
  • The space marks this approach rejected in the sources that discuss it.

This is a free choice relative to Q2 while the origin is healthy and CI fetches directly from it. The sources in the space argue against this replication approach, and its manual recovery fit is not established.

Three Git replicas with majority writes discarded

Replication for durability → Three Git replicas with majority writes

  • The space attests this durability approach and the evaluated combination.
  • Its operational burden for this four-volunteer team is not assessed by the space.

This attested alternative could preserve accepted updates across replicas, but the requirements do not force majority replication and the space does not compare its volunteer workload.

ADR3 · Contributor clone size R2Q1

Context. A first-time contributor must start without downloading the full history, and a contributor on a 50 Mbit/s connection has a two-minute latest-version target for a 40 GB monorepo.

Decision. Partial clone with sparse checkout.

Partial clone with sparse checkout chosen

Client data transfer → Partial clone with sparse checkout

“clone with a blob filter and a sparse checkout of the directories they work on”
  • Avoids requiring all history and limits transferred files to the contributor's work area.
  • The design reports no measurements proving the two-minute target; omitted objects may need later fetching.

The requirements force a reduced-transfer approach over full clone; the exact target still needs a measured clone result.

Full clone over Git discarded

Client data transfer → Full clone over the Git protocol

  • Leaves the complete history available locally.
  • Requires the full-history download and 40 GB exceeds the 750 MB theoretical two-minute transfer ceiling at 50 Mbit/s.

It misses R2 and Q1, so it cannot replace partial transfer for this problem.

ADR4 · Regional read serving Q1

Context. Contributors far from the European origin need the latest version quickly. Regional caches can serve repeated objects nearby, while the solution uses webhooks after pushes and directs CI to the origin.

Decision. Cache servers near clients.

Cache servers near clients chosen

Serving reads → Cache servers near the clients

“Cache servers in North America, Asia and South America serve clones and fetches”
  • Reduces read distance and can serve repeated objects locally.
  • Requires cache operations and freshness management; no timing result proves Q1.

Chosen as a plausible contributor-latency aid, not as a proven two-minute guarantee. The precise webhook and CI routing are not captured by this value.

#2 A region of #1: part of the solution grounded

Thought R1 and Q2 explain the canonical on-disk origin and its serialized reference updates: maintainers have one standard Git destination, and accepted pushes become ordered origin state for CI to fetch.

Move
  • Source of truth for repository state → Repository files on server disks
  • Reference update coordination → One server serializes the updates

Observed Git at any scale attests this combination. The single origin is the canonical push endpoint, and serialization gives CI a stable, ordered source after acceptance. These requirements call for a canonical, consistent authority but do not establish that local disks or single-server serialization are the only way to provide it.

R1 meetsQ2 meets

The file server stores each repository as a plain Git repository on its local disk, which is the authoritative state. That same server handles reference updates serially, so concurrent pushes are ordered and each update is applied atomically.

The point's trade-off This is simple to implement and provides clear consistency without distributed coordination. It gives up update throughput and horizontal availability, since the server and its disks are a central bottleneck and failure point.

#4 A region of #1: part of the solution grounded

Thought Q1 explains placing read caches near contributors in Asia and South America to reduce distance and repeat-transfer time.

Move
  • Serving reads → Cache servers near the clients

Observed Introducing Scalar attests regional cache servers, and the region matches the solution's topology. Nearby caches can reduce read latency and origin bandwidth, but the workspace has no measured regional clone time. The point's warning about stale cached objects is addressed in this solution by origin webhooks; the CI path bypasses caches and reads the origin.

Q1 partly

Regional or office cache servers handle fetches, clones, and CI checkouts close to users. On a cache miss, the local server forwards the request to the origin, stores the returned objects, and serves subsequent reads locally.

The point's trade-off This reduces latency and origin bandwidth for repeated reads, especially across distant offices. It adds cache storage and operational complexity, and cached objects may be stale or require invalidation before clients see newer data.

Attested by Introducing Scalar

Regions that justify the solution

G1 · Canonical serialized origin R1Q2 investigated at step 2

Source of truth for repository state → Repository files on server disks · Reference update coordination → One server serializes the updates

A single authoritative Git repository accepts maintainer pushes, and serialization provides the ordered state that direct-origin CI fetches after push acceptance. The requirements support this region, although they do not force its particular storage and coordination mechanisms.

G2 · Reduced contributor transfer R2Q1 investigated at step 3

Client data transfer → Partial clone with sparse checkout

Partial clone and sparse checkout let first-time contributors work without a full history and reduce transfer for a very large repository. The alternative full clone misses R2 and the arithmetic rules it out for Q1; actual performance still needs measurement.

G3 · Regional read caches Q1 investigated at step 4

Serving reads → Cache servers near the clients

Caches near distant contributors support lower read latency. This is consistent with Q1 but the two-minute target is unproven, and this value alone does not describe the cache webhook or direct-origin CI path.
