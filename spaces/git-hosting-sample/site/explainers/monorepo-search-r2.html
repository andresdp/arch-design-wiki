Hosting an open-source monorepo

An open-source foundation hosts a 12-year, 40 GB monorepo with about 300 daily pushes and 2,000 contributors across five continents. Most clones come from CI and first-time contributors who need only the latest version. Four volunteers operate donated servers in Europe and North America.

Alternatives

A1 · Replicated Git with regional reads

Keep plain Git repositories authoritative, coordinate updates across three replicas, and serve nearby reads from regional caches. Use partial clone with sparse checkout for contributor and CI transfers.

Composed of 2 partial design points, one per ADR:

  • ADR1 · Replicated plain Git R1Q2 Source of truth for repository state → Repository files on server disksReplication for durability → Three Git replicas with majority writesReference update coordination → Three-phase commit across replicas
  • ADR2 · Partial clone with nearby cache reads R2Q1Q2 Client data transfer → Partial clone with sparse checkoutServing reads → Cache servers near the clients

As a whole: Servers keep plain Git repositories as the authoritative state, maintaining three replicas and coordinating reference updates through a three-phase transaction. Developers use partial clone and sparse checkout, while regional cache servers serve nearby fetches and clones, forwarding misses to an origin.

B1 · Object-storage log with partial clones

Make the append-only object-storage log authoritative, use CAS for reference updates, and rebuild stateless local read caches. Partial clone limits client transfer.

Composed of 2 partial design points, one per ADR:

  • ADR1 · Object-storage log authority R1Q2 Source of truth for repository state → Write-ahead log in object storageReplication for durability → Durability delegated to object storageReference update coordination → Compare-and-swap on the log
  • ADR2 · Partial clone with stateless read servers R2Q1Q2 Client data transfer → Partial clone with sparse checkoutServing reads → Stateless servers with a local disk cache

As a whole: The object-storage append-only log is authoritative for objects and references, with writers using compare-and-swap when appending reference updates. Stateless servers reconstruct repositories into local caches from the log and serve reads, while Git partial clone and sparse checkout limit client transfers.

ADR1 · Repository authority, durability, and accepted writes R1Q2

Context. Maintainers need one canonical repository over standard Git, and CI must observe every accepted push. Local replicated Git offers explicit transactional coordination; an object-storage log provides one durable write authority with CAS, while server caches are derived. Neither combination has measured proof of the exact CI guarantee in this problem.

Decision. Replicated plain Git (A1); Object-storage log authority (B1).

Replicated plain Git chosen in A1

Source of truth for repository state → Repository files on server disksReplication for durability → Three Git replicas with majority writesReference update coordination → Three-phase commit across replicas

  • Canonical state remains in plain Git repositories.
  • Three replicas and coordinated reference transactions support durable accepted updates.
  • Replica coordination and recovery add volunteer operations work.
  • The space does not establish the exact CI visibility guarantee.

A1 favors direct Git authority and explicit replica coordination for pushes.

Object-storage log authority chosen in B1

Source of truth for repository state → Write-ahead log in object storageReplication for durability → Durability delegated to object storageReference update coordination → Compare-and-swap on the log

  • One append-only authority gives derived servers no unique state.
  • CAS sequences reference updates without coordinating Git replicas.
  • Correct immediate read visibility depends on log and cache behavior not quantified here.
  • Adds an object-storage log and reconstruction path.

B1 favors durable centralized authority and replaceable serving nodes.

Single file-server copy discarded

Source of truth for repository state → Repository files on server disksReplication for durability → Single copy on a file serverReference update coordination → One server serializes the updates

  • One server serializes updates simply.
  • A single copy risks availability and loss across donated sites.

Dropped because it gives up durability and can leave CI unable to fetch accepted state.

ADR2 · Contributor transfer and read serving R2Q1Q2

Context. New contributors and CI need small, fast checkouts across continents, while CI reads must remain fresh after a push. Partial clone is a standard Git transfer option; on-demand virtual filesystems can defer more object transfer but bring mixed support. Regional caches favor proximity, whereas nearest-up-to-date reads prioritize freshness and log-derived caches favor interchangeable servers.

Decision. Partial clone with nearby cache reads (A1); Partial clone with stateless read servers (B1).

Partial clone with nearby cache reads chosen in A1

Client data transfer → Partial clone with sparse checkoutServing reads → Cache servers near the clients

  • Partial transfer serves first-time contributors without full history.
  • Regional cache servers put reads closer to distant contributors.
  • Cache freshness can complicate post-push reads.
  • No measured data proves the two-minute target.

A1 chooses lower geographic read distance while retaining standard Git partial clone.

Partial clone with stateless read servers chosen in B1

Client data transfer → Partial clone with sparse checkoutServing reads → Stateless servers with a local disk cache

  • Partial clone limits client data transfer.
  • Servers can rebuild local cached copies from durable log state.
  • Cache misses and rebuilds can add latency.
  • No measured data proves the two-minute target or immediate post-push fetch behavior.

B1 keeps client transfer modest and pairs reads with replaceable log-derived servers.

Virtualized client with regional caches discarded

Client data transfer → Virtualized filesystem with on-demand objectsServing reads → Cache servers near the clients

  • Objects transfer on demand and regional caches reduce distance.
  • Virtual filesystem support is mixed and cache freshness is not assured.

Set aside because it increases client complexity without measured evidence for Q1.

Virtualized client with stateless servers discarded

Client data transfer → Virtualized filesystem with on-demand objectsServing reads → Stateless servers with a local disk cache

  • On-demand objects reduce initial client transfer and servers remain replaceable.
  • Object retrieval and cache rebuild latency can hurt the deadline; client and operations complexity increases.

The exploration did not improve on the partial-clone alternative for this volunteer-run service.

Round 1 · 3 points: seed A, seed B, seed C
#1 Seed of approach A mixed

Thought Replicated Git state and coordinated ref updates should serve R1 and Q2; partial clone should serve R2 and partly serve Q1.

Move
  • Source of truth for repository state → Repository files on server disks
  • Replication for durability → Three Git replicas with majority writes
  • Reference update coordination → Three-phase commit across replicas
  • Client data transfer → Partial clone with sparse checkout
  • Serving reads → Nearest up-to-date replica

Observed The point has no source attesting the complete combination. The nearest up-to-date replica directly supports freshness, while the space gives no measured clone time or operational staffing estimate.

R1 meetsR2 meetsQ1 partlyQ2 meetsC1 partly
  • Three Git replicas with majority writes, Three-phase commit across replicas: gains Q2 gives up C1: Majority replication and multi-replica transactions strengthen durable, ordered writes but add operational work for a small volunteer team.
  • Partial clone with sparse checkout: gains R2 gives up Q1: Partial transfer reduces the initial checkout but the space supplies no two-minute performance result.

The servers’ local plain Git repositories are authoritative, with each update coordinated as a three-phase transaction and replicated to three copies, succeeding after a majority records it. Clients use partial clone and sparse checkout, while fetches and checkouts are routed to the nearest replica containing the latest state.

The point's trade-off This provides durable copies, atomic reference updates, reduced client transfer, and potentially lower read latency. It gives up simpler operations and write latency because replicas must coordinate, and requires careful replica freshness tracking; partial clones also complicate clients and may require later object retrieval.

No source attests this combination.

The point's trade-off This provides durable storage, machine-loss tolerance, interchangeable read servers, and reduced client downloads. It gives up fast independent serving when log access or cache rebuilding is slow and relies on object-storage CAS semantics rather than consensus for concurrent updates.

#3 Seed of approach C weak

Thought A single serialized origin should keep pushes simple; caches and on-demand objects should serve R2 and partly serve Q1.

Move
  • Source of truth for repository state → Repository files on server disks
  • Replication for durability → Single copy on a file server
  • Reference update coordination → One server serializes the updates
  • Client data transfer → Virtualized filesystem with on-demand objects
  • Serving reads → Cache servers near the clients

Observed This is operationally simple, but its single-copy durability choice is a poor fit for a service split across two data centres and undermines reliable CI access after accepted pushes.

R1 meetsR2 meetsQ1 partlyQ2 partlyC1 meets
  • Single copy on a file server: gains C1 gives up Q2: One copy is easier to operate but a machine or site loss can make accepted state unavailable, so read-after-push is not assured.
  • Virtualized filesystem with on-demand objects, Cache servers near the clients: gains R2 gives up Q1: On-demand objects and regional caches reduce initial downloads but add client and cache behavior, with no measured clone time.

A file server holds each plain Git repository as the authoritative copy and serializes all reference updates. Regional cache servers serve read traffic, while clients use a virtual filesystem that fetches needed objects on demand, forwarding cache misses to the file-server origin.

The point's trade-off This is simple and provides centralized update ordering, nearby reads, and reduced client downloads. It sacrifices durability and availability through its single repository copy and server, and concentrates writes at one server.

No source attests this combination.

#5 New approach D, started from #2 mixed

Thought On-demand objects should reduce the initial transfer beyond partial clone for R2 and Q1 while retaining the log and rebuildable read servers.

Move
  • change Client data transfer: Partial clone with sparse checkout → Virtualized filesystem with on-demand objects

Observed Git at any scale attests the combination. The lower initial transfer is attractive, but the source evidence is mixed for virtualized filesystems and does not establish the target clone time; this does not beat the partial-clone point overall.

R1 meetsR2 meetsQ1 partlyQ2 partlyC1 partly
  • Write-ahead log in object storage, Durability delegated to object storage, Compare-and-swap on the log: gains R1 gives up Q2: A canonical log and CAS make one ordered write authority, but immediate CI visibility is not guaranteed by the design-space evidence.
  • Virtualized filesystem with on-demand objects, Stateless servers with a local disk cache: gains R2 gives up Q1, C1: Fetching objects on demand limits initial downloads, but adds virtual filesystem support and remote object latency to the clone path and operational surface.

The object-storage append-only log is the authoritative repository state, with reference updates committed by compare-and-swap; servers reconstruct local cached copies from it and serve reads without holding unique data. Developers use a virtual filesystem that fetches objects on demand, while any server can rebuild or warm its cache as needed.

The point's trade-off This gains durable centralized storage, stateless failover, and reduced client downloads, but log replay, cache misses, and object-fetch latency can slow reads. The virtual filesystem also adds client and filesystem complexity and depends on timely object retrieval.
