Hosting an open-source monorepo

An open-source foundation must host a 12-year, 40 GB monorepo with about 300 pushes daily and 2,000 contributors across five continents. Most clones are from CI and first-time contributors who need only the latest version. Four volunteers run donated servers in Europe and North America.

How to read this page

A coding agent searched for designs that solve this problem. It combined decisions (dimensions) and their options (values) into design points, and judged each point against every requirement: meets, partly or misses. It proposes 3 alternatives. Every judgement here is the agent's; the page lays out its rationale file.

  • Decisions (ADRs) lists the alternatives, then one record per decision: the requirements that drive it, and every option weighed, with its pros and cons, chosen by an alternative or discarded.
  • Comparison puts the alternatives side by side, with the rows where they differ first.
  • Trajectory shows how the agent got there:
    • the lanes show each approach round by round, with every point coloured strong, mixed or weak;
    • a strip shows how each point met each requirement;
    • the story gives each point's thought, change, observation and trade-offs.

Gaps in the space, at the bottom, lists where the design space fell short: requirements no dimension bears on, and values that only roughly fit. Every dimension and value links to its page in the space's wiki.

Alternatives

A1 · Replicated Git with regional cache

Keep plain Git repositories on server disks, coordinate updates across three replicas, and serve partial clones through regional caches. This is the clearest path using standard Git transfer with replicated accepted state, though its performance and volunteer burden need measurement.

Composed of 3 partial design points, one per ADR:

  • ADR1 · Replicated plain Git R1Q2 Source of truth for repository state → Repository files on server disksReplication for durability → Three Git replicas with majority writesReference update coordination → Three-phase commit across replicas
  • ADR2 · Partial clone with sparse checkout R2Q1 Client data transfer → Partial clone with sparse checkout
  • ADR3 · Regional cache servers Q1Q2 Serving reads → Cache servers near the clients

As a whole: Three plain Git repositories on separate server disks hold authoritative state, with writes succeeding after a majority acknowledges them. Reference changes use three-phase commit across the replicas, while clients use partial clone and sparse checkout; regional cache servers serve fetches and clones, forwarding misses to an origin.

B1 · Object-store log with partial clone

Use an append-only object-store log as authority, conditional updates for references, partial clones, and stateless read caches. This delegates durability and server recovery, but adds log and cache behavior to the operator workload.

Composed of 3 partial design points, one per ADR:

  • ADR1 · Object-store log R1Q2 Source of truth for repository state → Write-ahead log in object storageReplication for durability → Durability delegated to object storageReference update coordination → Compare-and-swap on the log
  • ADR2 · Partial clone with sparse checkout R2Q1 Client data transfer → Partial clone with sparse checkout
  • ADR3 · Stateless servers with local disk cache Q1Q2 Serving reads → Stateless servers with a local disk cache

As a whole: Object storage is authoritative for an append-only repository log, and compare-and-swap serializes reference changes. Stateless servers rebuild local read caches from the log; partial clone and sparse checkout reduce client transfer.

D1 · Object-store log with regional cache

Keep the object-store log and conditional reference updates, with partial clone and regional read caches. This prioritizes geographic read placement while requiring explicit cache freshness handling.

Composed of 3 partial design points, one per ADR:

  • ADR1 · Object-store log R1Q2 Source of truth for repository state → Write-ahead log in object storageReplication for durability → Durability delegated to object storageReference update coordination → Compare-and-swap on the log
  • ADR2 · Partial clone with sparse checkout R2Q1 Client data transfer → Partial clone with sparse checkout
  • ADR3 · Regional cache servers Q1Q2 Serving reads → Cache servers near the clients

ADR1 · Authoritative state, durability, and reference updates R1Q2

Context. The canonical repository must accept pushes and CI must observe accepted pushes. Replication and update ordering can protect this path, while the four-volunteer constraint makes operational complexity relevant but does not map to a design-space dimension.

Decision. Replicated plain Git (A1); Object-store log (B1, D1).

Replicated plain Git chosen in A1

Source of truth for repository state → Repository files on server disksReplication for durability → Three Git replicas with majority writesReference update coordination → Three-phase commit across replicas

  • Uses plain Git repository state.
  • Majority replication and transactional reference changes support a durable, ordered accepted-write path.
  • Adds replica coordination and storage overhead.
  • The space does not establish the standard protocol behavior or guarantee CI freshness under all failures.

Chosen by A1 for a direct Git authority and replicated reference updates.

Object-store log chosen in B1, D1

Source of truth for repository state → Write-ahead log in object storageReplication for durability → Durability delegated to object storageReference update coordination → Compare-and-swap on the log

  • A durable log is authoritative and conditional appends order updates.
  • Servers hold no unique data.
  • Depends on object-store durability and conditional-update behavior.
  • The complete end-to-end consistency guarantee is not proven by the space.

Chosen by B1 and D1 to make log durability and conditional update order central.

Single file server discarded

Source of truth for repository state → Repository files on server disksReplication for durability → Single copy on a file serverReference update coordination → One server serializes the updates

  • One server serializes updates with a simple authority.
  • A single copy provides no replicated recovery path.

Dropped because one failed file server can lose availability or accepted state, undermining Q2.

ADR2 · How clients obtain repository data R2Q1

Context. First-time contributors should avoid transferring the whole history, and distant contributors have a strict clone-time target. Partial transfer and on-demand access reduce initial data, but only the latter has mixed evidence and neither has a measured two-minute result in the space.

Decision. Partial clone with sparse checkout (A1, B1, D1).

Partial clone with sparse checkout chosen in A1, B1, D1

Client data transfer → Partial clone with sparse checkout

  • Fetches only needed history and files.
  • Uses standard Git features.
  • Does not quantify the clone time for the stated repository, network, and geography.

Chosen across alternatives because it directly addresses avoiding the full history with standard Git features.

Virtualized filesystem with on-demand objects discarded

Client data transfer → Virtualized filesystem with on-demand objects

  • Downloads objects only when opened, reducing initial transfer.
  • Evidence is mixed and on-demand object latency is unmeasured.

Set aside in favor of partial clone's standard Git feature path and clearer evidence.

ADR3 · Read serving for distant contributors and CI Q1Q2

Context. Readers span five continents while servers are in two regions. Near or rebuildable caches can reduce read distance, but Q2 requires that a post-acceptance CI fetch sees the accepted push; the design space does not specify cache invalidation or a numeric latency guarantee.

Decision. Regional cache servers (A1, D1); Stateless servers with local disk cache (B1).

Regional cache servers chosen in A1, D1

Serving reads → Cache servers near the clients

  • Places read caches near clients and forwards misses to the origin.
  • Cache freshness and the two-minute target are not established.

Chosen where the alternatives prioritize read geography; freshness needs an explicit implementation policy.

Stateless servers with local disk cache chosen in B1

Serving reads → Stateless servers with a local disk cache

  • Any server can serve a repository and rebuild its local cache from the log.
  • Cache warming may add latency, and freshness after acceptance is unspecified.

Chosen by B1 to pair flexible read serving with object-store authority.

Nearest up-to-date replica discarded

Serving reads → Nearest up-to-date replica

  • Routes reads to the closest replica known to have current state.
  • May not place cache capacity close enough for the two-minute target.

Considered for freshness, then set aside in favor of read placement or rebuildable serving in the selected alternatives.

#1 Seed of approach A mixed

Thought Three replicas and transactional reference updates should support R1 and Q2; partial clone and nearest-current reads should help R2 and Q1.

Move
  • Source of truth for repository state → Repository files on server disks
  • Replication for durability → Three Git replicas with majority writes
  • Reference update coordination → Three-phase commit across replicas
  • Client data transfer → Partial clone with sparse checkout
  • Serving reads → Nearest up-to-date replica

Observed The point combines familiar Git state with strong replication and current-read intent. It is unattested as a complete combination, and the space gives no measured performance or volunteer workload evidence.

R1 partlyR2 meetsQ1 partlyQ2 partlyC1 partly
  • Three Git replicas with majority writes, Three-phase commit across replicas: gains Q2 gives up C1: Replication and coordinated updates support consistent accepted writes but add systems and operating work for the small volunteer team.
  • Partial clone with sparse checkout, Nearest up-to-date replica: gains R2 gives up Q1: Selective transfer and nearby current reads reduce work and distance, though the space provides no measurements to prove the two-minute target.

Plain Git repositories on server disks remain authoritative, with three replicas storing each repository and majority writes providing durability. Three-phase commit orders reference updates atomically across replicas; fetches use the nearest up-to-date replica, while partial clone and sparse checkout limit client transfer.

The point's trade-off This provides machine-loss tolerance, local read performance, and reduced client bandwidth, but requires triple storage and coordination overhead. Writes and reads can incur latency or reduced availability when replicas cannot coordinate or one is not current.

No source attests this combination.

#2 Seed of approach B mixed

Thought A durable log and conditional append should support R1 and Q2; stateless caches and on-demand objects should reduce transfer and operator-specific state for Q1, R2, and C1.

Move
  • Source of truth for repository state → Write-ahead log in object storage
  • Replication for durability → Durability delegated to object storage
  • Reference update coordination → Compare-and-swap on the log
  • Client data transfer → Virtualized filesystem with on-demand objects
  • Serving reads → Stateless servers with a local disk cache

Observed The combination is attested by Git at any scale, but the design space labels on-demand filesystem evidence mixed and does not quantify clone completion or operational burden.

R1 partlyR2 meetsQ1 partlyQ2 partlyC1 partly
  • Write-ahead log in object storage, Durability delegated to object storage, Compare-and-swap on the log: gains Q2 gives up C1: The durable log and conditional update path support ordered writes but make volunteers depend on object-store behavior and log-derived serving.
  • Virtualized filesystem with on-demand objects, Stateless servers with a local disk cache: gains R2 gives up Q1: On-demand objects and rebuildable caches reduce initial transfer and server-specific state, while cache warming and object fetch latency leave the strict clone target unproven.

The object-storage append-only log is authoritative, and writers conditionally append reference updates with compare-and-swap; local repository copies are rebuildable derivatives. Stateless servers populate local caches from the log for reads, while clients use a virtual filesystem that fetches objects on demand.

The point's trade-off This provides durable storage, machine-independent serving, and reduced client downloads. It gives up immediate local availability: cache rebuilding and object access can add latency, while coordination depends on the object store’s compare-and-swap rather than a consensus protocol.
